# 한정 수량 예약 백엔드 개발 헌법

## Core Principles

### I. 서비스 경계와 API 호환성 유지

단일 Spring Boot 애플리케이션과 기능별 책임 경계를 유지한다.
`resource`는 예약 대상, `reservation`은 예약·취소를 담당하고,
`security`와 `ratelimit`은 이를 지원한다. `common`을 독립 업무 도메인으로 간주하지 않는다.
Controller는 HTTP 변환, Service는 요청 조정, 별도 Writer Bean은 트랜잭션,
Repository는 SQL을 담당한다. PostgreSQL은 수량·예약·성공한 생성 키의 유일한 원본이며,
Redis는 요청 제한만 담당한다.

기존 API와 계획서 4절의 확정 계약을 보존한다. 호환성 검토에는 메서드·경로·입력·권한,
성공 및 오류 상태·code, 응답 필드·헤더, 멱등 재현과 취소 동작을 포함한다.
리팩터링이나 테스트 통과를 이유로 계약을 바꾸지 않는다.
계약 변경이 필요하면 이유·호환성 영향·대응을 설명하고 사용자 지시에 따라
계획서·관련 도메인 문서·OpenAPI·테스트를 함께 갱신한다.
이는 계층 정리나 경쟁 처리 수정이 사용자에게 보이는 동작을 임의로 바꾸지 않게 한다.

### II. 도메인 근거를 확인한 설계

새 개발·수정·테스트·리뷰를 시작하기 전에 `knowledge/README.md`와 하위 Markdown 목록,
`knowledge/rules/`의 모든 규칙, 작업 대상과 연관 도메인의 문서를 읽는다.
연결된 계획서 절을 확인하고 실제 코드·SQL·테스트·설정과 대조한 뒤 설계한다.
업무 규칙·API·DB의 기준은 계획서 2~5절이며 최신 사용자 지시를 우선한다.
진행 설명에는 적용한 문서와 이번 검증 대상을 밝힌다.

새 도메인 또는 문서가 없는 기존 도메인은 개발 전에 `knowledge/domain/_template.md`를
기반으로 책임·데이터·불변식·상태 전이·권한·오류·멱등성·경쟁·장애·검증 근거를 기록하고
`knowledge/README.md` 목록에 등록한다. 적용하지 않는 항목에는 이유를 남긴다.
템플릿 예시를 확정 정책으로 복사하지 않는다.
문서와 구현이 다르면 차이와 영향을 확인하며, 구현만을 근거로 설계 규칙을 바꾸지 않는다.

### III. 기존 검증 방식과 실행 증거

한 단계의 한 검증 대상씩 진행한다. 기능 변경은 규칙·기대값 확인 → 테스트 작성 →
의도한 동작 실패 확인 → 최소 구현 → 관련 테스트와 영향받는 기존 테스트 실행 →
정리·재검증 순서를 따른다. 컴파일 오류는 기능 실패 검증의 증거가 아니다.
환경 변경은 최소 실행으로, 문서 변경은 내용·링크·형식 검사로 검증한다.

프로젝트의 테스트 분류와 발견 계약을 따른다. 순수 Unit은 Spring 없는 `*Test`,
Integration은 실제 PostgreSQL·Redis Testcontainers의 `*IT`로 구분한다.
Contract는 고정 OpenAPI 3.0.3과 실제 HTTP, Security는 실제 인증·보안 필터를 검사한다.
Property는 독립 모델·seed 재현·shrinking, PIT는 순수 규칙의 변이 탐지를 검증한다.
SQL·권한은 별도 고의 변경으로 탐지력을 확인하고 원복한다.
경쟁 검증은 독립 요청·트랜잭션의 응답과 모든 작업 종료 후 DB 불변식을 함께 검사한다.
k6는 threshold 종료 코드와 최종 DB 검사로 판정한다.

실제 존재하는 Gradle 태스크의 실행 범위·발견 규칙을 확인한다.
일반 `test`·`build`를 전체 심화 검증으로 간주하지 않는다.
테스트 0건·skip·변이 0건·NO_COVERAGE는 성공이 아니다.
실패를 반복 실행·mock 대체·임의 기대값 변경·버전 하향·`continue-on-error`로 숨기지 않는다.
명령·종료 코드·테스트 수·환경·seed·경쟁 및 장애 조건·미검증 범위를 기록한다.
새 변경·실패·미해결 문제가 없으면 무거운 전체 검증을 불필요하게 반복하지 않는다.

### IV. 업무 정책과 도메인 문서의 동기화

업무 정책이나 동작·계약을 변경하면 계획서와 관련 `knowledge/domain/` 문서,
공통 규칙·OpenAPI·테스트를 같은 변경 범위에서 갱신한다.
도메인 문서에는 책임·불변식·유스케이스·실패·경쟁·검증 사례와 변경 영향을 반영한다.
파일 추가·이름 변경 시 지식 문서 목록과 링크를 갱신한다.
코드와 문서가 서로 다른 정책을 설명하는 상태로 작업을 완료하지 않는다.

지속적인 지식·규칙은 `knowledge/`에, 결정·버전·실행 증거·성능은 프로젝트 루트 `docs/`의
기존 기록 체계에 둔다. 설계됨·구현됨·실행 검증됨을 구분한다.
실제 존재하는 코드·SQL·테스트와 실행 증거만 연결하며 없는 파일·명령은 예정으로 표시한다.
정책 변경의 근거와 검증을 함께 남겨 이후 수정에서도 같은 기대값을 사용할 수 있게 한다.

### V. 미확정 정책의 명시와 확인

기존 자료와 최신 사용자 지시로 확인되지 않은 업무 정책을 임의로 확정하지 않는다.
미확정 항목에는 질문·근거 부족·영향 범위를 명시하고 사용자에게 확인한다.
답변이 필요한 정책에 의존하는 설계·구현은 답변 전 확정하지 않으며,
확정된 정책에 대한 독립 작업은 계속할 수 있다.

문서·계획·구현 사이의 충돌은 차이와 영향을 설명해 기준을 확인한다.
도구 후보, 공식 자료 확인, 실제 채택, 실행 호환성 검증을 구분한다.
아직 없는 API·도메인 문서·CI·테스트 기반을 구현 또는 통과 상태로 표현하지 않는다.
이 원칙은 추측이 업무 규칙이나 완료 기록으로 굳어지는 것을 막는다.

### VI. 로컬 브라우저 콘솔은 백엔드 계약의 얇은 클라이언트

2026-10-26 사용자 지시로 저장소 루트 `frontend/`에 로컬 브라우저 콘솔을 둔다.
콘솔은 완료된 백엔드 API를 사람이 직접 조작·관찰하기 위한 클라이언트이며,
수량·예약·멱등성의 원본은 계속 PostgreSQL이다. 콘솔은 잔여 수량·예약 상태를
추측하거나 계산해 확정 값으로 표시하지 않고, 백엔드 응답만을 사실로 표시한다.

콘솔 작업은 백엔드 API 계약·보안 설정·SQL을 바꾸지 않는다. 백엔드에 CORS 허용을
추가하지 않으며, 브라우저는 같은 출처의 콘솔 서버를 거쳐서만 백엔드에 접근한다.
콘솔 서버는 계약에 정의된 경로·메서드만 전달하고 임의 사용자 식별 헤더를 만들지 않는다.
비밀번호는 브라우저 저장소·쿠키·로그·저장소 파일에 남기지 않는다.
브라우저 도입으로 달라지는 인증·CSRF 전제는 설계에 근거와 함께 기록한다.

콘솔도 Spec Kit·TDD 절차와 실행 증거 원칙(III)을 따른다. 기능은 실패하는 테스트로
시작하고, 순수 규칙·화면·서버 전달 계층의 자동 테스트와 실제 백엔드에 대한
종단 검증을 구분해 기록한다. 모의 응답만으로 실제 백엔드 연동을 검증했다고 하지 않는다.
의존성은 정확한 버전으로 고정하고 lockfile을 커밋한다.

## 기술·운영 제약과 확인 상태

- Java 25, preview 제외, 기존 `backend/`와 `com.limitedbooking.backend`를 유지한다.
  Gradle·패키지·경로를 계획서의 Maven 예시로 자동 교체하지 않는다.
  테스트 분류·실행 계약은 구현 단계에서 명시적인 Gradle 태스크로 구성한다.
- Spring MVC/Security/JDBC와 `NamedParameterJdbcTemplate`, Flyway를 설계 기준으로 사용한다.
  JPA 자동 스키마 생성이나 H2로 PostgreSQL 검증을 대체하지 않는다.
- 대상별 `0 ≤ available ≤ capacity`와
  `available + CONFIRMED 예약 수 = capacity`를 유지한다.
  사용자·생성 키당 예약은 최대 1개, 취소당 수량 복구는 최대 1개다.
  상태 전이는 `CONFIRMED → CANCELLED`만 허용하고 실패 트랜잭션은 부분 반영하지 않는다.
  생성·취소의 갱신 잠금 순서는 `resource → reservation`을 유지한다.
- 인증 UUID는 인증 결과에서만 얻는다. 타인 예약 조회·취소는 관리자에게도 404다.
  본문 제한·인증·요청 제한·입력 검증의 순서와 엄격한 JSON·오류 계약을 유지한다.
  Redis 제한·장애로 거부된 예약 쓰기는 DB를 변경하지 않는다.
- 실행은 localhost CLI/API 클라이언트와 2026-10-26 사용자 지시로 추가한
  localhost 전용 `frontend/` 브라우저 콘솔(원칙 VI) 범위다. 외부 공개·배포·
  그 밖의 브라우저 서비스는 별도 설계와 사용자 지시가 필요하다. 비밀번호·`.env`를 커밋하지 않고,
  기본 종료 절차에 DB 볼륨 삭제를 넣지 않는다.
- 2026-10-13 저장소 확인: Boot 4.1.1·Gradle Wrapper 9.7.1의 최소 골격과
  `BackendApplicationTests.contextLoads`가 존재한다. 개별 도메인 문서,
  예약 API·SQL·Redis·심화 테스트 기반과 CI 설정은 발견되지 않았다.
  `backend/build.gradle`의 `test`는 JUnit Platform을 사용하지만
  계획된 테스트 분류별 태스크는 아직 없다. 이 확인은 테스트 실행 성공의 증거가 아니다.
- 계획서 7절 12단계의 verify/deep-tests CI는 `.github/workflows/`에 둔다.
  `.specify/workflows/`는 Spec Kit 작업 절차이며 CI가 아니다. CI 파일 작성과 외부 CI 성공을 구분한다.
  2026-10-26 사용자 결정: verify는 pull_request·push(develop/main)에서 GitHub Actions로 실행하고,
  deep-tests는 workflow_dispatch 수동 실행만 둔다. 코드 리뷰(OCR)는 GitHub Actions로 실행하지 않는다.
  외부 실행 결과는 실제 run 기록이 있을 때만 성공으로 기록한다.

## 개발 절차와 검토 기준

1. 기준 문서와 실제 상태를 확인하고 한 검증 대상·기대값·영향 범위를 정한다.
   미확정 정책은 질문하고 이번 변경에 적용하는 근거를 밝힌다.
2. 실제 구현은 계획서의 `superpowers:executing-plans` 또는
   `superpowers:subagent-driven-development` 절차를 적용한다.
   변경 종류에 맞는 실패 확인·최소 구현·관련 검증을 수행한다.
3. 검토 시 서비스 경계, API 호환성, 수량·멱등성·취소·권한·롤백,
   문서 동기화, 테스트 발견과 실제 실행 증거를 확인한다.
   실패·skip·미원복 고의 결함이 남은 작업은 통합하지 않는다.
4. Git 작업은 `knowledge/rules/commit.md`와 `git-flow.md`를 따른다.
   저장소 최상위·HEAD·브랜치·기존 변경을 재확인하고 작업 브랜치와 목적별 커밋을 사용한다.
   사용자 변경을 보존하고 파일 경로를 명시해 스테이징한다.
   Conventional Commits의 type·scope는 영문, 제목·본문 설명은 한국어로 작성한다.
5. 완료 보고에는 변경 이유·실제 검증·미완료 및 미검증 범위·읽을 핵심 파일·다음 한 작업을 담는다.
   push·공개·외부 workflow 실행은 별도 사용자 지시 범위에서 수행한다.

## Governance

이 헌법은 기존 프로젝트 지침을 개발·리뷰의 공통 기준으로 정리한다.
최신 사용자 지시를 우선하고, 설계와 업무 계약의 기준은 계획서 2~5절로 유지한다.
`AGENTS.md`는 작업 지침, `knowledge/rules/`는 상세 개발 규칙,
`knowledge/domain/`은 해당 도메인의 정책과 근거를 제공한다.
헌법과 이들 문서가 충돌하면 임의로 우선순위를 새로 정하지 않고 차이와 영향을 확인한다.

개정 시 변경 이유·근거·영향받는 원칙·호환성·검증 범위를 명시한다.
업무 정책이나 계약의 개정은 관련 계획서·지식 문서·OpenAPI·테스트를 함께 갱신한다.
미확정 정책은 사용자 답변을 반영한 뒤 확정한다.
Spec Kit 헌법 명령 자체는 헌법 파일만 변경하며,
다른 산출물의 수정이 필요한 경우 후속 작업으로 명시한다.

헌법 버전은 SemVer를 따른다. 원칙 삭제나 호환되지 않는 재정의는 MAJOR,
새 원칙·절 또는 실질적인 지침 확장은 MINOR, 의미를 바꾸지 않는 명확화·오탈자 수정은 PATCH다.
`1.0.0`은 개발 헌법의 최초 작성 버전이며 애플리케이션의 출시·완료 버전과 별개다.
