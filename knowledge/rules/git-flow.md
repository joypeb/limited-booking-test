# Git Flow 규칙

사용자 요청으로 추가한 브랜치 운영 규칙이다. [계획서](<../../한정 수량 예약 백엔드 로컬 개발 계획.md>)의 단계별 검증·로컬 실행·외부 push 제한을 유지한다. 커밋 형식과 검증은 [커밋 규칙](commit.md)을 따른다. Git Flow는 브랜치 운영 방식이며 별도 `git-flow` 도구 설치를 요구하지 않는다.

## 브랜치 역할과 이름

| 브랜치 | 역할 | 시작 기준 | 병합 대상 |
|---|---|---|---|
| `main` | 검증한 로컬 기준 버전 | 최초 저장소 구성 | release·hotfix 결과를 받음 |
| `develop` | 완료한 작업을 통합하는 브랜치 | main | 다음 release의 기준 |
| `feature/<주제>` | 한 기능·검증 대상 개발 | develop | develop |
| `fix/<주제>` | 개발 중 발견한 결함 수정 | develop | develop |
| `docs/<주제>` | 문서 작업 | develop | develop |
| `chore/<주제>` | 도구·환경·유지보수 | develop | develop |
| `release/<버전>` | 로컬 기준 버전 확정·검증 | develop | main, 이후 수정 내용을 develop에도 반영 |
| `hotfix/<주제>` | main 기준 버전의 긴급 결함 수정 | main | main과 develop, 진행 중인 release에도 반영 |

- 주제는 소문자 영문·숫자·하이픈으로 짧게 쓴다. 예: `feature/reservation-idempotency`, `test` 목적을 포함한 `feature/reservation-concurrency`, `docs/git-rules`.
- 하나의 작업 브랜치는 한 목적을 담당한다. 관련 없는 단계 전체를 장기간 한 브랜치에 쌓지 않는다.
- main·develop에 일반 기능을 직접 커밋하지 않는다. 초기 저장소 구성은 예외이며 최초 커밋 후 develop을 만든다.
- release·hotfix는 필요할 때만 만든다. 이 프로젝트에서 release는 로컬 검증 버전이며 배포·공개를 뜻하지 않는다.

## 초기 상태와 작업 시작

2026-10-13 확인 시 현재 브랜치 이름은 main이며 HEAD 커밋은 없다. develop·작업 브랜치가 이미 생성됐다고 가정하지 않는다. 이 문서 작성은 실제 커밋·브랜치 생성 수행 기록이 아니다.

1. 저장소 최상위·현재 브랜치·HEAD 존재 여부·작업 트리·로컬 브랜치를 확인한다.
2. 최초 커밋이 없으면 파일과 제외 규칙을 선별·검토하고, 초기 구성 작업에서 최소 골격을 검증해 최초 커밋을 만든다. 미구현·미검증 범위를 명시한다. 그 뒤 main에서 develop을 생성한다.
3. 일반 작업은 develop을 기준으로 새 작업 브랜치를 만든다. 기존 변경이 있으면 소유자와 범위를 확인하고 안전하게 보존한다. 무조건 reset·clean·stash로 지우거나 옮기지 않는다.
4. 원격 저장소가 있고 동기화가 지시된 경우 fetch로 변경을 확인하고 명시적으로 통합한다. 원격이 없는 로컬 작업은 로컬 브랜치를 기준으로 진행한다.

최초 커밋과 develop이 존재하고 작업 트리가 안전한 경우의 로컬 작업 예시다. 아래 명령은 안내이며 실행 기록이 아니다.

```sh
git switch develop
git switch -c feature/reservation-idempotency
```

## 작업 완료와 develop 통합

1. 규칙·기대값 확인 → 실패 테스트 → 최소 구현 → 관련 검증 순서로 작업하고 작은 커밋을 남긴다.
2. develop이 바뀌었다면 작업 브랜치에 develop을 merge한다. 충돌은 양쪽 의도·계약·SQL·테스트를 확인해 해결하고 영향받는 검증을 다시 실행한다.
3. develop과의 전체 diff, 변경된 계약·문서, 실행 증거, 미검증 범위를 검토한다. 실패·skip·미원복 고의 결함이 남은 작업은 통합하지 않는다.
4. 로컬에서는 develop으로 전환해 `git merge --no-ff <작업 브랜치>`로 작업 경계를 보존한다. 원격 협업이 지시된 경우에는 같은 검토 내용을 PR에 담고 merge commit 방식으로 통합한다.
5. 병합 결과에서 영향받는 검증을 실행한다. 동일한 코드에 새 변경·실패가 없으면 무거운 전체 부하를 반복하지 않는다.
6. 브랜치 정리는 병합·검증·남은 고유 커밋 여부를 확인한 뒤 수행한다. 미병합 브랜치를 강제로 삭제하지 않는다.

- PR에는 문제·변경된 동작·실제 검증·미검증·읽을 핵심 파일을 적는다. 로컬 리뷰와 외부 PR·CI 결과를 구분한다.
- 공유 브랜치는 rebase·강제 push로 이력을 재작성하지 않는다. 기준 브랜치 동기화는 명시적인 merge를 기본으로 한다.

## release와 hotfix

- release는 develop에서 만들고 새 기능 추가를 멈춘다. 버전·문서·최종 검증과 결함 수정만 반영한다.
- 버전은 `0.x.y`로 시작하는 로컬 개발 버전으로 관리한다. 검증한 기능 범위가 늘면 MINOR, 해당 기준 버전의 결함 수정은 PATCH를 올리고, `1.0.0`은 합의한 첫 버전 완료 기준을 충족할 때 사용한다. 실제 Gradle 버전과 기록을 함께 맞춘다.
- 합의한 완료 범위의 검증과 재현 절차를 확인한 release만 main에 `--no-ff`로 병합한다. 6단계 핵심 버전과 12단계 최종 버전을 구분하고, 태그가 전체 계획 완료를 뜻하지 않게 기록한다.
- main의 병합 결과를 확인하고 `v<버전>` annotated tag를 남긴다. 태그는 검증한 로컬 기준점을 표시한다. 이미 공유한 태그를 다른 커밋으로 이동하지 않는다.
- release의 수정은 develop에도 병합하고 그 결과를 검증한다. 진행 중인 기능을 main으로 역반영하지 않는다.
- hotfix는 main에서 분기해 결함 재현 테스트·최소 수정·관련 검증을 수행한 뒤 main에 병합하고 PATCH 버전을 태그한다. 같은 수정은 develop과 진행 중인 release에도 반영한다.
- 잘못 병합한 변경은 공유 이력을 유지하는 revert로 되돌리고 관련 검증을 수행한다. merge commit 되돌림은 부모와 후속 재병합 영향을 확인한 뒤 처리한다.
- push·원격 브랜치 삭제·PR 게시·외부 CI 실행·공개·배포는 해당 작업에 대한 사용자 지시 범위에서만 수행한다. 이 규칙의 작성 자체는 외부 작업 지시가 아니다.
