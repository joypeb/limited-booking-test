# 커밋 규칙

근거: [계획서](<../../한정 수량 예약 백엔드 로컬 개발 계획.md>) 1.3절의 검증 후 작은 커밋, 8.3절의 실행 기록과 사용자 요청으로 추가한 커밋 규약. 브랜치와 병합은 [Git Flow 규칙](git-flow.md)을 따른다.

## 커밋 단위

- 한 커밋은 한 목적·한 검증 대상을 담는다. 기능 추가, 무관한 리팩터링, 의존성 변경을 섞지 않는다.
- 동작 변경에 필요한 코드·SQL·테스트·OpenAPI·계획서·지식 문서는 함께 반영한다. 같은 규칙을 설명하는 파일을 분리해 서로 모순되는 상태를 만들지 않는다.
- 기능 커밋은 관련 테스트와 영향받는 기존 테스트의 실제 통과 후 작성한다. 환경 설정은 최소 실행, 문서 변경은 내용·링크·형식 검사로 검증한다.
- TDD의 실패 확인은 실행 증거로 남긴다. 작업 브랜치에 실패 테스트를 중간 저장할 필요가 있으면 본문에 실패 이유와 미완료 상태를 적고, 통합 브랜치 병합 전에는 해당 검증을 통과시킨다.
- 테스트 skip, 임의 기대값 변경, 고의 장애·변이의 원복 누락으로 통과 상태를 만들지 않는다.

## 메시지 형식

Conventional Commits 형식을 사용한다. type·scope는 영문, 제목과 본문 설명은 한국어로 작성한다.

```text
<type>(<scope>): <변경한 동작을 설명하는 제목>

<필요한 경우 문제·변경 이유·영향>
검증: <실제 명령 / 종료 코드 / 테스트 수 또는 문서 검사>
미검증: <남은 범위가 있으면 명시>
```

- scope는 필요할 때 `resource`, `reservation`, `security`, `ratelimit`, `db`, `build`, `knowledge` 등 실제 변경 범위로 적는다. 전역 변경은 생략할 수 있다.
- 제목은 가급적 72자 이내로 구체적인 동작을 설명한다. `수정`, `작업 완료`처럼 내용을 알 수 없는 제목을 피한다.
- 동작·환경·계약 변경에는 이유와 실제 검증 결과를 본문에 남긴다. 상세 기록은 `docs/test-evidence.md` 등으로 연결한다. 실행하지 않은 결과를 통과로 적지 않는다.
- 기존 API 계약을 깨는 변경은 type 뒤 scope가 있으면 닫는 괄호 뒤에 `!`를 붙이고, 본문에 `BREAKING CHANGE:`와 영향·대응을 적는다. 계획서·계약·테스트 변경도 함께 수행한다.
- 이슈가 실제 존재할 때만 번호를 연결한다. 자동 커밋 도구·훅이 이미 설치됐다고 가정하지 않는다.

| type | 용도 | 제목 예시 |
|---|---|---|
| feat | 기능 추가 | `feat(resource): 최초 수량이 0인 예약 대상을 생성한다` |
| fix | 잘못된 동작 수정 | `fix(reservation): 중복 취소 시 수량을 한 번만 복구한다` |
| refactor | 외부 동작을 유지하는 구조 정리 | `refactor(reservation): 생성 트랜잭션을 별도 Writer로 분리한다` |
| test | 테스트 추가·개선 | `test(reservation): 마지막 수량의 동일 키 경쟁을 검증한다` |
| docs | 문서 변경 | `docs(knowledge): 커밋과 Git Flow 규칙을 추가한다` |
| build | 빌드·의존성·태스크 변경 | `build: 통합 테스트용 Gradle 태스크를 추가한다` |
| ci | CI 구성 변경 | `ci: 계약 테스트 실행 단계를 추가한다` |
| perf | 측정으로 확인한 성능 개선 | `perf(reservation): 예약 조회 쿼리의 지연을 줄인다` |
| chore | 기타 유지보수 | `chore: 로컬 생성 파일의 Git 제외 규칙을 추가한다` |
| revert | 기존 커밋 되돌리기 | `revert: 요청 제한 설정 변경을 되돌린다` |

예시는 메시지 형식이며 기능 구현·검증 완료 기록이 아니다. 되돌림에는 대상 커밋과 이유를 본문에 적는다.

## 스테이징과 확인

1. `git rev-parse --show-toplevel`, `git branch --show-current`, `git status --short`로 저장소·브랜치·기존 변경을 확인한다.
2. 작업한 파일과 변경 조각을 검토한다. 사용자나 다른 작업의 변경은 임의로 포함·삭제하지 않는다.
3. 파일 경로를 명시한 `git add -- <경로>` 또는 `git add -p`로 필요한 변경만 스테이징한다. 추적되지 않은 파일의 내용도 확인한다. 전체 디렉터리를 무조건 추가하지 않는다.
4. `git diff --cached --check`, `git diff --cached`, `git diff --cached --stat`으로 공백 오류·정확한 내용·범위를 확인한다.
5. 변경에 필요한 검증 결과를 확인하고 커밋한다. `git status --short`와 `git show --stat --oneline HEAD`로 결과와 남은 변경을 확인한다.

- `.env`, 비밀번호·토큰, DB 데이터, 로그, 빌드 산출물, 로컬 캐시와 개인 IDE 설정은 커밋하지 않는다. 공유가 필요한 IDE 설정은 목적과 내용을 확인해 선별한다.
- Flyway 마이그레이션과 Wrapper 등 재현에 필요한 파일을 빌드 산출물이라는 이유로 제외하지 않는다. 기존 적용 마이그레이션 수정 대신 새 마이그레이션으로 변경한다.
- 공유 이력은 amend·rebase·강제 push로 임의 재작성하지 않는다. 일반 수정·revert 커밋으로 정정한다.
- 커밋 작성과 외부 push·공개·workflow 실행은 별개다. 외부 작업은 기존 프로젝트 지침에 따른 별도 사용자 지시 범위에서 수행한다.
