# Feature Specification: Redis 원자적 예약 요청 제한

**Feature Branch**: `feature/redis-rate-limit`

**Created**: 2026-10-22

**Status**: Draft

**Input**: 계획서 7절 8단계 전체 범위에 대해 기본 정책을 유지하는 명세를 작성한다. 인증된 예약 생성·취소의 사용자별 고정 창 제한, 원자적 집계, 만료, 장애 거부, 업무 데이터 보호와 기존 HTTP·경쟁 검증의 회귀를 포함한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 사용자별 예약 쓰기 횟수 제한 (Priority: P1)

인증 사용자는 최초 쓰기부터 60초 동안 생성·취소를 합산해 20회까지 요청할 수 있고, 초과하면 다시 시도할 대기 시간을 받는다. 다른 사용자의 사용량에는 영향을 주지 않는다.

**Why this priority**: 한 사용자의 반복 쓰기가 예약 처리를 독점하지 않도록 확정된 제한을 적용한다.

**Independent Test**: 충분한 수량과 소유 예약을 준비해 생성·취소 혼합 요청의 허용 수, 초과 응답, 사용자 격리와 만료 후 재허용을 검사한다.

**Acceptance Scenarios**:

1. **Given** 제한 키가 없는 사용자, **When** 같은 창에서 생성·취소를 합산해 21회 요청, **Then** 첫 20회는 후속 처리로 진행하고 21번째는 429 `RATE_LIMITED`와 양의 정수 `Retry-After`를 받는다. 허용은 업무 성공 보장과 구분한다.
2. **Given** 사용자 A가 한도를 소진, **When** 사용자 B가 첫 쓰기를 요청, **Then** B의 요청은 독립적으로 허용된다. 인증된 ADMIN의 예약 쓰기에도 같은 정책을 적용한다.
3. **Given** 첫 요청으로 창이 시작됨, **When** 후속 허용·거부 요청을 보내고 창 만료 뒤 다시 요청, **Then** 후속 요청이 만료를 연장하지 않으며 만료 뒤 첫 요청은 새 창의 1회로 허용된다.
4. **Given** 같은 사용자의 빈 창과 충분한 수량, **When** 창이 만료되기 전에 21건 이상을 동시에 요청, **Then** 정확히 20건만 후속 처리로 진행하고 나머지는 429이며 집계 유실·영구 키가 없다.

---

### User Story 2 - 인증·제한·검증 순서와 재요청 (Priority: P1)

사용자는 입력 오류와 멱등 재전송도 횟수에 포함된다는 일관된 규칙을 적용받는다. 인증되지 않은 요청과 상한 초과 본문은 제한 저장소에 접근하지 않는다.

**Why this priority**: 검증·재전송 경로를 이용한 제한 우회를 막고 기존 인증·입력 계약을 보존한다.

**Independent Test**: 실제 인증 헤더와 HTTP 진입 경로로 오류·재요청·취소를 보내고 응답, 카운트, 후속 처리 진입과 업무 데이터를 함께 검사한다.

**Acceptance Scenarios**:

1. **Given** 8KiB 이하의 인증된 쓰기, **When** 잘못된 JSON·UUID·생성 키, 미정의/중복 필드, 미지원 생성 Content-Type 또는 비어 있지 않은 취소 본문을 전송, **Then** 한도 이내에는 기존 400/415 계약으로 거부되지만 횟수는 각각 1회 증가한다. 한도 소진 뒤에는 입력 검증보다 429가 앞선다.
2. **Given** 성공한 생성 키 또는 이미 취소한 예약, **When** 동일 생성·중복 취소를 재요청, **Then** 각 요청을 집계하며 한도 이내에는 기존 최초 생성 응답 재현·중복 취소 계약을 지키고, 한도 초과에는 429로 차단한다.
3. **Given** 8KiB 이하의 미인증 또는 잘못된 비밀번호 요청, **When** 예약 쓰기 요청, **Then** 401 `UNAUTHENTICATED`와 `WWW-Authenticate`를 반환하고 Redis 호출·키 생성·카운트 변경이 없다.
4. **Given** 일반 또는 chunked/길이 헤더 없는 본문이 8192바이트를 초과, **When** 인증 여부와 무관하게 요청, **Then** 413 `PAYLOAD_TOO_LARGE`가 먼저 반환되고 제한 저장소에 접근하지 않는다. 8192바이트 이하는 후속 순서를 따른다.
5. **Given** 기존 MVC에서 처리하는 인코딩 취소 경로, **When** 인증된 요청을 전송, **Then** 일반 취소와 동일하게 집계하고 이후 본문·UUID 검증 및 취소 계약을 적용해 경로 표현으로 우회할 수 없다.

### User Story 3 - 제한 저장소 장애에도 데이터 보호와 독립 기능 유지 (Priority: P1)

사용자는 제한을 판단할 수 없는 동안 예약 쓰기의 명확한 실패를 받는다. 정상 DB를 사용하는 조회와 대상 생성은 계속 사용할 수 있다.

**Why this priority**: 장애를 허용으로 오인해 무제한 쓰기가 발생하거나 애플리케이션 전체가 중단되는 것을 막는다.

**Independent Test**: 실제 제한 저장소의 중단·연결 단절·명령 지연을 재현해 생성·취소·기존 키 재요청과 독립 API 결과 및 데이터 전후를 비교한다.

**Acceptance Scenarios**:

1. **Given** Redis 오류·연결 끊김·명령 timeout, **When** 인증된 생성·취소 또는 성공 키 재요청, **Then** 503 `DEPENDENCY_UNAVAILABLE`이며 Controller·업무 서비스·DB 트랜잭션으로 진행하지 않고 예약·수량·성공 키 기록이 바뀌지 않는다.
2. **Given** Redis가 중단되고 DB는 정상, **When** 인증된 대상 조회·소유 예약 조회·ADMIN 대상 생성, **Then** 각각 기존 200·200·201 계약을 지키며 Redis에 접근하지 않는다.
3. **Given** 제한을 통과한 요청의 DB 처리가 실패, **When** 실패 후 사용량을 확인, **Then** 업무 변경은 롤백되고 제한 카운트는 유지된다. 장애 해제 후 같은 생성 키 재시도는 다시 집계하고 한도 이내라면 성공할 수 있다.
4. **Given** 초과 또는 Redis 장애로 거부된 요청, **When** 오류 응답을 검사, **Then** `application/problem+json`과 기존 ProblemDetail 표준 필드·code를 지키며 SQL·스택·비밀번호를 노출하지 않는다.

---

### User Story 4 - 기존 예약 정합성의 회귀를 확인 (Priority: P2)

개발자는 요청 제한 도입 뒤에도 기존 인증·소유권·멱등성·롤백·경쟁 결과가 유지된다는 재현 가능한 증거를 남긴다.

**Why this priority**: 제한 도입으로 기존 시험이 의도치 않은 429/503에 가려지거나 전체 HTTP 경로를 잃는 것을 방지한다.

**Independent Test**: 격리된 실제 의존성으로 기존 HTTP 시험과 경쟁 11종 각 10회 및 종료 보호 fixture를 실행하고 기존 기대 응답·관측 경로·최종 상태를 대조한다.

**Acceptance Scenarios**:

1. **Given** 현재 HTTP 시험이 `postgresOnly()`를 사용, **When** 제한을 연결한 환경으로 전환, **Then** 예약 쓰기를 포함하는 시험은 격리된 실제 Redis를 연결해 원래 검사하려던 응답과 DB 상태까지 도달한다. 순수 DB 시험까지 Redis 의존성을 강제하지 않는다.
2. **Given** 기존 경쟁 11종 각 10회, **When** 경쟁 전용 10,000회/60초와 매 회차 전 테스트 전용 사용자 제한 키 초기화를 적용, **Then** 기존 HTTP 인증·필터·Controller 경로 및 경쟁 결과와 경로 관측을 유지하고 예상 밖 429/503은 실패다.
3. **Given** 기본 정책의 전용 HTTP 사례, **When** 실제 필터를 통과해 허용·초과·장애를 검사, **Then** 내부 서비스 호출만의 시험 및 한도를 높인 경쟁 시험과 별개로 제한 동작을 입증한다.

### Edge Cases

- 초과 요청도 카운트를 증가시키지만 TTL을 연장하지 않는다. 최초 동시 요청에서도 만료 설정이 누락되지 않아야 한다.
- 남은 TTL이 1000ms 경계 또는 1초 미만이어도 대기 시간은 올림하며 최소 1초다. 판정 시 관측한 TTL과 이후 관측 사이의 시간 경과를 구분한다.
- 정상 한도 내 입력·소유권·품절·충돌 거부도 이미 집계한 횟수를 되돌리지 않는다. 한도 소진 시 타인/없는 예약 취소도 소유권 조회 전에 429가 될 수 있다.
- 취소 뒤 생성 재요청도 제한 통과 뒤에만 최초 CONFIRMED 응답을 재현하며 GET은 현재 CANCELLED를 유지한다.
- Redis 명령이 적용된 후 응답이 유실되면 사용량 반영 여부가 불확실할 수 있다. 이 경우에도 쓰기는 503으로 거부하고 DB를 변경하지 않는다. Redis·DB의 원자 커밋이나 실패 시 카운트 정확 복구를 약속하지 않는다.
- 기존 인코딩 경로·본문 크기·미인증 우선순위 회귀를 유지한다. 필터 중복 적용으로 단일 HTTP 요청을 두 번 집계하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 인증 Principal의 UUID별로 `POST /api/reservations`와 `POST /api/reservations/{id}/cancel` 진입 횟수를 합산해 최초 요청부터 20회/60초 고정 창을 적용해야 한다. 요청 body·임의 `X-User-Id`·생성 키·대상별로 사용량을 분리하지 않는다. (US1)
- **FR-002**: 창의 1~20번째는 후속 처리를 허용하고 21번째 이후는 429 `RATE_LIMITED`로 거부해야 한다. 모든 대상 진입 요청을 한 번씩 집계하며 허용·거부 요청 모두 창을 연장하지 않는다. (US1)
- **FR-003**: 최초 동시 요청에도 카운트 증가·최초 만료 설정·잔여 만료 조회가 하나의 원자적 판단이어야 한다. 창의 경계는 Redis TTL이며 앱 시계의 분·정각 경계로 바꾸지 않는다. (US1)
- **FR-004**: 429의 `Retry-After`는 판정 시 잔여 PTTL로 `max(1, ceil(PTTL / 1000))`을 계산한 정수 초여야 한다. (US1, Edge Cases)
- **FR-005**: 실제 바이트 기준 8KiB 본문 제한 → 인증 → 요청 제한 → 입력 검증 → 서비스 순서를 보장해야 한다. 기존 취소 검증도 제한 뒤에 실행하고 미인증·본문 초과 요청은 Redis에 접근하지 않아야 한다. (US2)
- **FR-006**: 멱등 생성 재전송·중복 취소·잘못된 입력을 집계해야 한다. 생성/취소와 무관한 GET 및 대상 생성·조회에는 이 제한을 적용하지 않아야 한다. (US2, US3)
- **FR-007**: Redis 의존성 오류·연결 단절·명령 timeout에는 503 `DEPENDENCY_UNAVAILABLE`로 거부해야 한다. 허용 대체나 무제한 재시도로 진행하지 않으며, 분류하지 못한 내부 결함을 일괄 503으로 숨기지 않는다. (US3)
- **FR-008**: 제한 초과·Redis 장애 시 Controller·업무 서비스에 도달하거나 DB 트랜잭션을 시작하지 않아야 하며 예약 행·상태·시각·성공 키 및 대상 수량은 변경되지 않아야 한다. (US3)
- **FR-009**: 제한 통과 뒤에만 DB 트랜잭션을 시작하고 DB 실패나 후속 거부로 이미 소비한 카운트를 되돌리지 않아야 한다. 성공 예약의 생성 키 보존과 제한 키 만료는 서로 독립적이어야 한다. (US2, US3)
- **FR-010**: 제한 필터의 429/503도 기존 오류 형식·민감정보 비노출을 따라야 한다. 401 인증 헤더, 정상 생성의 Location·Replay, 기존 소유권·취소·불변식 계약을 유지해야 한다. (US2, US3, US4)
- **FR-011**: 실제 Redis에서 기본 20/60초 경계·사용자 격리·동시 집계·TTL 존재와 비연장·만료 후 재허용을 검증해야 한다. 만료 시험만 IT 한정 3회·짧은 창을 허용하고 정확한 값·이유를 기록하며 유한한 상한 안에서 상태를 기다려야 한다. (US1)
- **FR-012**: 실제 Authorization·보안 필터를 통과하는 HTTP로 생성/취소 합산, 잘못된 입력·재요청 포함, 미인증 Redis 미접근, 413 우선, 인코딩 취소 경로, Redis 장애·지연 및 DB 실패 카운트 유지·업무 무변경을 검증해야 한다. mock만으로 의존성 통합·장애 검증을 대체하지 않는다. (US2, US3)
- **FR-013**: 현재 `postgresOnly()` HTTP 시험 중 영향받는 시험은 실제 Redis 연결·테스트 전용 키 격리를 갖추고 원래 기대값을 유지해야 한다. 경쟁은 10,000회/60초·매 반복 회차 전 해당 키 초기화로 전환하며 기존 11종 각10회·경로 관측·종료/전송 실패 보호를 회귀 검증해야 한다. 기본 제한 시험의 한도를 올리거나 제한을 비활성화해 통과시키지 않는다. (US4)
- **FR-014**: 모든 병행 작업의 결과·예외·상한 시간·종료를 확인한 뒤 단일 SELECT로 수량 보존식을 검사해야 한다. 설정 전환이 종료 실패 후 다음 회차 reset·준비·요청 제출 차단을 훼손하지 않아야 한다. (US4)
- **FR-015**: 구현 단계에서 관련 시험과 일반 `verify`를 실행하고 명령·종료 코드·실행 수·실패/skip·의존성 버전·제한값·장애 조건·미검증 범위를 기존 docs 기록 체계에 남겨야 한다. 테스트 0건을 통과로 보지 않으며 문서 작성과 실제 실행 검증을 구분한다. (US4)

### 지정 기술 제약과 범위

다음은 사용자와 기준 계획서가 이미 지정한 제약이며 새로운 구현 설계 선택이 아니다. 클래스 배치·설정 구조·장애 주입 수단 등 세부 설계는 후속 plan에서 정한다.

- Redis 키는 `reservation:write-limit:{userId}`이고 Lua에서 INCR·최초 PEXPIRE·PTTL을 원자 처리한다. 초기 Redis 명령 timeout은 200ms다. HTTP 전체 응답 시간이 정확히 200ms 이하라는 보장은 아니다.
- 계획서 제공 인터페이스 `RedisRateLimiter.check(UUID userId): RateLimitDecision`과 `allowed`(boolean)·`retryAfterSeconds`(long)를 유지한다. RateLimitFilter·RedisRateLimiter·RateLimitDecision·`rate-limit.lua` 및 RedisRateLimitIT·RateLimitApiIT·RedisFailureIT는 8단계 예정 산출물이며 현재 존재/통과한 것으로 표현하지 않는다.
- PostgreSQL은 예약·수량·성공 키의 유일 원본이며 Redis 수량 저장·분산 락을 도입하지 않는다. 기존 스키마·READ COMMITTED·resource → reservation 잠금 순서를 바꾸지 않는다.
- 범위는 localhost CLI/API 및 8단계다. 완료한 7단계의 재구현, 9단계 전체 계약 검증기, 속성/변이/부하 확장, 외부 CI·배포는 포함하지 않는다. 이번 산출물은 명세·품질 체크리스트·feature 선택 정보에 한정한다.

### Key Entities *(include if feature involves data)*

- **사용자별 쓰기 창**: 인증 UUID에 대응하는 합산 횟수와 최초 요청부터의 잔여 수명. 만료 후 다음 요청이 새 창을 시작한다.
- **제한 판단**: 해당 요청의 허용 여부와 거부 시 재시도 대기 시간. 예약 성공 여부와 독립적이다.
- **보호할 업무 상태**: 대상 수량, 예약·소유자·상태·시각·성공 생성 키. 제한 판단의 저장소가 소유하거나 복제하지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 기본 창에서 사용자별 첫 20회만 후속 처리로 진행하며 21번째부터 거부된다. 생성·취소 혼합과 21건 이상 동시 요청에서도 같은 총수를 만족한다.
- **SC-002**: 다른 사용자에게 사용량이 전파되는 사례는 0건이며, 후속 허용·거부로 창이 연장되는 사례는 0건이다. 만료 뒤 첫 요청은 허용된다.
- **SC-003**: 상한 이하 인증된 대상 요청의 재전송·잘못된 입력은 각 1회 집계되고 미인증·상한 초과·비대상 요청의 집계는 0회다. 거부 대기 시간은 모든 경계 사례에서 양의 정수로 정확히 계산된다.
- **SC-004**: 제한 초과·제한 의존성 장애로 거부된 쓰기의 업무 데이터 변경은 0건이다. 정상 업무 저장소를 사용하는 조회 2종과 관리자 대상 생성은 장애 중에도 기존 성공 결과를 유지한다.
- **SC-005**: 후속 업무 실패로 사용량이 복구되는 사례는 0건이며, 기존 멱등 응답·취소 상태·소유권 및 수량 보존 계약 위반은 0건이다.
- **SC-006**: 기존 경쟁 11종 각10회와 종료 보호 회귀에서 예상 밖 제한/장애 응답·미수집 결과·종료 미확인·수량 불일치는 0건이다. 전용 제한 HTTP 시험과 기존 관련 회귀는 발견 0건·실패·skip 없이 완료되어야 한다.

## Assumptions

- 기준은 [계획서](<../../한정 수량 예약 백엔드 로컬 개발 계획.md>) 2~5절·7절 8단계, [요청 제한 규칙](../../knowledge/rules/rate-limit.md), [API·보안 규칙](../../knowledge/rules/api-and-security.md) 및 ratelimit/reservation/security/resource 도메인 문서다. 새 업무 정책이나 미확정 정책의 기본값을 추가하지 않았다.
- 기존 인증·본문 제한·예약/대상 API·DB 제약·경쟁 시험을 재사용한다. [008 명세](../008-reservation-concurrency/spec.md)의 완료 범위를 다시 구현하지 않고 제한 연결 영향만 회귀 검증한다.
- 2026-10-22 코드 대조: ratelimit 제품 패키지·Lua·업무 제한 시험은 아직 없다. `application-local.yaml`에는 Redis timeout 200ms가 이미 있다. SecurityConfig에는 인증 뒤 취소 본문·UUID 검증이 있어 순서 연결의 영향 대상이다.
- ContainerTestSupport는 실제 PostgreSQL+Redis 실행 및 `postgresOnly()`를 지원하지만 ResourceApiIT·SecurityIT·예약 HTTP IT·ReservationConcurrencyIT는 현재 후자를 쓴다. 기존 경쟁은 실제 HTTP 경로를 사용하고 있으므로 이를 내부 서비스 시험으로 낮추지 않는다.
- 검증은 테스트 소유 동적 포트·격리 DB/Redis 키를 사용하며 로컬 개발 데이터나 무관한 키를 초기화하지 않는다. 실제 장애 시험은 기본 timeout을 유지한다. 짧은 만료 창과 높은 경쟁 한도는 해당 검증에만 적용한다.
- 이 명세는 구현·기능 시험 실행 증거가 아니다. 현재 단계에서는 코드·SQL·OpenAPI·기준 정책을 변경하지 않으며 다음 단계는 명세 검토 후 plan이다.
