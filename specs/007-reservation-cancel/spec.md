# 기능 명세: 소유자의 예약 조회·취소

**작업 브랜치**: `feature/reservation-cancel` (명세 작성: `docs/reservation-cancel-spec`)

**작성일**: 2026-10-20

**상태**: 명세 초안·품질 검토 완료. 구현·실행 검증 전이다.

**입력**: 로컬 개발 계획 7절의 6단계(소유자의 예약 조회·취소). 소유자만 자신의 예약을 단건 조회·취소하고, 취소와 수량 복구를 함께 반영하며 중복 취소에도 수량을 한 번만 복구한다.

## 사용자 시나리오와 검증 *(필수)*

### 사용자 이야기 1 - 내 예약의 현재 상태 확인하기 (우선순위: P1)

인증된 사용자는 자신의 예약 식별자로 현재 상태(확정 또는 취소)와 생성·취소 시각을 확인한다. 다른 사람의 예약이나 없는 예약은 존재 여부를 알 수 없게 같은 방식으로 거부된다.

**우선순위 이유**: 취소 결과와 재요청 결과를 구분해 확인하는 유일한 수단이며, 소유권 보호의 기본이다.

**독립 검증**: 사용자 A의 예약을 준비하고 A·B·관리자·미인증 요청, 없는 식별자 요청의 결과를 비교한다.

**인수 시나리오**:

1. **조건** 사용자 A의 확정 예약이 있을 때, **행동** A가 조회하면, **결과** 예약 식별자·대상·확정 상태·생성 시각을 받고 취소 시각은 비어 있다.
2. **조건** 사용자 A의 예약이 있을 때, **행동** 사용자 B 또는 관리자가 조회하면, **결과** 예약 없음으로 거부하며 없는 식별자를 조회한 결과와 구분되지 않는다.
3. **조건** 존재하지 않는 식별자일 때, **행동** 인증 사용자가 조회하면, **결과** 예약 없음으로 거부한다.
4. **조건** 자격 증명이 없거나 잘못됐을 때, **행동** 조회하면, **결과** 인증 실패로 거부한다.
5. **조건** 식별자 형식이 잘못됐을 때, **행동** 인증 사용자가 조회하면, **결과** 입력 오류로 거부한다.

---

### 사용자 이야기 2 - 내 예약 취소하고 수량 돌려주기 (우선순위: P1)

소유자는 확정된 자신의 예약을 취소하고, 수량 한 개가 다른 사용자에게 다시 예약 가능해진다.

**우선순위 이유**: 취소와 수량 복구가 함께 반영되지 않으면 수량 보존식이 깨진다.

**독립 검증**: 최초 수량 1인 대상에 예약 후 취소하고 응답 상태·취소 시각, 남은 수량, 확정 예약 수를 대조한다.

**인수 시나리오**:

1. **조건** 최초 수량 1인 대상에 A의 확정 예약이 있어 남은 수량이 0일 때, **행동** A가 취소하면, **결과** 취소 상태와 비어 있지 않은 UTC 취소 시각을 받고 남은 수량은 1, 확정 예약은 0개다.
2. **조건** 취소를 마친 예약이 있을 때, **행동** A가 조회하면, **결과** 취소 응답과 같은 취소 상태·취소 시각을 받는다.
3. **조건** A의 예약이 있을 때, **행동** B 또는 관리자가 취소하면, **결과** 예약 없음으로 거부하고 상태·수량을 변경하지 않는다. 없는 식별자 취소도 같은 결과다.
4. **조건** 취소 요청에 비어 있지 않은 본문이 있거나 자격 증명이 없을 때, **행동** 취소하면, **결과** 각각 입력 오류·인증 실패로 거부하고 데이터는 변경하지 않는다. 8,192바이트 초과 본문은 기존 상한 규칙으로 인증보다 먼저 거부한다.

---

### 사용자 이야기 3 - 취소를 다시 보내도 안전하기 (우선순위: P1)

사용자는 취소 응답을 확신할 수 없을 때 다시 취소 요청을 보내도 수량이 추가로 늘거나 취소 시각이 바뀌지 않아야 한다.

**우선순위 이유**: 중복 취소로 수량이 최초 수량을 넘거나 보존식이 깨지는 것을 막는다.

**독립 검증**: 취소된 예약에 취소를 다시 보내고 응답·수량·취소 시각을 첫 취소 결과와 비교한다.

**인수 시나리오**:

1. **조건** 이미 취소된 예약이 있을 때, **행동** 소유자가 다시 취소하면, **결과** 성공으로 응답하며 상태는 취소, 취소 시각은 처음 값과 같고 남은 수량은 1을 유지한다.
2. **조건** 취소 상태가 기록된 뒤 수량 복구를 의도적으로 실패시킬 때, **행동** 취소하면, **결과** 성공을 반환하지 않고 예약은 확정 상태·취소 시각 없음, 남은 수량은 0으로 그대로 남는다.
3. **조건** 수량 복구 시 남은 수량이 이미 최초 수량과 같아 복구할 수 없는 불일치가 있을 때, **행동** 취소하면, **결과** 내부 불변식 위반으로 전체를 되돌리고 성공·품절·일시적 이용 불가로 위장하지 않는다.

---

### 사용자 이야기 4 - 취소 이후의 생성 요청 구분하기 (우선순위: P2)

사용자는 취소 후 원래 생성 키로 재전송하면 최초 생성 결과를 받고, 새 키로는 복구된 수량을 예약할 수 있다.

**우선순위 이유**: 생성 재요청과 현재 상태를 혼동하거나 취소 예약이 재활성화되는 것을 막는다.

**독립 검증**: 실제 취소 기능으로 만든 취소 예약에 원래 키·새 키 생성 요청을 각각 보내고 조회 결과·수량을 대조한다.

**인수 시나리오**:

1. **조건** A가 예약 후 취소했을 때, **행동** 같은 키·대상으로 생성 재요청하면, **결과** 최초 생성 성공 결과(확정 상태 포함)를 재현하고 재현임을 표시한다. 이후 조회는 취소 상태이며 수량·예약 수는 변하지 않는다.
2. **조건** 수량 1인 대상이 품절이라 다른 키의 생성이 거부됐을 때, **행동** 소유자 취소로 수량이 복구된 뒤 그 키로 다시 생성하면, **결과** 새 예약이 성공하고 남은 수량은 0이다.

### 경계 사례

- 취소된 예약은 다시 확정 상태로 돌아가지 않으며 예약 기록은 삭제하지 않는다.
- 관리자 권한은 다른 사용자의 예약 조회·취소 권한을 주지 않는다.
- 취소 시 대상 갱신 잠금을 예약 갱신보다 먼저 얻는 순서를 지킨다. 동시 취소·생성과 취소 경쟁의 반복 검증은 7단계다.
- 의존성 장애·잠금 대기 시간 초과는 일시적 이용 불가로 처리하고 부분 반영을 남기지 않는다.
- 요청 제한(취소 횟수 포함)은 8단계에서 연동하며 이번 단계의 완료 조건이 아니다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 인증된 사용자는 자신의 예약을 식별자로 단건 조회해 식별자·대상·현재 상태·생성 시각·취소 시각을 받아야 한다. 확정이면 취소 시각은 비고, 취소면 값이 있어야 한다. 이야기 1.1·2.2로 검증한다.
- **FR-002**: 타인의 예약과 없는 예약에 대한 조회·취소는 관리자를 포함해 동일한 예약 없음으로 거부하고 상태를 변경하지 않아야 한다. 이야기 1.2~1.3·2.3으로 검증한다.
- **FR-003**: 미인증·잘못된 자격 증명은 인증 실패, 잘못된 식별자 형식과 비어 있지 않은 취소 본문은 입력 오류로 기존 공통 오류 계약에 따라 거부해야 한다. 이야기 1.4~1.5·2.4로 검증한다.
- **FR-004**: 확정 예약의 취소는 상태를 취소로 바꾸고 UTC 취소 시각을 기록하며 수량 한 개 복구와 함께 모두 반영되거나 모두 반영되지 않아야 한다. 이야기 2.1·3.2로 검증한다.
- **FR-005**: 이미 취소된 예약의 취소는 성공으로 기존 상태·취소 시각을 반환하고 수량을 추가 복구하지 않아야 한다. 예약당 복구 수량은 최대 1개다. 이야기 3.1로 검증한다.
- **FR-006**: 모든 처리 후 대상별 남은 수량은 0 이상 최초 수량 이하이고 남은 수량과 확정 예약 수의 합은 최초 수량과 같아야 한다. 복구가 이를 위반하면 전체를 되돌리고 내부 오류로 드러내야 한다. 이야기 2·3의 상태 대조와 3.3으로 검증한다.
- **FR-007**: 취소 후 원래 키의 생성 재요청은 최초 확정 생성 결과를 재현하고 예약을 재활성화하지 않아야 하며, 복구된 수량은 다른 키로 새로 예약할 수 있어야 한다. 이야기 4로 검증한다.
- **FR-008**: 취소는 대상 → 예약 순서로 갱신 잠금을 얻고 확정·소유자 조건이 맞을 때만 상태를 바꿔야 한다. 장애·대기 시간 초과는 일시적 이용 불가, 분류하지 못한 결함은 내부 오류로 처리하며 민감 정보를 노출하지 않아야 한다. 계획서 5.3절과 대조하고 경쟁 반복 검증은 7단계로 미룬다.

### 핵심 개체

- **예약**: 식별자, 대상, 소유 사용자, 생성 키, 상태(확정/취소), 생성 시각, 취소 시각. 상태는 확정 → 취소로만 바뀌며 취소 시각은 한 번 기록되면 바뀌지 않는다.
- **예약 대상**: 최초 수량과 남은 수량. 취소 성공 시 남은 수량이 한 개 늘어난다.
- **예약 현재 상태 결과**: 조회·취소 응답. 최초 생성 결과와 별개로 현재 상태를 나타낸다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 최초 수량 1에서 예약→취소 후 취소 상태·취소 시각 존재·남은 수량 1이며, 취소를 두 번 더 보내도 남은 수량은 1, 취소 시각 변경 0건이다.
- **SC-002**: 타인(관리자 포함)·없는 식별자에 대한 조회·취소 사례 100%가 같은 예약 없음 결과이고, 그로 인한 상태·수량 변경은 0건이다.
- **SC-003**: 수량 복구 실패 사례에서 예약 상태·취소 시각·남은 수량이 요청 전과 100% 같다.
- **SC-004**: 취소 후 원래 키 재요청은 최초 생성 정보와 불일치 0건, 재활성화 0건이며, 품절이었던 다른 키는 복구 후 1회 만에 성공한다.
- **SC-005**: 구현 후 조회·취소를 포함해 여기까지의 기능을 CLI로 한 차례 모두 실행한 기록이 남는다.

## 전제와 의존성

- 기준은 [로컬 개발 계획](<../../한정 수량 예약 백엔드 로컬 개발 계획.md>) 2~5절(특히 5.3 취소 흐름)·7절 6단계, [예약 도메인](../../knowledge/domain/reservation.md), [인증 도메인](../../knowledge/domain/security.md), [트랜잭션 규칙](../../knowledge/rules/domain-and-transactions.md), [API·보안 규칙](../../knowledge/rules/api-and-security.md), [기존 외부 계약](../../docs/openapi.yaml)이다. 기존 상태 코드·오류 코드·필드 계약을 바꾸지 않는다.
- 5단계 예약 생성·재현, 4단계 인증·본문 상한·공통 오류, 3단계 취소 판단 규칙을 재사용한다. 3단계 취소 판단 규칙은 이번 단계에서 실제 요청 경로의 이미 취소됨 분기에 연동한다.
- 범위는 소유자 단건 조회·취소다. 동시 경쟁 반복 검증은 7단계, 요청 제한은 8단계, 계약·속성·변이·부하는 후속이다. 목록 조회·취소 철회·예약 삭제는 범위 밖이다.
- 제공 인터페이스·테스트 이름(`ReservationCancelIT`·`ReservationOwnershipIT`)·실행 명령은 후속 `$speckit-plan`에서 계획서 7절 6단계에 따라 구체화한다. 명세 품질 검토를 구현·테스트 통과로 취급하지 않는다.
