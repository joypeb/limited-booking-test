## Clarifications

### Session 2026-10-23

업무 정책 질문은 없다. 아래는 검증 설계의 모호점을 계획서 근거로 해소한 기록이다(Orchestrator, 사용자 전체 진행 지시 범위).

- Q: 기존 변이 결과 게이트(도구 프로브 대상)를 유지하고 새 실행을 추가하는가, 업무 규칙으로 교체하는가? → A: 기존 변이 실행·게이트를 업무 세 규칙 대상으로 교체하고 탐지율 80% 판정을 추가한다. 근거: 계획서 6.2절은 변이 실행 명령 하나만 계약하고 10단계는 대상을 세 규칙으로 정한다. 실행 명령 이름은 유지해 문서 계약 변경을 최소화한다.
- Q: 속성 시도의 사용자 집합에 ADMIN을 포함하는가? → A: USER_A·USER_B 두 명. 근거: 10단계 “고정된 작은 집합”, 타인 예약 404는 관리자 포함 동일 규칙이며 관리자 경로는 계약·보안 IT가 이미 검증한다.
- Q: US2의 고의 결함은 무엇으로 만드는가? → A: US4의 네 고의 변경 중 하나(생성 재요청의 대상 비교 제거)를 속성 검증에도 적용해 실패 seed·축소 순서를 얻는다. 근거: 계획서는 Property 실패 재현과 고의 변경을 모두 요구하며, 같은 고의 변경을 쓰면 별도 결함 주입 수단이 필요 없다. 취소 확정 상태 조건 제거는 취소 판단이 이미 취소된 예약을 먼저 반환하므로 순차 실행에서 관측되지 않고 경쟁 테스트의 책임이다(계획서 10단계 “동시 실행 교차는 Property로 증명하지 않음”). 네 변경 모두에서 속성 검증의 실패 여부를 함께 기록하되, 순차 관측 불가 변경의 미탐지는 결함으로 세지 않고 이유를 남긴다.
- Q: (Implement 중 추가) PIT가 핵심 규칙에 변이를 만들지 못하면? → A: 도구 필터·연산자 한계를 조사해 필요한 필터만 끄고(레코드 생성자), 연산자가 없는 enum 매핑 교체는 US4 수동 고의 변경 E로 보완한다. 근거: 10단계 “PIT의 높은 점수만으로 판단하지 않는다”.
- Q: 속성 검증 실패 시 “축소 최소 순서 5건 이하”는 필수 기준인가? → A: 대상 비교 제거의 이론적 최소 순서(같은 키로 대상1 생성→대상2 생성)가 2건이므로 5건 이하를 성공 기준으로 둔다. 도구 축소가 기준에 못 미치면 실제 결과와 이유를 기록하고 Advisor 분석을 요청한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 임의 명령 순서에서도 수량과 예약 상태가 독립 모델과 일치함을 확인하는 개발자 (Priority: P1)

개발자는 손으로 고른 사례뿐 아니라 생성·재요청·다른 대상 키 재사용·조회·본인 취소·중복 취소·타인 취소·없는 예약 참조가 섞인 임의 순서에서도 시스템의 결과가 규칙만으로 계산한 기대 결과와 같은지 확인한다.

**Why this priority**: 개별 예제 테스트는 작성자가 떠올린 순서만 검사한다. 순서를 생성하면 재요청 후 취소, 취소 후 같은 키 재요청, 품절 뒤 같은 키 재시도처럼 놓치기 쉬운 조합의 불변식 위반을 찾을 수 있다.

**Independent Test**: 격리된 실제 PostgreSQL을 사용하는 내부 서비스 순차 실행으로 고정 seed의 속성 검증을 단독 실행하고, 실제 시도 수·명령별 결과·최종 상태 비교가 모두 통과하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 매 시도마다 초기화된 저장소와 최초 수량 0~5의 대상 두 개, **When** 사용자 2명·대상 2개·생성 키의 작은 고정 집합에서 고른 명령 1~30건을 순서대로 실행, **Then** 각 명령의 결과 종류(새 성공·재현 성공·품절·키 충돌·대상 없음·예약 없음·조회 결과·취소 결과)가 독립 모델의 기대와 같다.
2. **Given** 같은 시도, **When** 모든 명령 실행이 끝남, **Then** 대상별 잔여 수량, 확정 예약 수, `잔여 + 확정 = 최초 수량`, (사용자, 키)당 예약 1개 이하, 예약별 상태가 독립 모델과 같다.
3. **Given** 재요청 명령, **When** 같은 사용자·키·대상으로 다시 생성, **Then** 최초 생성 결과의 예약 식별자·대상·`CONFIRMED`·생성 시각을 재현하고 재현 표시가 참이며, 원 예약이 취소된 뒤에도 최초 결과를 재현한다.
4. **Given** 타인의 예약 또는 존재하지 않는 논리 참조, **When** 조회·취소, **Then** 예약 없음 결과이며 어떤 수량·상태도 바뀌지 않는다.
5. **Given** 고정 seed, **When** 같은 명령을 두 번 실행, **Then** 같은 명령 순서가 생성되고 실제 시도 수는 매번 100회 이상이다.

### User Story 2 - 속성 실패를 seed와 최소 명령 순서로 재현하는 개발자 (Priority: P1)

개발자는 속성 검증이 실패하면 seed와 축소된 최소 명령 순서를 받아 같은 결과를 다시 만들고, 그 최소 사례를 일반 회귀 테스트로 고정한다.

**Why this priority**: 재현할 수 없는 무작위 실패는 원인 분석과 회귀 방지에 쓸 수 없다. 축소 결과는 실제 원인을 짧게 보여 준다.

**Independent Test**: 결함을 일시적으로 주입한 상태에서 속성 검증을 실행해 실패 seed·축소 순서를 얻고, 같은 seed 재실행이 같은 최소 순서를 보고하는지, 추가한 일반 회귀 테스트가 결함 상태에서 실패하고 원복 뒤 통과하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 고의 결함 상태, **When** 속성 검증 실행, **Then** 실패가 종료 코드에 반영되고 seed와 축소된 명령 순서·모델 기대·실제 결과의 차이가 출력된다.
2. **Given** 실패 seed, **When** 같은 seed로 재실행, **Then** 같은 축소 명령 순서가 보고된다. 축소를 위한 재실행마다 저장소와 논리 ID 대응표가 초기화된다.
3. **Given** 축소된 최소 사례, **When** 일반 회귀 테스트로 추가, **Then** 결함 상태에서 실패하고 원복 상태에서 통과한다. 기록은 고의 결함과 실제 구현에서 발견한 결함을 구분한다.
4. **Given** 기본 실행, **When** seed를 지정하지 않음, **Then** 고정 기본 seed로 회귀 검증이 수행된다. 새 seed 탐색은 seed를 명시한 별도 실행으로 구분해 기록한다.

### User Story 3 - 순수 규칙 테스트의 결함 탐지력을 변이로 측정하는 개발자 (Priority: P2)

개발자는 이름·수량 규칙, 생성 키 규칙, 취소 판단 규칙의 조건을 자동으로 바꿨을 때 대응 Unit 테스트가 이를 실패로 탐지하는지 확인하고, 남은 변이를 설명한다.

**Why this priority**: 통과하는 테스트가 실제로 조건 변화를 잡는지 측정해야 검증문 부족을 찾을 수 있다. 순수 규칙에 한정하면 빠르게 반복할 수 있다.

**Independent Test**: 세 규칙과 대응 Unit만 대상으로 변이 실행을 단독 수행하고 생성·탐지·생존·무효 결과와 보고서를 확인한다. 실행에 Spring과 컨테이너를 시작하지 않는다.

**Acceptance Scenarios**:

1. **Given** 세 규칙과 대응 Unit, **When** 변이 실행, **Then** 생성 변이 1개 이상, 탐지율 80% 이상, 대상 밖 클래스 변이 0, 커버리지 없음·도구 오류 0이다.
2. **Given** 살아남은 변이, **When** 분류, **Then** 각 변이가 “검증문 부족·테스트하지 않은 입력·동등 변이·도구의 한계” 중 하나와 이유로 기록되고, 중요한 규칙에서 설명되지 않은 생존 변이는 0이다. 검증문 부족·미검증 입력은 Unit 보완 후 재실행해 탐지됨을 확인한다.

### User Story 4 - SQL·권한·키 비교의 고의 변경을 테스트가 잡는지 확인하는 개발자 (Priority: P2)

개발자는 변이 도구가 다루지 않는 SQL 조건·소유자 조건·키 비교를 한 번에 하나씩 고의로 제거하고, 어떤 일반·경쟁·권한·속성 테스트가 실패하는지 확인한 뒤 반드시 원복한다.

**Why this priority**: 순수 규칙의 변이 점수만으로 SQL·동시성·권한의 안전성을 주장할 수 없다.

**Independent Test**: 각 고의 변경을 단독 적용해 지정 테스트를 실행하고 실패 테스트 목록을 기록한 뒤, 원복 diff가 비어 있음과 같은 테스트의 통과를 확인한다.

**Acceptance Scenarios**:

1. **Given** 수량 차감의 “잔여 > 0” 조건 제거, **When** 관련 테스트 실행, **Then** 1개 이상의 테스트가 실패한다.
2. **Given** 취소 상태 갱신의 “확정 상태” 조건 제거, 소유자 조건 제거, 생성 재요청의 대상 비교 제거 각각, **When** 관련 테스트 실행, **Then** 각 변경마다 1개 이상의 테스트가 실패한다. 실패하지 않으면 해당 테스트를 보완해 실패를 확인한다.
3. **Given** 네 변경의 원복, **When** 전체 심화 검증 실행, **Then** 고의 결함이 남지 않았고 모든 그룹이 실행 1건 이상·실패0·skip0으로 통과한다.

### Edge Cases

- 최초 수량 0인 대상에 대한 생성은 품절이며 같은 키로 다른 대상 생성은 성공할 수 있다(실패 키 비보존).
- 품절 후 같은 사용자·키로 다른 대상을 생성해 성공한 뒤, 원래 대상으로 재요청하면 키 충돌이다.
- 취소 후 같은 키·같은 대상 재요청은 새 예약 없이 최초 `CONFIRMED` 결과를 재현하고 조회는 `CANCELLED`다.
- 중복 취소는 같은 취소 시각을 반환하고 수량을 추가로 복구하지 않는다.
- 생성이 성공하지 않은 명령 번호를 참조하는 조회·취소는 예약 없음이다.
- 명령 1건뿐인 순서와 30건 순서를 모두 생성할 수 있어야 한다.
- 축소 중 재실행에서 이전 시도의 데이터·대응표가 남으면 거짓 실패·거짓 통과가 생기므로 매 실행 초기화한다.
- 변이 도구가 중복 입력을 건너뛰어 생성 예산과 실제 실행 수가 다를 수 있으므로 실제 실행 수로 판정한다.

## Requirements *(mandatory)*

### Functional Requirements

**속성 검증 (US1·US2)**

- **FR-001**: 명령은 생성(사용자·대상·키), 조회(사용자·논리 참조), 취소(사용자·논리 참조)로 표현하며 재요청·다른 대상 키 재사용·타인 취소·중복 취소·없는 참조는 이 명령의 조합으로 생성되어야 한다. 사용자·대상·키는 작은 고정 집합에서 고른다.
- **FR-002**: 예약 참조는 생성 명령의 순번을 논리 ID로 사용하고, 모델과 실제 예약 식별자의 대응표를 모델과 분리해 관리해야 한다. 성공하지 않은 생성이나 범위 밖 번호의 참조는 예약 없음을 기대한다.
- **FR-003**: 독립 모델은 실제 SQL·서비스·업무 규칙 클래스를 호출하지 않고 맵·집합으로 의미만 표현해야 한다. 실제 구현의 계산식을 복사한 메서드로 통과시키지 않는다.
- **FR-004**: 각 시도는 저장소를 초기화하고 최초 수량 0~5의 대상 2개를 만든 뒤 명령 1~30건을 순차 실행해야 한다. 축소를 위한 재실행에도 같은 초기화를 적용한다.
- **FR-005**: 각 명령의 결과 종류와 성공 결과의 필드(대상·상태·재현 여부·생성 시각의 최초값 동일성·취소 시각 유무와 중복 취소 시 동일성)를 모델과 비교하고, 모든 명령 뒤 대상별 잔여 수량·확정 수·보존식·(사용자,키) 유일성·예약별 상태를 모델과 비교해야 한다.
- **FR-006**: 실제 시도 수를 세어 100회 이상임을 검증하고 seed와 함께 출력해야 한다. 생성 예산과 실제 실행 수를 구분한다.
- **FR-007**: 기본 실행은 고정 seed를 사용하고, 환경으로 지정한 seed로 재현·탐색할 수 있어야 한다. 실패 시 seed·축소 명령 순서·차이를 읽을 수 있는 형식으로 출력한다.
- **FR-008**: 속성 검증은 속성 전용 실행 그룹에서 실제로 발견·실행되어야 하며, 일반 Unit·일반 통합 실행에는 포함되지 않아야 한다. 0건 실행·skip은 실패로 처리한다.
- **FR-009**: 고의 결함으로 얻은 축소 최소 사례를 일반 회귀 통합 테스트로 추가하고, 결함 상태 실패·원복 상태 통과를 확인해야 한다.
- **FR-010**: 속성 검증이 인증·요청 제한을 우회한 내부 서비스의 순차 정합성 검증이며 동시 실행 교차를 증명하지 않는다는 한계를 테스트 설명과 실행 기록에 남겨야 한다.

**변이 검증 (US3)**

- **FR-011**: 변이 실행 대상은 이름·수량 규칙, 생성 키 규칙, 취소 판단 규칙의 세 클래스로 한정하고 대응 Unit만 선택해야 한다. Spring·컨테이너를 시작하지 않는다.
- **FR-012**: 변이 결과 게이트는 생성 1개 이상, 탐지율 80% 이상, 커버리지 없음·시간 초과·도구 오류 0, 대상 밖 변이 0을 검사하고 위반 시 실패해야 한다. 이전 보고서로 통과하지 않는다.
- **FR-013**: 살아남은 변이를 네 분류와 이유로 기록하고, 검증문 부족·미검증 입력은 Unit 보완 후 재실행으로 탐지를 확인해야 한다. 동등 변이를 제외한 이유를 남긴다.

**고의 변경 탐지 (US4)**

- **FR-014**: 네 가지 고의 변경(수량 차감 잔여 조건, 취소 확정 상태 조건, 소유자 조건, 생성 재요청 대상 비교)을 한 번에 하나씩 적용해 실패한 테스트 이름을 기록하고, 각 변경 직후 원복해 제품 코드 diff가 비어 있음을 확인해야 한다.
- **FR-015**: 고의 변경을 탐지한 테스트가 없으면 해당 규칙을 검사하는 테스트를 보완하고 그 테스트가 고의 변경 상태에서 실패함을 확인해야 한다.
- **FR-016**: 모든 원복 뒤 전체 심화 검증(Unit·일반 통합·계약·속성)과 변이 실행을 실행해 실패0·skip0을 확인해야 한다.

**기록 (공통)**

- **FR-017**: 실행 명령·종료 코드·테스트 수·seed·실제 시도 수·축소 결과·변이 수치와 분류·고의 변경별 실패 테스트·미검증 범위를 실행 근거 문서에 기록하고, 계획서 10단계 체크박스는 실제 검증 후에만 표시해야 한다. 버전·결정·지식 문서·README의 실행 계약 설명을 실제 상태와 맞춘다.

### Key Entities

- **명령(Command)**: 생성·조회·취소 중 하나와 사용자·대상·키 또는 논리 참조. 사람이 읽을 수 있는 표현을 가진다.
- **독립 모델(Reference Model)**: 대상별 최초·잔여 수량, (사용자,키)→논리 예약, 논리 예약별 소유자·대상·상태·최초 생성 결과를 맵·집합으로 보관한다.
- **논리 ID 대응표**: 생성 명령 순번 → 실제 예약 식별자·생성 시각·취소 시각.
- **명령 결과(Outcome)**: 결과 종류와 비교할 필드 값.
- **변이 결과**: 변이별 대상·위치·상태·탐지 테스트와 생존 분류.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 고정 seed 기본 실행에서 실제 시도 100회 이상, 시도당 명령 1~30건, 실패0이며 같은 seed 두 번 실행의 생성 순서가 동일하다.
- **SC-002**: 고의 결함 상태에서 속성 검증이 실패하고 축소된 최소 순서가 5건 이하 명령으로 보고되며, 같은 seed 재실행이 같은 최소 순서를 보고한다.
- **SC-003**: 축소 최소 사례의 일반 회귀 테스트가 결함 상태 실패 → 원복 상태 통과를 보인다.
- **SC-004**: 세 순수 규칙의 변이 탐지율 80% 이상, 설명되지 않은 생존 변이 0, 커버리지 없음·도구 오류 0.
- **SC-005**: 네 고의 변경 각각에서 1개 이상의 테스트가 실패하고, 원복 뒤 제품 코드 diff 0.
- **SC-006**: 최종 전체 심화 검증과 변이 실행이 종료 코드 0, 모든 그룹 실행 1건 이상·실패0·skip0이다.

## Assumptions

- 사용자는 ADMIN을 제외한 USER_A·USER_B 두 명, 대상 2개, 생성 키 3개(예: K1~K3)의 고정 집합을 사용한다. 작은 집합이 재요청·충돌을 자주 만들도록 하기 위함이다.
- 대상 생성은 실제 대상 생성 경로를 사용하고 초기화는 기존 테스트 전용 초기화(예약 → 대상 순서)를 사용한다.
- 속성 검증은 기존 속성 도구와 고정 seed 관례를 재사용하고, 변이 실행은 기존 변이 도구 구성을 대상만 바꾸어 재사용한다. 도구 교체·버전 변경은 하지 않는다.
- 기존 변이 결과 게이트의 도구 프로브 대상은 업무 규칙 대상으로 교체한다. 도구 프로브 Unit은 일반 Unit에 남는다.
- 고의 결함의 주입·원복은 제품 코드의 일시 변경으로 수행하며 커밋하지 않는다. 장애 주입용 공개 파라미터를 추가하지 않는다.
- 실제 AI 구현 결함을 발견하지 못하면 이야기를 만들지 않고 고의 변이 결과만 기록한다.
