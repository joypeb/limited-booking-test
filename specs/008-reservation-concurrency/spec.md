## Clarifications

### Session 2026-10-20

- Q: 생성과 취소가 경쟁하는 시험에서, 생성 성공과 품절이라는 두 결과를 각각 반드시 재현해야 하나요? → A: 일반 경쟁 10회에 더해, 생성 성공·품절 순서를 각각 강제로 재현하고 각 10회 검증한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 한정 수량을 초과하지 않고 예약한다 (Priority: P1)

사용자는 다른 예약 요청이 몰려도 남은 수량 안에서만 예약을 확정받는다.

**Why this priority**: 초과 예약을 막는 것이 한정 수량 서비스의 핵심 가치다.

**Independent Test**: 수량 10인 대상에 서로 다른 사용자·생성 키 조합 100건을 동시에 제출하고 각 결과와 최종 수량을 비교한다. 사용자는 기존 고정 계정을 사용하고 키를 달리하여 조합을 구별할 수 있다.

**Acceptance Scenarios**:

1. **Given** 최초 수량과 잔여 수량이 10인 대상, **When** 서로 다른 사용자·키 조합의 예약 요청 100건이 경쟁하면, **Then** 성공 10건과 품절 90건이며 확정 예약 10건·잔여 수량 0이다.
2. **Given** 앞 경쟁이 종료된 상태, **When** 모든 요청 결과와 대상 상태를 대조하면, **Then** 예상 외 오류나 누락된 결과가 없고 초과 예약은 0건이다.

---

### User Story 2 - 동시에 재전송해도 하나의 예약 결과를 받는다 (Priority: P1)

사용자는 같은 생성 키로 여러 번 요청해도 중복 예약이나 추가 수량 차감 없이 최초 결과를 받는다. 같은 키로 대상을 바꾸면 충돌로 거부된다.

**Why this priority**: 경쟁 중 재전송 때문에 수량이 유실되거나 중복 예약이 생기면 사용자가 결과를 신뢰할 수 없다.

**Independent Test**: 동일 사용자·키의 동시 생성, 충분한 수량에서의 중복 생성, 다른 대상 간 키 충돌을 각각 독립된 초기 상태에서 확인한다.

**Acceptance Scenarios**:

1. **Given** 잔여 수량 1, **When** 같은 사용자·키·대상으로 10건을 동시에 요청하면, **Then** 모두 생성 성공이며 동일 예약 식별자·대상·최초 생성 시각·확정 상태·예약 위치를 반환한다. 최초 생성은 1건, 재현은 9건이고 저장 예약은 1건·잔여 수량은 0이다.
2. **Given** 잔여 수량 10, **When** 같은 사용자·키·대상으로 10건이 경쟁하면, **Then** 모두 같은 생성 결과를 받고 저장 예약은 1건·잔여 수량은 9다. 경쟁으로 중복 저장을 거부한 요청의 수량 차감도 남지 않는다.
3. **Given** 각각 잔여 수량 1인 서로 다른 대상 두 개, **When** 같은 사용자·키로 대상별 1건씩 경쟁하면, **Then** 한 대상만 생성 성공하고 다른 대상은 생성 키 충돌이다. 승자 대상은 예약 1건·잔여 0, 패자 대상은 예약 0건·잔여 1이다.
4. **Given** 두 요청 모두 최초 성공 기록을 찾지 못한 상태, **When** 같은 대상의 마지막 1개 또는 잔여 2개를 두고 각각 경쟁하면, **Then** 두 요청 모두 같은 생성 결과를 받고 최종 예약은 1건이다. 마지막 수량 소진 뒤 성공 기록 재확인과, 수량 차감 뒤 중복 저장 거부·전체 복구가 각각 실제로 발생했다는 증거를 남긴다.

---

### User Story 3 - 취소가 겹쳐도 수량을 한 번만 돌려받는다 (Priority: P1)

사용자는 취소를 동시에 재전송해도 같은 취소 결과를 받는다. 다른 사용자의 생성과 취소가 겹쳐도 수량과 최종 상태가 일치한다.

**Why this priority**: 중복 복구는 초과 예약을 유발하며 생성과 취소가 섞인 경우에도 수량 보존이 필요하다.

**Independent Test**: 한 예약의 10건 동시 취소와, 잔여 수량 0인 수량 1 대상의 기존 예약 취소·새 키 생성 경쟁을 따로 확인한다.

**Acceptance Scenarios**:

1. **Given** 수량 1 대상에 확정 예약 1건·잔여 수량 0, **When** 소유자가 같은 예약을 10건 동시에 취소하면, **Then** 전부 같은 예약의 취소 상태·최초 취소 시각을 받고 잔여 수량은 1로 한 번만 증가한다. 예약 행은 유지된다.
2. **Given** 수량 1 대상에 확정 예약 1건·잔여 수량 0, **When** 기존 예약 취소와 다른 생성 키의 새 예약이 경쟁하면, **Then** 취소는 성공하고 새 생성은 성공 또는 품절이다. 생성 성공이면 기존 예약 취소·새 확정 1건·잔여 0, 품절이면 기존 예약 취소·새 예약 없음·잔여 1이다.
3. **Given** 같은 초기 상태의 생성·취소 요청, **When** 취소의 수량 복구가 확정된 뒤 생성의 수량 판단이 진행되도록 순서를 제어하면, **Then** 생성 성공·기존 예약 취소·새 확정 1건·잔여 0을 각 10회 재현한다.
4. **Given** 같은 초기 상태의 생성·취소 요청, **When** 생성의 품절 판단이 끝난 뒤 취소가 수량을 복구하도록 순서를 제어하면, **Then** 생성 품절·기존 예약 취소·새 예약 없음·잔여 1을 각 10회 재현한다.
5. **Given** 앞 생성이 품절로 끝난 상태, **When** 취소 완료 후 같은 새 키로 다시 생성하면, **Then** 성공하여 확정 1건·잔여 0이며 이전 취소 예약은 재활성화되지 않는다.

---

### User Story 4 - 경쟁 결과를 재현하고 근거를 확인한다 (Priority: P2)

개발자는 우연한 성공과 실제 경쟁 경로의 검증을 구분하고, 다른 실행에서도 조건과 결과를 확인할 수 있다.

**Why this priority**: 이 프로젝트의 목적은 정합성을 직접 이해하고 재현 가능한 증거로 검증하는 것이다.

**Independent Test**: 앞 사례별 반복 결과와 경쟁 경로 관측, 종료 여부, 최종 수량·상태 기록을 검토한다.

**Acceptance Scenarios**:

1. **Given** 독립적으로 초기화된 경쟁 사례, **When** 각 사례를 10회 수행하면, **Then** 각 회차의 모든 요청 결과·종료·최종 상태가 확인되고 실패 회차도 누락 없이 기록된다.
2. **Given** 특정 경로를 확인하는 소규모 경쟁, **When** 두 요청을 최초 키 조회 완료 지점에서 맞추면, **Then** 실제 경쟁 경로가 관측되어야 통과하며 경로 미실행을 성공으로 처리하지 않는다.
3. **Given** 경쟁 중 수량 차감 뒤 예약 저장 실패가 발생하면, **When** 실패 요청이 종료되면, **Then** 그 요청의 부분 예약·수량 감소·성공 키 기록은 남지 않고 장애 제거 후 같은 키로 재시도할 수 있다.

### Edge Cases

- 동일 키의 성공 응답 개수와 고유 예약 개수는 다르다. 최초 응답 1건과 재현 응답을 구분한다.
- 서로 다른 대상의 키 충돌은 패자 대상의 수량까지 검사하며 승자만 검사하고 끝내지 않는다.
- 생성·취소 일반 경쟁과 두 순서 제어 사례를 구분하고, 일반 경쟁에서 한 결과만 관측되었다고 다른 순서의 검증을 대체하지 않는다. 두 허용 결과를 상태별로 검증한다. 허용된 품절을 장애와 섞지 않는다.
- 미완료 작업·예외·시간 초과·작업 종료 실패가 있으면 해당 회차는 실패다. 결과를 버리거나 재실행 성공으로 덮지 않는다.
- 준비 중 수량을 변경한 상태나 실행 중 관측만으로 최종 정합성을 판정하지 않는다.
- 취소 후 같은 생성 키 재요청은 최초 확정 결과를 재현하며 현재 상태 조회는 취소 상태를 유지한다. 기존 계약의 회귀 대상으로 유지한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: US1의 100건 경쟁에서 정확히 10건의 예약만 확정하고 나머지 90건은 품절로 구별해야 한다.
- **FR-002**: US2의 동일 사용자·키·대상 경쟁은 수량 1과 10에서 각각 예약 1건만 남기고 최초 생성 결과를 모든 성공 요청에 재현해야 한다.
- **FR-003**: US2의 다른 대상 간 같은 사용자·키 경쟁은 한 예약만 확정하고 패자 대상의 차감을 전부 복구해야 한다.
- **FR-004**: US3의 동시 취소 10건은 모두 동일한 취소 상태·시각을 반환하고 수량 복구를 정확히 1회만 반영해야 한다.
- **FR-005**: US3의 일반 생성·취소 경쟁 10회는 명시된 두 결과 중 하나만 허용한다. 별도로 생성 성공 순서와 품절 순서를 강제로 재현하여 각각 10회 검증해야 하며, 각 회차에서 의도한 순서가 실제 실행되었음을 관측해야 한다. 실패 생성의 키는 후속 성공을 막지 않아야 한다.
- **FR-006**: 모든 경쟁 종료 후 대상별 잔여 수량이 0 이상·최초 수량 이하이고, 잔여 수량과 확정 예약 수의 합이 최초 수량과 같아야 한다. 사용자·키별 예약은 최대 1건이어야 한다.
- **FR-007**: 경쟁 검증은 실제 예약 처리와 저장 결과를 사용해야 하며 각 작업은 독립적으로 완료 또는 전체 취소되어야 한다. 준비 데이터는 경쟁 시작 전에 확정하고 회차별로 격리해야 한다.
- **FR-008**: 100건 경쟁은 제한된 작업자 수로 실행하고 요청 시작 앞에서 함께 출발시켜야 한다. 소규모 사례에서는 최초 키 조회 후 두 요청의 경쟁을 보장하되, 검증을 위한 대기가 자원 보유 작업끼리 무한히 기다리는 구조를 만들면 안 된다.
- **FR-009**: 마지막 1개 소진 뒤 성공 기록 재확인과, 충분한 수량에서 중복 저장 거부 후 전체 복구는 별도 소규모 사례로 관측해야 한다. US2의 수량 1·2 조건과 수량 10 경쟁을 구별해 기록해야 한다.
- **FR-010**: US1~US3의 각 경쟁 사례와 FR-009의 두 강제 경로 사례 및 FR-005의 생성 성공·품절 순서 제어 사례를 각각 10회 반복해야 한다. 모든 작업의 예외·유한한 완료 제한 시간·종료 여부를 검사하고, 모두 종료된 뒤 한 관측 시점의 수량·확정 예약 집계로 FR-006을 판정해야 한다. 구체 제한 시간은 실행 계획에 명시한다.
- **FR-011**: 정상 인증을 포함한 실제 사용자 요청 진입 경로의 동시 생성·취소 사례를 유지해야 한다. 내부 처리만 검증한 사례와 구분하고 이후 요청 제한 도입 후에도 전체 경로 사례를 유지해야 한다.
- **FR-012**: 차감 후 저장 실패의 전체 복구와 같은 키 재시도 성공을 실제 저장 상태로 확인해야 한다. 이미 검증한 순차 장애와 이번 동시 경쟁의 증거를 구분해야 한다.
- **FR-013**: 기록에는 사례·반복별 요청 수·결과 수·소요 시간·작업자 수·사용 연결 수와 상한·환경·실행 명령·종료 코드·검증 수·경쟁 경로 관측·미검증 범위를 포함해야 한다. 재현 절차와 전체 회차의 결과로 제3자가 판정할 수 있어야 한다.
- **FR-014**: 정상 경쟁에서 예상 품절·키 충돌 외 오류나 결과 누락은 실패로 판정해야 한다. FR-012의 고의 실패 사례는 지정한 실패 자체를 예상 결과로 구분하되, 지정하지 않은 오류·결과 누락·부분 반영은 실패로 판정해야 한다. 경쟁 테스트 및 영향받는 기존 검증이 모두 통과한 뒤에만 해당 구현을 완료로 기록해야 한다.

### Key Entities *(include if feature involves data)*

- **예약 대상**: 최초 수량·잔여 수량을 가진 기존 대상. 이번 단계는 새 업무 속성을 추가하지 않는다.
- **예약과 생성 키**: 사용자·키에 연결된 기존 예약. 식별자·대상·최초 생성 시각은 유지하며 확정에서 취소로만 전이한다.
- **경쟁 실행 기록**: 사례·반복 번호·준비 상태·참여 요청·결과·실행 조건·관측 경로·최종 상태를 연결하는 검증 증거. 새 업무 데이터가 아니다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 수량 10·서로 다른 조합 100건의 경쟁 10회 모두 성공 10건·품절 90건·확정 예약 10건·잔여 0을 만족한다.
- **SC-002**: 동일 키 10건 경쟁은 수량 1과 10에서 각 10회 모두 고유 예약 1건·최초 생성 1건·동일 결과 10건이며 잔여 수량은 각각 0과 9다. 별도 수량 1·2의 강제 경쟁도 각각 10회 모두 지정 경로를 관측한다.
- **SC-003**: 다른 대상 간 키 충돌 10회 모두 성공 1건·충돌 1건이고 패자 수량 유실은 0이다.
- **SC-004**: 동시 취소 10건 경쟁 10회 모두 취소 결과가 같고 복구 횟수는 1이다. 일반 생성·취소 경쟁 10회 모두 허용 상태 중 하나이고 수량 불일치는 0이다. 별도 순서 제어 사례는 생성 성공 10회·품절 10회를 각각 재현하고, 의도한 순서의 관측률은 100%이며 최종 수량·상태 불일치는 0이다.
- **SC-005**: 모든 사례·회차에서 요청 결과 수집률과 작업 종료 확인율이 100%이고 수량 보존 위반·중복 예약·설명되지 않은 오류는 0건이다.
- **SC-006**: 실행 기록으로 각 인수 사례의 초기 상태·실행 조건·전체 결과·최종 상태·판정을 추적할 수 있다. 지정 경쟁 경로의 미관측 회차는 통과 0건으로 처리하고 한계를 명시한다.

## Assumptions

- 기준은 [로컬 개발 계획](<../../한정 수량 예약 백엔드 로컬 개발 계획.md>) 2~5절 및 7절 7단계다. [예약](../../knowledge/domain/reservation.md)·[대상](../../knowledge/domain/resource.md)·[보안](../../knowledge/domain/security.md) 지식과 [개발·검증 규칙](../../knowledge/rules/development-and-testing.md)을 적용한다.
- 6단계까지의 생성·조회·취소 구현을 선행 기반으로 사용한다. 현재 실제 경쟁 반복은 미검증이며 본 명세 작성은 기능 구현·테스트 실행 완료를 뜻하지 않는다.
- 이번 범위는 경쟁 정합성과 재현 증거다. 새로운 업무 기능·계약 변경·외부 공개·운영 성능 보장·후속 요청 제한 및 장애 확대·계약/속성/변이 심화·부하 시험은 포함하지 않는다.
- 후속 요청 제한 도입 전의 이번 단계에서 제한값을 임의로 구현하지 않는다. 도입 후 경쟁 시험의 설정과 초기화는 기존 요청 제한 규칙을 따르고 적용값을 기록한다.
- 요청 결과의 성공·품절·생성 키 충돌 의미는 기존 계약을 따른다. 구체 도구·동기화·관측 방법과 시간 제한·실행 명령은 다음 계획 단계에서 확정한다.
- 반복 검증은 지정한 경쟁 경로를 실제 관측했다는 근거이며 가능한 모든 실행 순서나 운영 규모의 안전성을 증명하지 않는다.
