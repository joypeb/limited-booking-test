**Feature Branch**: `feature/012-load-security-recovery`

**Created**: 2026-10-24

**Status**: Clarified(2026-10-24)

**Input**: 사용자 요청: 계획서 7절 11단계(로컬 부하·보안·장애 복구)를 Spec Kit SDD와 TDD로 개발한다. 0~10단계는 완료되었으며 반복하지 않는다.

## 기준과 범위

- 설계 기준: [계획서](<../../한정 수량 예약 백엔드 로컬 개발 계획.md>) 2~5절, 3.2절(load 프로필), 6.1~6.3절, 7절 11단계, 13절. 적용 지식: `knowledge/rules/*.md` 전체, `knowledge/domain/reservation.md`·`resource.md`·`security.md`·`ratelimit.md`.
- 이번 단계는 **실제 애플리케이션의 보안 경계·의존성 장애 복구·로컬 부하**를 검증한다. 예약·취소·멱등성·권한·요청 제한의 업무 규칙과 API 계약은 바꾸지 않는다. 검증 중 실제 결함이 드러나면 규칙을 완화하지 않고 재현·원인·영향을 기록한 뒤 최소 수정한다.
- 이미 검증된 사례(예: 기존 보안·소유권·롤백·Redis 장애 IT)는 재작성하지 않고 근거로 연결한다. 11단계 체크리스트 중 비어 있는 항목만 추가한다.
- 범위 밖: CI workflow·README 최종본(12단계), Qodana, 외부 공개·배포, 운영 규모 성능 주장, 다중 노드·네트워크 분할 시뮬레이션 도구 도입.

## Clarifications

### Session 2026-10-24

업무 정책 질문은 없다. 아래는 검증 설계의 모호점을 계획서·실제 코드 근거와 Explorer 갭 분석·Advisor 의견으로 해소한 기록이다(Orchestrator, 사용자 전체 진행 지시 범위).

- Q: 보안 항목 중 이미 검증된 것을 SecurityIT에 다시 작성하는가? → A: 재작성하지 않는다. Explorer 갭 분석 결과 타인 조회·취소(ReservationOwnershipIT), 본문 userId·알 수 없는 필드·UUID(ReservationCreateIT·ApiContractIT·SecurityIT), 401·403·413(SecurityIT)은 충족이다. 새로 추가할 것은 예약 경로의 `X-User-Id` 위조(현재 대상 경로만 검증)와 로그 비노출 검사 두 가지이며, 나머지는 실행 근거의 항목→테스트 연결표로 보고한다.
- Q: “DB 연결 중단”은 어떻게 재현하는가? → A: 테스트 소유 PostgreSQL의 관리 연결에서 대상 DB의 신규 연결을 막고(`ALLOW_CONNECTIONS false`) 앱의 기존 연결을 강제 종료한다. 복구는 연결 허용 재설정이다. 컨테이너 stop/restart는 동적 포트가 바뀌어 같은 앱 컨텍스트의 재연결 검증이 불가능하므로 쓰지 않는다.
- Q: “DB 응답 정지”도 범위인가? → A: 포함한다(US2-3). 계획서 11단계가 “503·유한한 응답 시간”을 요구하고, 현재 설정에는 클라이언트 측 소켓 읽기 상한이 없어 서버측 statement timeout이 동작하지 않는 정지 상태에서 무한 대기할 가능성이 있다(Advisor 추정, 미실행). 테스트로 먼저 재현(RED)하고, 확인되면 계약을 바꾸지 않는 최소 설정(드라이버 소켓 읽기 상한, statement 5초보다 긴 값)으로 수정하며 계획서 5.3절·결정 기록을 갱신한다. 재현되지 않으면 수정하지 않고 결과만 기록한다.
- Q: 장애 응답 시간 상한(FR-010)은? → A: 잠금 보유 4초(lock 2초 + 여유), 연결 거부 6초(연결 획득 3초 + 여유), 응답 정지 12초(소켓 읽기 상한 7초 + 연결 획득 여유). 근거: 설정값 계층 lock 2초 < statement 5초 < 소켓 7초, macOS Docker Desktop 지연 여유. 기존 생성 잠금 사례의 9초 상한은 기존 테스트 값으로 유지한다.
- Q: 응답 유실은 어떻게 재현하는가? → A: 테스트가 raw TCP로 생성 요청을 보내고, 상한 있는 DB 폴링으로 해당 (사용자, 키) 예약의 커밋을 확인한 뒤 응답을 읽지 않고 연결을 닫는다. 이후 같은 키로 재시도한다. 제품 코드·공개 API에 후크를 추가하지 않는다. 커밋이 상한 안에 확인되지 않으면 실패다.
- Q: 로그 비노출은 무엇으로 검사하는가? → A: 실제 로그 이벤트를 메모리 appender로 캡처해 메시지·인자·예외 스택 문자열 전체에서 비밀번호 원문·Authorization 값을 찾는다. 표준 출력 전체 캡처는 병행 스레드 소음 때문에 보조 수단으로만 쓴다.
- Q: 통과로 바로 끝나는 검증 테스트의 RED는? → A: 이미 올바른 동작을 검증하는 새 테스트는 10단계와 같이 제품 코드의 일시적 고의 변경(커밋 금지·즉시 원복)으로 탐지력을 확인한다. 예: 신원 해석이 `X-User-Id`를 읽게 변경, Authorization 값을 로그로 출력, 취소의 잠금 시간 설정 제거, 재현 표시를 거짓으로 변경.
- Q: load DB는 어떻게 준비하는가? → A: Compose 초기화 스크립트는 기존 named volume에 적용되지 않으므로, 실행 스크립트가 같은 PostgreSQL에 `reservation_load`가 없을 때만 생성하고 앱 기동 시 Flyway가 스키마를 적용한다. 초기화는 load DB에서 reservations → resources 순 DELETE, 제한 카운터는 USER_A·USER_B 키만 삭제한다.
- Q: 부하 제한값은 어떻게 명시하는가? → A: load 설정은 제한값 기본값을 두지 않고 실행 시 필수 환경 변수로 받는다(부하 100,000/60초, 제한 시험 20/60초). 값 누락 시 기동 실패가 되어 변경값이 항상 명시된다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 실제 인증 경로에서 객체 권한·입력 위조·정보 노출을 막는지 확인하는 개발자 (Priority: P1)

개발자는 실제 Basic 인증 헤더와 전체 보안 필터를 통과하는 요청으로 타인 예약 접근, 사용자 식별자 위조, 일반 사용자의 관리자 기능 사용, 비정상 인증·입력·큰 본문을 시도하고, 모두 계약된 거부 응답으로 끝나며 데이터가 바뀌지 않고 SQL·비밀번호·스택 트레이스가 응답과 로그에 드러나지 않음을 확인한다.

**Why this priority**: 객체 수준 권한 누락과 식별자 위조는 정합성 위반보다 피해가 크고, 내부 서비스 테스트로는 필터 순서·인증 경로의 결함을 잡지 못한다.

**Independent Test**: 격리된 실제 PostgreSQL·Redis와 실제 HTTP 서버로 보안 통합 테스트를 단독 실행해 각 항목의 응답 상태·code·헤더·DB 무변경·응답/로그 비노출을 확인한다.

**Acceptance Scenarios**:

1. **Given** USER_B의 확정 예약, **When** USER_A 또는 ADMIN이 실제 Basic 헤더로 그 예약을 조회·취소, **Then** 존재하지 않는 예약과 구별되지 않는 404 `NOT_FOUND`이며 예약 상태와 대상 잔여 수량이 바뀌지 않는다.
2. **Given** USER_A 인증, **When** 생성 본문에 `userId`(또는 `quantity`)를 추가, **Then** 400 `INVALID_REQUEST`이고 예약·수량·키 기록이 생기지 않는다.
3. **Given** USER_A 인증과 `X-User-Id: <USER_B 또는 ADMIN UUID>` 헤더, **When** 예약 생성, **Then** 생성된 예약의 소유자는 USER_A이며 USER_A의 조회는 200, USER_B의 조회는 404다.
4. **Given** USER 계정, **When** 관리자 대상 생성 API 호출, **Then** 403 `FORBIDDEN`이고 대상이 생기지 않는다.
5. **Given** 인증 없음·존재하지 않는 사용자·잘못된 비밀번호, **When** 보호된 API 호출, **Then** 401 `UNAUTHENTICATED`와 `WWW-Authenticate`이며 세션 쿠키가 없다.
6. **Given** 인증된 요청, **When** 잘못된 UUID 경로·본문, 알 수 없는 필드, 8KiB 초과 본문(Content-Length 표시·chunked 모두), **Then** 각각 400·400·413이며 `application/problem+json`과 계약된 `code`를 갖는다. 413은 인증 이전에 거부된다.
7. **Given** 위 거부 요청들과 DB 장애 응답, **When** 응답 본문·헤더와 해당 시간 동안의 애플리케이션 로그를 검사, **Then** 요청에 사용한 비밀번호 원문, Authorization 헤더 값, SQL 문장·SQLSTATE 상세, Java 스택 트레이스·예외 클래스 이름이 응답에 없고, 비밀번호 원문과 Authorization 값은 로그에도 없다.

### User Story 2 - DB 장애·잠금 시간 초과·응답 유실에서 부분 반영 없이 같은 키로 복구하는 개발자 (Priority: P1)

개발자는 DB 연결이 끊기거나 DB가 응답하지 않거나 잠금을 얻지 못하는 동안 예약 쓰기가 유한한 시간 안에 503으로 끝나고 아무것도 부분 저장되지 않으며, 장애가 사라진 뒤 같은 생성 키로 정상 처리됨을 확인한다. 또한 서버가 커밋까지 끝낸 뒤 클라이언트가 응답을 잃어버린 경우 같은 키 재시도가 같은 예약을 돌려줌을 확인한다.

**Why this priority**: 장애 시 무한 대기·부분 커밋·재시도 중복 예약은 수량 불변식을 직접 깨뜨린다. 계획서 2절의 “DB 제약 오류·응답 전 연결 실패” 실패 조건을 끝까지 검증하는 단계다.

**Independent Test**: 테스트가 소유한 격리 PostgreSQL에 장애를 주입하는 전용 통합 테스트를 단독 실행해 각 장애의 응답 상태·code·응답 시간 상한·DB 상태·복구 후 결과를 확인한다.

**Acceptance Scenarios**:

1. **Given** 대상(수량 충분)과 USER_A, **When** 애플리케이션의 기존 DB 연결이 강제로 끊기고 새 연결도 거부되는 동안 예약 생성·취소, **Then** 각 요청이 정해진 상한 시간 안에 503 `DEPENDENCY_UNAVAILABLE`로 끝나고 대상 잔여 수량·예약 행·예약 상태가 장애 전과 같다.
2. **Given** 1의 장애를 제거, **When** 같은 사용자·같은 생성 키·같은 대상으로 재요청, **Then** 201과 `Idempotent-Replayed: false`(실패 키는 보존하지 않음)이며 예약 1건·잔여 수량 1 감소다. 장애 중 취소에 실패한 예약은 복구 후 취소가 성공하고 수량은 1만 복구된다.
3. **Given** DB 서버가 응답하지 않는 상태(프로세스 정지 등), **When** 예약 생성, **Then** 요청이 무한히 대기하지 않고 정해진 상한 시간 안에 503으로 끝나며, 서버 재개 뒤 DB에 해당 요청의 예약·수량 변경이 없고 같은 키로 정상 처리된다.
4. **Given** 다른 트랜잭션이 대상 행 잠금을 보유, **When** 같은 대상에 대한 예약 생성과 (다른 예약의) 취소, **Then** 각각 잠금 시간 초과 기준에 맞는 상한 안에 503이고 부분 저장이 없으며, 잠금 해제 뒤 같은 키 생성·같은 예약 취소가 정상 처리된다.
5. **Given** 예약 생성 요청을 보낸 클라이언트, **When** 서버가 커밋을 완료한 것을 DB로 확인한 뒤 클라이언트가 응답을 읽지 않고 연결을 버림, **Then** 같은 키·같은 대상 재시도는 201·같은 예약 id·같은 생성 시각·`Idempotent-Replayed: true`이고 예약 행 1건·잔여 수량 1 감소만 존재한다.
6. **Given** 모든 장애 사례 종료, **When** 단일 집계 조회로 검사, **Then** 대상별 `잔여 + 확정 예약 수 = 최초 수량`, `0 ≤ 잔여 ≤ 최초 수량`이 성립한다.

### User Story 3 - 로컬 부하에서 정합성과 지연을 측정하고 판정하는 개발자 (Priority: P2)

개발자는 load 전용 설정·전용 DB로 실행한 실제 애플리케이션에 낮은 경쟁·높은 경쟁·재요청·요청 제한 시나리오를 실행하고, 부하 도구의 임계값 종료 코드와 종료 후 DB 불변식 검사로 통과·미달을 판정해 기록한다.

**Why this priority**: 테스트 컨테이너 사례가 통과해도 실제 기동 설정·연결 풀·인증 비용이 결합된 부하에서 정합성과 오류 분류가 유지되는지는 별도 확인이 필요하다. 다만 결과는 로컬 측정이며 기능 정합성 검증 뒤에 수행한다.

**Independent Test**: load 전용 DB를 초기화하고 load 설정으로 앱을 실행한 뒤 각 시나리오 스크립트를 실행해 종료 코드·상태 코드별 건수·지연 백분위·DB 검사 결과를 저장한다.

**Acceptance Scenarios**:

1. **Given** 초기화된 load DB, 여러 대상·충분한 수량, 사용자당 100,000건/60초 제한, **When** 10VU가 매번 다른 키로 생성 → 취소를 준비 30초 + 본 측정 2분 동안 반복(3회, 매회 초기화), **Then** 결과(p50/p95/p99·처리량·상태 코드별 건수)가 기록되고 잠정 기준 p95 < 500ms·예상치 못한 오류율 < 1%의 통과·미달이 판정되며, 종료 후 모든 대상에서 불변식이 성립한다.
2. **Given** 수량 1000의 대상 1개, **When** 50VU가 서로 다른 키로 생성 요청 총 2000회(3회, 매회 초기화), **Then** 201이 정확히 1000건, 본문 code가 `SOLD_OUT`인 409가 정확히 1000건, 그 외 상태(429·503·500·시간 초과) 0건이며 종료 후 확정 1000·잔여 0이다. 하나라도 어긋나면 부하 도구가 0이 아닌 종료 코드로 끝난다.
3. **Given** 재요청 시나리오, **When** 같은 키 집합을 여러 번 전송, **Then** HTTP 성공 건수(최초 + 재현)와 DB 고유 예약 건수가 구분되어 기록되고, 고유 예약 수 = 사용한 키 수, 재현 응답의 예약 id는 최초 응답과 같다.
4. **Given** 원래 제한 20건/60초로 실행한 앱과 초기화한 제한 카운터, **When** 한 사용자가 21건 이상의 쓰기 요청, **Then** 21번째부터 429 `RATE_LIMITED`와 1 이상의 정수 `Retry-After`이고, 429 요청은 예약·수량을 바꾸지 않는다(DB 검사).
5. **Given** 각 시나리오, **When** 실행 종료, **Then** 부하 도구 임계값이 종료 코드에 반영되고 DB 불변식 검사 결과가 별도 파일로 저장된다. 고의로 기대값을 어긋나게 만든 실행은 0이 아닌 종료 코드를 낸다.
6. **Given** 판정 기준 미달, **When** 원인 분석, **Then** 병목 후보 하나를 측정으로 확인하고 하나만 바꿔 같은 조건으로 재측정한 결과를 기록한다. 원인 불명 상태에서 가상 스레드·풀 증가·캐시를 추가하지 않는다.

---

### Edge Cases

- 장애 주입 중에도 조회·대상 API가 아닌 쓰기 요청만 테스트 대상이며, 요청 제한 카운터는 DB 실패로 되돌리지 않는다(장애 사례 사이 카운터 초과로 429가 섞이지 않게 테스트 제한값을 명시한다).
- DB 연결이 끊긴 뒤 풀의 죽은 연결을 다시 사용해도 성공이나 500으로 끝나지 않고 503 또는 복구된 정상 처리여야 한다. 분류하지 못한 예외는 500으로 드러나야 하며 503으로 숨기지 않는다.
- 응답 유실 사례에서 클라이언트 연결 종료만으로 커밋을 추정하지 않는다. 커밋 미확인 상태라면 테스트는 실패로 처리한다.
- 잠금 시간 초과로 503이 난 생성 요청의 키는 보존되지 않으므로 잠금 해제 후 같은 키의 최초 응답은 `Idempotent-Replayed: false`다.
- 높은 경쟁에서 409가 `SOLD_OUT`이 아닌 code(예: `IDEMPOTENCY_CONFLICT`)면 예상 품절로 세지 않는다.
- 부하 중 429가 나오면 제한 설정 누락이므로 예상 결과로 섞지 않고 실패로 판정한다.
- load DB는 로컬 개발 DB(`reservation_local`)와 분리되어야 하며, 초기화 스크립트가 다른 DB를 지우지 않아야 한다.
- 8KiB 정확히인 본문은 통과, 1바이트 초과는 413이다(기존 검증 유지).

## Requirements *(mandatory)*

### Functional Requirements

**보안 (US1)**

- **FR-001**: 계획서 11단계 보안 항목(타인 조회·취소, 본문 `userId`, `X-User-Id` 위조, USER의 관리자 API, 미인증·잘못된 비밀번호, 잘못된 UUID, 알 수 없는 필드, 큰 본문 413)마다 실제 Authorization 헤더와 전체 보안 필터를 통과하는 HTTP 테스트가 1개 이상 존재해야 한다. 기존 테스트가 충족하는 항목은 재작성하지 않고 근거로 연결하며, 비어 있는 항목은 보안 통합 테스트에 추가한다.
- **FR-002**: 각 거부 사례는 상태·`code`·`application/problem+json`·필수 헤더(401 `WWW-Authenticate`)와 DB 무변경(예약 행·잔여 수량·대상 수)을 함께 검증해야 한다.
- **FR-003**: `X-User-Id` 위조 생성은 인증 사용자 소유로 저장되어야 하며, 저장된 소유자를 실제 HTTP 조회 결과(소유자 200, 위조 대상 사용자 404)와 DB 값으로 확인해야 한다.
- **FR-004**: 거부 응답과 DB 장애 응답의 본문·헤더에 비밀번호 원문·Authorization 값·SQL 문장·SQLSTATE·스택 트레이스·예외 클래스 이름이 없어야 하며, 같은 기간의 애플리케이션 로그에 비밀번호 원문·Authorization 값이 없어야 한다. 로그 검사는 실제 로그 출력을 캡처해 수행한다.

**의존성 장애 복구 (US2)**

- **FR-005**: DB 연결 강제 종료와 신규 연결 거부를 테스트 소유 PostgreSQL에서 재현하고, 그동안의 예약 생성·취소가 상한 시간 안에 503 `DEPENDENCY_UNAVAILABLE`로 끝나며 부분 저장이 없음을 검증해야 한다.
- **FR-006**: DB 서버 응답 정지를 재현하고 예약 생성이 상한 시간 안에 503으로 끝남을 검증해야 한다. 현재 설정으로 상한을 지키지 못하면 실제 결함으로 기록하고, 계약을 바꾸지 않는 최소 설정 변경으로 해결한 뒤 계획서·결정 기록을 갱신해야 한다.
- **FR-007**: 대상 행 잠금 보유 중 생성·취소가 잠금 시간 초과에 맞는 상한 안에 503으로 끝나고 부분 저장이 없음을 검증해야 한다. 생성의 잠금 시간 초과는 기존 회귀 테스트(`ReservationRollbackIT.lockTimeoutIs503AndSameKeyRecovers`)를 근거로 연결하고, 확정 예약 취소의 잠금 시간 초과(현재 미검증)를 새로 추가한다.
- **FR-008**: 모든 장애 제거 후 같은 생성 키로 201·`Idempotent-Replayed: false` 정상 처리, 실패했던 취소의 정상 처리와 1회 복구를 검증해야 한다.
- **FR-009**: 커밋 완료를 DB로 확인한 뒤 클라이언트가 응답을 버리는 재현을 만들고, 같은 키 재시도가 같은 id·생성 시각·재현 표시 참을 반환하며 예약 1건·수량 1 감소만 남음을 검증해야 한다.
- **FR-010**: 각 장애 사례의 응답 시간을 측정해 상한과 비교해야 한다. 상한 값과 근거(잠금 2초·statement 5초·연결 획득 3초·Redis 200ms 등 설정값)는 계획 단계에서 확정해 테스트와 기록에 같은 값을 사용한다.
- **FR-011**: 장애 주입·해제 후크는 테스트 코드에만 두고 공개 API에 장애 주입 수단을 추가하지 않아야 한다. 장애는 테스트가 소유한 컨테이너에만 적용하고 종료 시 원상 복구한다.

**로컬 부하 (US3)**

- **FR-012**: load 실행 설정은 로컬 개발 DB와 분리된 `reservation_load` DB를 사용하고, 요청 제한 값을 실행 시 명시적으로 지정할 수 있어야 하며(부하 100,000건/60초, 제한 시험 20건/60초), localhost에만 바인딩해야 한다. 비밀번호는 환경 변수로만 받는다.
- **FR-013**: load DB 준비·초기화와 시나리오별 데이터 준비, 제한 카운터 초기화, 종료 후 DB 불변식 검사를 사람의 기억 없이 재현 가능한 스크립트·SQL로 제공해야 한다. 초기화는 load DB만 대상으로 해야 한다.
- **FR-014**: 낮은 경쟁·높은 경쟁·재요청 시나리오 스크립트와 별도의 요청 제한 스크립트를 제공해야 한다. 높은 경쟁은 201·409만 예상 상태로 두고 모든 409의 본문 code가 `SOLD_OUT`임을 검사한다.
- **FR-015**: 각 스크립트는 check와 함께 임계값으로 판정을 종료 코드에 반영해야 하며, 고의로 기대를 어긋나게 만든 실행이 0이 아닌 종료 코드를 내는 것을 1회 이상 확인해야 한다.
- **FR-016**: 낮은 경쟁은 준비 30초 + 본 측정 2분을 3회, 높은 경쟁·재요청·요청 제한은 각 3회 실행하며 매회 load 데이터와 제한 카운터를 초기화해야 한다. 각 실행의 원시 결과 요약과 DB 검사 결과를 저장한다.
- **FR-017**: 성능 보고서에 기기·CPU 아키텍처·JDK·Docker 메모리·DB/Redis 이미지·연결 풀·제한값·데이터량·대상 커밋·p50/p95/p99·처리량·상태 코드별 건수·판정·한계를 기록해야 한다. Basic 인증·BCrypt 비용을 포함한 전체 HTTP 측정이며 순수 서비스 성능·운영 규모와 구분한다.
- **FR-018**: 판정 미달 시 병목 하나를 측정으로 확인하고 하나만 변경해 같은 조건으로 재측정해야 한다. 원인 없는 튜닝을 추가하지 않는다.

**기록 (공통)**

- **FR-019**: 실행 명령·종료 코드·테스트 수·장애 조건·응답 시간·보안 항목→테스트 연결·미검증 범위를 실행 근거 문서에 기록하고, 계획서 11단계·13절 체크박스는 실제 검증 후에만 표시해야 한다. 버전(부하 도구 등)·결정·지식 문서·README의 실행 안내를 실제 상태와 맞춘다.
- **FR-020**: 기존 일반 Unit·일반 통합·계약·속성·변이 실행 그룹이 실패0·skip0으로 유지되어야 하며 새 통합 테스트는 일반 통합 그룹에서 실제 발견·실행되어야 한다.

### Key Entities

- **보안 사례**: 행위자(ADMIN·USER_A·USER_B·미인증), 요청(경로·헤더·본문), 기대 상태·code·헤더, DB 무변경 조건, 비노출 검사 문자열.
- **장애 사례**: 장애 종류(연결 종료·연결 거부·응답 정지·잠금 보유·응답 유실), 주입·해제 절차, 응답 시간 상한, 장애 전후 DB 스냅샷, 복구 요청과 기대 결과.
- **부하 시나리오**: VU·반복/시간·대상 수·수량·키 정책·제한값·예상 상태와 임계값.
- **부하 실행 기록**: 실행 번호·초기화 확인·상태 코드별 건수·지연 백분위·처리량·종료 코드·DB 검사 결과.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 11단계 보안 항목 100%가 실제 HTTP 테스트에 연결되고, 권한·위조 위반 0건, 응답·로그의 비밀정보 노출 0건이다.
- **SC-002**: 모든 장애 사례가 상한 시간 안에 503으로 끝나고, 부분 저장 0건, 장애 제거 후 같은 키 복구 성공 100%다.
- **SC-003**: 응답 유실 재현에서 재시도 결과의 예약 id가 커밋된 예약과 같고 DB 예약 행은 1건이다.
- **SC-004**: 높은 경쟁 3회 모두 201 = 1000, `SOLD_OUT` 409 = 1000, 기타 상태 0, 종료 후 확정 1000·잔여 0이며 부하 도구 종료 코드 0이다.
- **SC-005**: 낮은 경쟁 3회의 p95·예상치 못한 오류율과 잠정 기준(p95 < 500ms, 오류율 < 1%) 대비 통과·미달이 기록되고, 모든 부하 실행 뒤 DB 불변식 위반 0건이다.
- **SC-006**: 요청 제한 시나리오에서 21번째 이후 요청이 모두 429와 1 이상 `Retry-After`를 받고 429 요청에 의한 DB 변경 0건이다.
- **SC-007**: 고의로 기대를 어긋나게 만든 부하 실행 1회 이상이 0이 아닌 종료 코드를 낸다.
- **SC-008**: 최종 일반 build·일반 통합·계약·속성·변이 실행이 종료 코드 0, 실행 그룹별 1건 이상·실패0·skip0이다.

## Assumptions

- 로컬 계정은 기존 ADMIN·USER_A·USER_B 세 개뿐이며 부하 시나리오의 사용자 쓰기는 USER_A·USER_B로 나누고, 대상 준비는 ADMIN으로 수행한다. 계정 추가는 범위 밖이다.
- 부하 대상 앱은 호스트 JVM에서 load 설정으로 실행하고 PostgreSQL·Redis는 기존 Compose 서비스(고정 이미지)를 사용한다. load DB는 같은 PostgreSQL 인스턴스의 별도 DB다.
- 부하 도구는 현재 기기에 설치된 k6(실행 확인한 버전을 기록)를 사용한다. 버전 고정은 기록으로 수행한다.
- 장애 재현은 Testcontainers가 소유한 컨테이너에서만 수행하고 Compose 서비스에는 장애를 주입하지 않는다.
- 기존 테스트의 기록된 커버리지(SecurityIT·ReservationOwnershipIT·ReservationRollbackIT·ReservationCancelIT·RedisFailureIT·ApiContractIT)는 그대로 유지하며 중복 재작성하지 않는다.
- 부하 결과가 잠정 기준에 미달해도 이번 단계의 실패로 숨기지 않고 미달로 기록한다. 정합성·권한 위반은 미달이 아니라 결함이다.
