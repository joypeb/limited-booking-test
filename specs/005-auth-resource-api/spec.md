# 기능 명세: 로컬 인증과 예약 대상 생성·조회 API

**작업 브랜치**: `feature/auth-resource-api`

**작성일**: 2026-10-17

**상태**: 초안

**입력**: 사용자가 선택한 [로컬 개발 계획](<../../한정 수량 예약 백엔드 로컬 개발 계획.md>) 7절의 「4단계: 로컬 인증과 예약 대상 API」. 고정 식별자를 가진 로컬 사용자 인증·권한 확인, 요청 본문 크기 상한과 엄격한 입력 검증, 공통 오류 응답, 예약 대상 생성·단건 조회를 실제 요청 경로에서 제공하고 검증한다.

## 사용자 시나리오와 검증 *(필수)*

### 사용자 이야기 1 - 로컬 계정 인증과 역할별 권한 확인 (우선순위: P1)

관리자와 일반 사용자는 사전에 정의된 로컬 계정 자격 증명으로 요청을 보내고, 시스템은 요청마다 자격 증명과 권한을 확인해 허용된 작업만 수행한다. 인증된 사용자의 고유 식별자는 오직 인증 결과에서만 가져오며 클라이언트가 임의로 전달한 사용자 식별자는 신뢰하지 않는다.

**우선순위 이유**: 이후 모든 대상·예약 요청의 소유권과 관리자 권한 판단이 인증 결과와 고정 사용자 식별자에 의존한다.

**독립 검증**: 예약 생성·취소 기능 없이도 무인증·잘못된 비밀번호·일반 사용자·관리자 자격 증언과 임의의 사용자 식별자 헤더·본문을 전달해 인증 성공·거부(401)·권한 거부(403)·식별자 불신뢰를 각각 확인한다.

**인수 시나리오**:

1. **조건** 고정된 고유 식별자(UUID)를 가진 로컬 계정 `ADMIN`·`USER_A`·`USER_B`와 환경에서 주입된 비밀번호가 설정돼 있을 때, **행동** 자격 증명 없이 요청하거나 잘못된 비밀번호로 대상 생성·조회를 요청하면, **결과** `401`(`UNAUTHENTICATED`) 상태, 인증 요구 헤더(`WWW-Authenticate`), 공통 오류 형식 응답을 반환하고 데이터를 변경하지 않는다.
2. **조건** 일반 사용자(`USER_A` 또는 `USER_B`)가 유효한 자격 증명으로 인증됐을 때, **행동** 예약 대상 생성을 요청하면, **결과** `403`(`FORBIDDEN`) 상태와 공통 오류 형식 응답으로 거부하고 대상을 저장하지 않는다.
3. **조건** 관리자(`ADMIN`)가 유효한 자격 증명으로 인증됐을 때, **행동** 유효한 예약 대상 생성을 요청하면, **결과** `201` 상태로 대상을 생성하고, 이후 `ADMIN`·`USER_A`·`USER_B` 모두 해당 대상을 `200`으로 단건 조회할 수 있다.
4. **조건** 인증된 사용자의 요청에 임의의 `X-User-Id` 헤더가 포함돼 있을 때, **행동** 인증된 사용자 식별자를 확인하거나 요청을 처리하면, **결과** 외부 헤더 값을 무시하고 오직 인증 주체(Principal)에 할당된 고정 UUID만 사용한다. 요청 본문에 정의되지 않은 `userId` 필드를 넣은 경우에는 `400`(`INVALID_REQUEST`)으로 거부한다.
5. **조건** localhost 비브라우저 클라이언트 전용 환경일 때, **행동** 인증 요청을 반복 수행하면, **결과** 서버 세션을 생성하거나 유지하지 않으며, 전체 출처 허용(CORS 와일드카드) 설정을 열지 않는다.

### 사용자 이야기 2 - 예약 대상 생성과 단건 조회 (우선순위: P1)

관리자는 예약 대상의 이름과 최초 수량을 지정해 새 대상을 등록하고, 인증된 사용자는 생성된 대상의 식별자로 대상 정보와 현재 남은 수량을 단건 조회한다.

**우선순위 이유**: 예약 생성·취소가 참조할 대상 데이터와 초기 수량 상태를 API를 통해 준비하고 확인할 수 있어야 한다.

**독립 검증**: 관리자로 대상을 생성한 뒤 반환된 위치 정보와 응답 본문을 확인하고, 일반 사용자로 해당 식별자와 존재하지 않는 식별자를 각각 조회해 비교한다.

**인수 시나리오**:

1. **조건** 관리자가 인증된 상태일 때, **행동** 유효한 이름과 최초 수량 `0` 또는 `1000`으로 대상 생성을 요청하면, **결과** `201` 상태, 생성된 단건 조회 경로(`Location: /api/resources/{id}`), 그리고 `id`·정리된 `name`·`capacity`·`available`(`available = capacity`)을 반환하며 저장소에 동일하게 기록된다.
2. **조건** 관리자가 앞뒤에 일반 공백·탭·줄바꿈이 포함된 이름(예: `  예약 대상  `)이나 내부 공백·비줄바꿈 공백(U+00A0·U+2007·U+202F)·이모지(`😀` 100개)가 포함된 유효한 이름으로 생성을 요청할 때, **행동** 대상을 생성하고 다시 단건 조회하면, **결과** 기존 확정된 이름 정리 규칙에 따라 앞뒤 제거 대상 공백만 정리되고 내부 공백·비줄바꿈 공백은 보존된 이름이 저장·반환된다.
3. **조건** 대상이 생성돼 있을 때, **행동** 인증된 사용자가 해당 대상의 UUID로 단건 조회하면, **결과** `200` 상태와 저장된 `id`·`name`·`capacity`·`available`을 반환한다.
4. **조건** 인증된 사용자가 존재하지 않는 UUID로 단건 조회할 때, **행동** 조회를 요청하면, **결과** `404`(`NOT_FOUND`) 상태와 공통 오류 형식 응답을 반환한다.

### 사용자 이야기 3 - 본문 크기 상한·엄격한 입력 검증·공통 오류 응답 (우선순위: P2)

클라이언트가 과도한 크기의 본문, 지원하지 않는 미디어 형식, 정의되지 않은 필드나 중복 키, 암묵적 형 변환을 유도하는 값, 범위 밖의 입력을 보낼 때 시스템은 정해진 우선순위에 따라 요청을 일찍 거부하고 일관된 오류 형식으로 응답한다.

**우선순위 이유**: 비정상 입력이나 우회 요청이 하위 계층이나 저장소로 전달되지 않게 차단하고, 클라이언트가 모든 실패 원인을 동일한 구조로 판별할 수 있어야 한다.

**독립 검증**: 인증 전 본문 초과 요청(길이 헤더 유무·분할 전송 포함), 잘못된 미디어 형식, 잘못된 JSON·UUID·경계 밖 값을 각각 전송해 상태 코드·오류 코드·응답 형식을 확인한다.

**인수 시나리오**:

1. **조건** 요청 본문이 `8KiB(8,192바이트)`를 초과할 때, **행동** 자격 증명 없이 또는 자격 증명과 함께 길이 헤더가 있는 요청·길이 헤더가 없는 요청·분할 전송(chunked) 요청을 보내면, **결과** 인증보다 먼저 실제 읽은 바이트 기준으로 차단해 `413`(`PAYLOAD_TOO_LARGE`)과 공통 오류 형식 응답을 반환한다.
2. **조건** 요청 본문이 `8,192바이트` 이하일 때, **행동** 본문 크기 검사를 통과한 생성 요청을 처리하면, **결과** 읽은 본문이 손실되지 않고 후속 입력 변환·검증 계층에서 정상적으로 재사용된다.
3. **조건** 대상 생성 요청의 미디어 형식이 `application/json`이 아닐 때(예: `text/plain`), **행동** 인증된 관리자가 요청을 보내면, **결과** `415`(`UNSUPPORTED_MEDIA_TYPE`)와 공통 오류 형식 응답으로 거부한다.
4. **조건** 관리자가 대상 생성을 요청할 때, **행동** 빈 이름·공백만 있는 이름·정리 후 코드 포인트 101개 이름, 범위 밖 수량(`-1`, `1001`), 부동소수점 수량(`1.5`), 문자열 수량(`"10"`), 정의하지 않은 필드(`userId` 등), 중복된 JSON 키, 잘못된 JSON 구문을 각각 보내면, **결과** 모두 `400`(`INVALID_REQUEST`)과 공통 오류 형식 응답으로 거부하고 대상을 저장하지 않는다.
5. **조건** 인증된 사용자가 잘못된 UUID 형식의 경로로 대상을 조회하거나 취소 경로(`/api/reservations/{id}/cancel`)에 8,192바이트 이하의 비어 있지 않은 본문을 보낼 때, **행동** 요청을 전송하면, **결과** `400`(`INVALID_REQUEST`)과 공통 오류 형식 응답으로 거부한다.
6. **조건** 인증 실패(401), 권한 부족(403), 대상 없음(404), 본문 크기 초과(413), 미지원 미디어 형식(415), 입력 오류(400)가 발생할 때, **행동** 응답 본문과 헤더를 확인하면, **결과** 모든 응답이 `application/problem+json` 미디어 형식과 필수 속성(`type`, `title`, `status`, `detail`, `instance`, `code`)을 갖추며 SQL·스택 트레이스·비밀번호를 노출하지 않는다.

### 경계 사례

- 본문 크기 `8,192바이트`(허용)와 `8,193바이트`(413 거부), `Content-Length`가 없거나 작게 표시된 분할 전송(chunked) 본문의 실제 읽기 상한 초과.
- 미인증 상태에서 `8,193바이트` 본문 전송 시 `401`이 아니라 `413`이 먼저 반환되는지, `8,192바이트` 이하 미인증 요청에서는 `401`과 `WWW-Authenticate`가 반환되는지 구분.
- 최초 수량 `0`·`1`·`1000`(201 허용)과 `-1`·`1001`·부동소수점(`0.5`, `1.0`)·문자열(`"1"`)(400 거부).
- 이름 누락(`null`)·빈 문자열·일반 공백/탭/줄바꿈만 있는 문자열(400 거부), 앞뒤 공백 제거 후 1자·100자·`😀` 100개·NBSP 1개(201 허용), 정리 후 101자·`😀` 101개(400 거부).
- 정의하지 않은 필드(`userId`, `quantity`, `available` 등), 동일 JSON 객체 내 중복 키(예: `{"name":"a","name":"b","capacity":1}`), 깨진 JSON 본문(400 거부).
- 단건 조회 경로의 유효하지 않은 UUID 문자열(400 거부)과 유효한 형식이지만 저장소에 없는 UUID(404 거부).
- 취소 경로(`/api/reservations/{id}/cancel`)에 전달된 `8,192바이트` 이하의 비어 있지 않은 본문(400 거부)과 `8,193바이트` 이상 본문(413 거부).
- 임의의 `X-User-Id` 헤더를 함께 보낸 요청에서 헤더 값으로 사용자 식별자가 위조되지 않는지 확인.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 시스템은 `ADMIN`·`USER_A`·`USER_B` 세 로컬 계정에 고정된 고유 UUID를 할당하고, 실행 환경에서 주입받은 비밀번호를 단방향 해시로 보관해야 한다. 실행 환경 비밀번호와 테스트용 가짜 비밀번호는 분리해야 하며, 코드·문서·오류 응답에 비밀번호 원문이나 해시를 노출하지 않아야 한다. 이야기 1.1·1.3으로 검증한다.
- **FR-002**: 시스템은 서버 세션을 생성하지 않는 무상태 Basic 인증을 통해 모든 보호된 요청의 자격 증명을 확인해야 한다. 자격 증명이 없거나 잘못된 경우 `401`(`UNAUTHENTICATED`)과 `WWW-Authenticate` 헤더를 반환하고, 일반 사용자가 관리자 전용인 대상 생성을 요청하면 `403`(`FORBIDDEN`)으로 거부해야 한다. 이야기 1.1~1.3으로 검증한다.
- **FR-003**: 시스템은 인증된 사용자의 UUID를 오직 인증 주체(Principal)에서만 조회해야 한다. 요청 본문의 `userId`나 임의의 `X-User-Id` 헤더를 신뢰하지 않으며, 정의되지 않은 `userId` 본문 필드는 `400`(`INVALID_REQUEST`)으로 거부해야 한다. 이야기 1.4·3.4로 검증한다.
- **FR-004**: 시스템은 localhost 비브라우저 클라이언트 환경을 전제로 동작하며, CSRF 보호를 비활성화하는 경우 그 목적과 localhost 한정 전제를 문서·설정에 명시해야 한다. 전체 출처 허용(CORS 와일드카드) 설정을 추가하지 않아야 한다. 이야기 1.5로 검증한다.
- **FR-005**: 관리자가 유효한 이름과 최초 수량(`0~1000`)으로 대상 생성을 요청하면 시스템은 기존 확정된 이름·수량 규칙을 적용해 대상을 저장하고, `201` 상태·`Location: /api/resources/{id}` 헤더·생성된 대상 정보(`id`, 정리된 `name`, `capacity`, `available=capacity`)를 반환해야 한다. 생성 시각은 주입된 UTC 기준 시계를 사용해 기록해야 한다. 이야기 2.1~2.2로 검증한다.
- **FR-006**: 인증된 사용자가 대상 UUID로 단건 조회를 요청하면 시스템은 대상이 존재할 때 `200` 상태와 대상 정보(`id`, `name`, `capacity`, `available`)를 반환하고, 존재하지 않을 때 `404`(`NOT_FOUND`)를 반환해야 한다. 잘못된 UUID 형식은 `400`(`INVALID_REQUEST`)으로 거부해야 한다. 이야기 2.3~2.4·3.5로 검증한다.
- **FR-007**: 시스템은 인증 단계보다 앞에서 모든 요청 본문의 실제 읽는 크기를 `8,192바이트(8KiB)`로 제한해야 한다. 길이 헤더 유무나 분할 전송(chunked) 여부와 무관하게 `8,192바이트`를 초과하는 요청은 즉시 `413`(`PAYLOAD_TOO_LARGE`)으로 거부하고, 상한 이하인 본문은 후속 처리에서 재사용할 수 있도록 전달해야 한다. 이야기 3.1~3.2로 검증한다.
- **FR-008**: 시스템은 생성 요청에서 `application/json` 이외의 미디어 형식을 `415`(`UNSUPPORTED_MEDIA_TYPE`)로 거부하고, 알 수 없는 JSON 필드·중복 JSON 키·숫자 필드의 암묵적 형 변환(부동소수점·문자열 등)·잘못된 JSON 구문·이름 및 수량 규칙 위반·취소 요청의 비어 있지 않은 본문을 모두 `400`(`INVALID_REQUEST`)으로 거부해야 한다. 이야기 3.3~3.5로 검증한다.
- **FR-009**: 필터(본문 크기 상한·인증·권한)와 요청 처리 전반에서 발생하는 모든 정의된 오류는 `application/problem+json` 형식과 필수 속성(`type`, `title`, `status`, `detail`, `instance`, `code`)을 일관되게 반환해야 한다. SQL·스택 트레이스·비밀번호 등 내부 세부 정보를 노출하지 않으며, 분류되지 않은 내부 결함은 임의의 4xx/503 코드로 숨기지 않고 `500`으로 탐지해야 한다. 이야기 1.1~1.2·2.4·3.1·3.3~3.6으로 검증한다.
- **FR-010**: 검증 기록은 기능 미구현 상태에서의 의도된 실패 확인과 구현 후 통과 결과를 구분하고, 실행 명령·종료 코드·실행 수·실패 수·건너뜀 수·환경·미검증 범위를 남겨야 한다. 테스트 0건·실패·건너뜀을 통과로 기록하지 않아야 한다. 이야기 1~3의 통합 검증으로 확인한다.

### 핵심 개체

- **로컬 인증 계정**: 역할(`ADMIN` 또는 `USER`), 고정된 사용자 UUID, 해시 처리된 자격 증명을 가진다. 요청 처리 중 사용자 식별자의 유일한 신뢰 출처다.
- **예약 대상**: 고유 식별자(`id`), 정리된 이름(`name`), 최초 수량(`capacity`, 0~1000), 현재 남은 수량(`available`, 생성 시 `capacity`와 동일)을 가진다. 저장소에는 UTC 기준 생성 시각(`created_at`)도 함께 보관한다.
- **공통 오류 응답**: 문제 유형(`type`), 요약 제목(`title`), 상태 코드(`status`), 안전한 상세 설명(`detail`), 요청 경로(`instance`), 고정 오류 코드(`code`)로 구성된다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 미인증·오류 비밀번호(`401` 및 `WWW-Authenticate`), 일반 사용자의 대상 생성(`403`), 관리자의 대상 생성(`201`), 세 로컬 계정의 단건 조회(`200`), 임의 `X-User-Id` 무시 및 미정의 `userId` 필드 거부(`400`) 사례가 실제 보안 경로에서 100% 기대 결과와 일치한다.
- **SC-002**: 최초 수량 경계(`0`, `1000`, `-1`, `1001`), 부동소수점·문자열 수량, 빈 이름·공백 이름·코드 포인트 경계(100자 허용·101자 거부), 중복 JSON 키·미정의 필드, 잘못된 UUID(`400`), 없는 UUID(`404`) 사례가 모두 기대 상태 코드 및 저장 결과와 일치하며, 거부된 요청으로 생성되는 대상은 0건이다.
- **SC-003**: `8,192바이트` 이하 본문은 정상 전달되고 `8,193바이트` 이상 본문(길이 헤더 유무·chunked 포함)은 미인증 요청에서도 인증보다 먼저 `413`으로 100% 차단되며, 미지원 미디어 형식(`415`)과 비어 있지 않은 취소 본문(`400`)이 모두 기대대로 거부된다.
- **SC-004**: 본문 상한 필터·인증/권한 처리·입력 및 도메인 검증에서 반환되는 모든 오류 응답이 `application/problem+json` 형식과 필수 6개 속성(`type`, `title`, `status`, `detail`, `instance`, `code`)을 100% 충족하고, 비밀번호·SQL·스택 트레이스 노출은 0건이다.
- **SC-005**: 기존 단위·통합 검증과 이번 단계의 보안·예약 대상 통합 검증이 모두 실패 0건·건너뜀 0건으로 통과하며, 의도된 실패 확인과 통과 증거가 실행 기록에 구분돼 남는다.

## 전제와 의존성

- 기준은 [로컬 개발 계획](<../../한정 수량 예약 백엔드 로컬 개발 계획.md>) 2~5절과 7절 4단계, [security 지식](../../knowledge/domain/security.md), [resource 지식](../../knowledge/domain/resource.md), [API·보안 규칙](../../knowledge/rules/api-and-security.md), [OpenAPI 계약](../../docs/openapi.yaml)이다. 기존 확정 계약을 변경하지 않는다.
- 2단계에서 구현·검증된 `resources`·`reservations` 스키마와 읽기 저장소(`ResourceRepository.find`), 테스트 데이터 준비·초기화(`TestData`), 3단계에서 구현·Unit 검증된 순수 규칙(`ResourceRules.normalizeName`, `ResourceRules.validateCapacity`)을 이번 단계의 실제 요청 경로에서 연결해 사용한다.
- 1단계에서 기동 확인용으로만 두었던 임시 계정 설정(`toolchain`)은 이번 4단계에서 고정 UUID를 가진 `ADMIN`·`USER_A`·`USER_B` 로컬 Basic 인증 구성으로 대체·정리하되, 기존 도구 최소 검증이 깨지지 않도록 함께 확인한다.
- 이번 단계에서 취소 경로(`/api/reservations/{id}/cancel`)에 대해 검증하는 범위는 **8KiB 초과 본문 413 거부**와 **비어 있지 않은 본문 400 거부**까지다. 실제 예약 생성·멱등 키 재전송·롤백은 5단계, 예약 단건 조회·취소 상태 전이·수량 복구·소유자 검증은 6단계, Redis 요청 제한(429·503)은 8단계 범위다.
- 구체적인 클래스·메서드 시그니처(`SecurityConfig`, `LocalIdentityResolver`, `ApiExceptionHandler`, `RequestBodyLimitFilter`, `ClockConfig`, `ResourceController`, `ResourceService`, `ResourceApiIT`, `SecurityIT`)와 Jackson 엄격 설정·필터 등록 방식·실행 절차는 후속 `$speckit-plan`에서 계획서 4단계와 실제 저장소 구조에 맞춰 설계한다.
