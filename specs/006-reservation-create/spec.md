# 기능 명세: 예약 생성·성공한 키 재현·실패 복구

**작업 브랜치**: `feature/reservation-create` (명세 작성: `docs/reservation-create-spec`)

**작성일**: 2026-10-19

**상태**: 명세 품질 검토 및5단계 구현·실행 인수 완료. 증거는 docs/test-evidence.md를 따른다.

**입력**: 로컬 개발 계획 7절의 5단계(예약·성공한 키·롤백). 인증된 사용자의 한 개 예약, 성공한 생성 키의 결과 재현, 실패 시 수량·예약·키의 부분 반영 방지를 명세한다.

## 사용자 시나리오와 검증 *(필수)*

### 사용자 이야기 1 - 남은 수량 한 개 예약하기 (우선순위: P1)

인증된 사용자는 예약 대상과 생성 키를 지정해 한 개를 예약하고, 예약 식별자와 확정 결과를 받는다. 수량이 없거나 대상이 존재하지 않으면 서로 다른 실패 이유를 확인한다.

**우선순위 이유**: 실제 예약과 남은 수량을 일치시키는 기본 사용자 흐름이다.

**독립 검증**: 최초 수량 1인 대상에 한 번 예약하고 반환된 예약 정보·위치 정보, 남은 수량, 확정 예약 수를 대조한다. 수량 0인 대상과 없는 대상도 별도로 요청한다.

**인수 시나리오**:

1. **조건** 수량 1인 대상과 사용하지 않은 생성 키가 있을 때, **행동** 인증된 사용자가 예약하면, **결과** 새 예약의 식별자·대상 식별자·확정 상태·생성 시각과 해당 예약의 위치 정보를 받는다. 최초 생성임을 표시하고 남은 수량은 0, 확정 예약은 1개가 된다.
2. **조건** 수량이 0인 대상과 사용하지 않은 키가 있을 때, **행동** 예약하면, **결과** 품절로 거부하고 예약·성공 키를 남기지 않는다.
3. **조건** 존재하지 않는 대상과 사용하지 않은 키가 있을 때, **행동** 예약하면, **결과** 대상 없음으로 거부하고 예약·성공 키를 남기지 않는다.
4. **조건** 같은 사용자에게 수량이 충분한 대상의 기존 예약이 있을 때, **행동** 다른 유효한 키로 예약하면, **결과** 별도 예약이 하나 생성되고 수량도 한 개만 더 줄어든다.

---

### 사용자 이야기 2 - 같은 요청을 안심하고 다시 보내기 (우선순위: P1)

사용자는 응답을 받았는지 확신할 수 없을 때 같은 키로 다시 요청해 최초 성공 결과를 확인한다. 키를 다른 대상에 잘못 사용하면 충돌을 확인하며, 다른 사용자의 키와는 간섭하지 않는다.

**우선순위 이유**: 재전송으로 수량이 중복 소비되거나 예약이 추가되는 일을 방지해야 한다.

**독립 검증**: 준비된 성공 예약을 기준으로 같은 사용자·키·대상 재요청, 다른 대상 요청, 다른 사용자의 같은 키 요청을 각각 비교한다.

**인수 시나리오**:

1. **조건** 마지막 한 개를 예약해 남은 수량이 0일 때, **행동** 같은 사용자·키·대상으로 다시 요청하면, **결과** 품절 대신 최초 성공의 예약 식별자·대상·확정 상태·생성 시각·위치 정보·성공 구분을 재현하고 재현된 응답임을 표시한다. 예약 수와 남은 수량은 바뀌지 않는다.
2. **조건** 사용자가 키 하나로 대상 A 예약을 성공했을 때, **행동** 같은 키로 대상 B를 요청하면, **결과** 키 충돌로 거부하고 A·B 모두 수량과 예약을 변경하지 않는다. B가 없거나 품절이어도 기존 키의 대상 불일치를 우선 판별한다.
3. **조건** 사용자 A가 키 하나를 사용했고 다른 사용자 B에게 예약 가능한 수량이 있을 때, **행동** B가 동일한 키를 사용하면, **결과** A와 독립된 새 예약을 생성한다.
4. **조건** 같은 대상 식별자를 표기한 유효한 요청들이 있을 때, **행동** 같은 사용자·키로 JSON 공백 또는 UUID 영문 대소문자 표기만 바꾸어 재전송하면, **결과** 같은 대상으로 판단해 최초 결과를 재현한다.
5. **조건** 최초 생성 시각에 마이크로초보다 세밀한 부분이 포함될 때, **행동** 생성 후 같은 요청을 다시 보내면, **결과** 최초·재요청 시각이 저장된 UTC 마이크로초 정밀도 값과 정확히 같으며 다른 생성 정보도 동일하다.
6. **조건** 과거 성공 예약이 이미 취소된 상태로 준비돼 있을 때, **행동** 같은 사용자·키·대상으로 생성 재요청을 하면, **결과** 최초의 확정 생성 결과를 재현한다. 취소 상태·취소 시각·남은 수량을 변경하거나 예약을 재활성화하지 않는다. 취소 실행과 현재 상태 조회 기능은 후속 단계다.

### 사용자 이야기 3 - 실패 후 같은 키로 다시 시도하기 (우선순위: P1)

사용자는 예약 처리가 실패해도 수량만 소비되거나 성공하지 않은 키가 막히는 일을 겪지 않아야 한다. 장애가 해소되면 같은 키로 다시 예약할 수 있어야 한다.

**우선순위 이유**: 부분 반영은 실제 예약 없이 수량을 잃게 하고 재시도도 막는다.

**독립 검증**: 수량 감소 이후 예약 저장이 실패하는 조건을 만들고, 처리 종료 후 수량·예약·성공 키를 확인한다. 실패 원인을 제거한 뒤 같은 키로 다시 요청한다.

**인수 시나리오**:

1. **조건** 수량 1인 대상과 새 키가 있을 때, **행동** 수량 감소 이후 예약 저장을 의도적으로 실패시키면, **결과** 성공 결과를 반환하지 않고 수량은 1, 예약 수는 0, 해당 사용자·키의 성공 기록은 없음으로 복구된다.
2. **조건** 앞선 저장 실패 원인이 제거됐을 때, **행동** 같은 사용자·키·대상으로 재시도하면, **결과** 새 예약 하나를 성공시키며 수량은 0이 된다. 실패한 요청의 재현으로 표시하지 않는다.
3. **조건** 다른 요청이 같은 사용자·키의 예약을 먼저 성공시켰을 때, **행동** 뒤따른 처리가 동일 사용자·키의 중복으로 실패하면, **결과** 그 처리의 수량 변경을 모두 되돌린 뒤 기존 성공 결과를 기준으로 같은 대상은 재현, 다른 대상은 키 충돌로 판별한다.
4. **조건** 예약 식별자 중복, 없는 대상 참조, 연결 실패 등 사용자·키 중복 이외의 문제가 발생할 때, **행동** 실패 원인을 판별하면, **결과** 기존 성공의 재현으로 오인하지 않는다. 의존성 장애·정해진 대기 시간 초과는 일시적 이용 불가로 처리하고, 분류하지 못한 내부 결함은 내부 오류로 드러내며 부분 반영은 남기지 않는다.
5. **조건** 품절·입력 오류·일시적 이용 불가로 생성이 실패했고 키에 성공 이력이 없을 때, **행동** 원인을 해소하거나 요청을 바로잡아 같은 키로 다시 요청하면, **결과** 이전 실패 때문에 차단하지 않고 현재 조건에 따라 새 성공이 가능하다. 수량 변경 기능을 새로 만들지 않고 독립된 예약 가능 대상으로도 확인할 수 있다.

---

### 사용자 이야기 4 - 잘못된 요청을 데이터 변경 없이 거부하기 (우선순위: P2)

사용자는 인증 실패·입력 오류·품절·대상 없음·키 충돌을 구분해 요청을 바로잡을 수 있어야 한다.

**우선순위 이유**: 실패 이유를 명확히 전달하고 잘못된 입력이 수량과 사용자 식별을 훼손하지 않게 한다.

**독립 검증**: 정상 예약 요청에서 자격 증명·키·본문을 하나씩 바꾸어 거부 사유와 데이터 무변경을 확인한다.

**인수 시나리오**:

1. **조건** 자격 증명이 없거나 잘못됐을 때, **행동** 상한 이하 예약 요청을 보내면, **결과** 인증 실패로 거부하고 예약·수량·키를 변경하지 않는다.
2. **조건** 키가 누락·빈 값·65자 이상이거나 공백·비ASCII 문자·허용하지 않은 기호를 포함할 때, **행동** 예약하면, **결과** 입력 오류로 거부한다. 키를 자르거나 공백 제거·대소문자 변환해 허용하지 않는다. 허용 문자로만 구성한 1자와 64자 키는 허용한다.
3. **조건** 대상 식별자가 누락·null·잘못된 형식이거나 본문이 잘못된 JSON, 중복 필드, 미정의 필드(수량·사용자 식별자 포함)를 가질 때, **행동** 예약하면, **결과** 입력 오류로 거부하고 데이터는 변경하지 않는다.
4. **조건** 정상 인증에 임의 사용자 식별 헤더가 붙을 때, **행동** 유효한 예약을 요청하면, **결과** 인증된 사용자 소유로만 생성한다. 대소문자만 다른 유효 키는 별개로 취급한다.
5. **조건** 본문이 8,192바이트를 초과하거나 지원하지 않는 형식일 때, **행동** 예약 요청을 보내면, **결과** 기존 본문 상한·미디어 형식 거부 규칙을 적용한다. 초과 본문은 인증보다 먼저 차단하며, 상한 이하 미인증 요청은 인증 실패로 거부한다.
6. **조건** 정의된 거부 사유가 발생했을 때, **행동** 응답을 확인하면, **결과** 기존 공통 오류 계약으로 사유를 구분할 수 있고 비밀번호·SQL·스택 트레이스는 노출하지 않는다.

### 경계 사례

- 마지막 수량을 이미 소비한 성공 키의 재요청과, 성공 이력이 없는 키의 품절 요청을 구분한다.
- 동일 사용자·키는 대상 전체에서 공유하며, 다른 사용자 또는 대소문자가 다른 키는 별개다.
- 수량 감소가 불가능한 시점에 앞선 요청의 성공 이력이 생겼다면, 새로 확인한 이력에 따라 재현·충돌을 판별한다.
- 중복 판별 이후 기존 성공 기록을 찾을 수 없으면 내부 불변식 위반이다. 성공을 꾸며내거나 무제한 재시도하지 않는다.
- 최초 결과를 재현한다는 것은 필드 값의 일치이며, JSON 공백·필드 순서까지 같은 바이트를 보장하는 것은 아니다.
- 커밋 후 응답을 받지 못해도 성공 키는 유지된다. 전체 연결 중단·응답 유실 장애 시험은 후속 검증이며 이번 명세 품질 검토로 완료 처리하지 않는다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 인증된 사용자는 대상과 유효한 생성 키로 정확히 한 개를 예약할 수 있어야 한다. 사용자 식별은 인증 결과만 따르고 요청 수량·사용자 지정은 허용하지 않아야 한다. 이야기 1.1·4.3~4.4로 검증한다.
- **FR-002**: 새 예약은 고유 식별자·대상·확정 상태·UTC 생성 시각·위치 정보를 반환하고 최초 생성과 재현 여부를 구분해야 한다. 기존 성공 응답 계약을 유지해야 한다. 이야기 1.1·2.1로 검증한다.
- **FR-003**: 모든 처리 종료 후 대상별 남은 수량은 0 이상 최초 수량 이하이고, 남은 수량과 확정 예약 수의 합은 최초 수량과 같아야 한다. 성공은 한 개를 소비하며 거부·실패·재현은 추가 소비가 없어야 한다. 이야기 1~4의 상태 대조로 검증한다.
- **FR-004**: 성공 이력이 없는 키는 대상 없음과 품절을 구별해 거부해야 한다. 성공 키가 있으면 현재 수량·대상 존재 확인보다 재현 또는 대상 불일치 판별을 우선해야 한다. 이야기 1.2~1.3·2.1~2.2로 검증한다.
- **FR-005**: 생성 키는 ASCII 영문·숫자·밑줄·하이픈 1~64자로 제한하고 원문 그대로 비교해야 한다. 사용자와 키의 조합당 예약은 최대 하나이며 다른 키로 추가 예약을 허용해야 한다. 이야기 1.4·2.3·4.2·4.4로 검증한다.
- **FR-006**: 같은 사용자·키·대상은 최초 성공 구분·위치 정보와 생성 정보 전체를 재현하고 추가 예약·수량 변경이 없어야 한다. 대상 동일성은 UUID 값으로 판단해야 한다. 이야기 2.1·2.4~2.5로 검증한다.
- **FR-007**: 같은 사용자·키로 다른 대상을 요청하면 키 충돌로 거부하고 두 대상 모두 해당 실패 요청으로 수량이 소비되지 않아야 한다. 이야기 2.2·3.3으로 검증한다.
- **FR-008**: 성공한 예약은 키의 지속적인 기록이며 보존 기간 만료로 삭제하지 않아야 한다. 취소된 예약도 최초 확정 생성 정보를 재현하고 현재 상태는 바꾸지 않아야 한다. 이야기 2.6으로 상태별 재현을 검증하고 보존 정책은 기존 계약과 대조한다.
- **FR-009**: 최초·재현 생성 시각은 실제 저장된 UTC 마이크로초 값과 정확히 일치해야 한다. 더 세밀한 시각을 입력한 경우도 동일해야 한다. 이야기 2.5로 검증한다.
- **FR-010**: 수량 소비와 예약·성공 키 기록은 모두 반영되거나 모두 반영되지 않아야 한다. 실패한 생성 키를 보존하지 않으며 원인 제거 후 같은 키의 재시도를 허용해야 한다. 이야기 3.1~3.2·3.5로 검증한다.
- **FR-011**: 사용자·키 중복으로 실패한 처리의 변경을 모두 취소한 후에만 기존 성공 기록으로 재현·충돌을 판별해야 한다. 다른 식별자 중복·참조 오류·연결 장애를 이 중복으로 오인하지 않아야 하며, 기존 성공이 없으면 내부 오류로 탐지해야 한다. 이야기 3.3~3.4 및 경계 사례로 검증한다.
- **FR-012**: 키·본문·인증·크기·형식 오류는 기존 계약에 맞게 거부하고, 정의된 오류는 공통 형식으로 전달하며 내부 민감 정보를 숨겨야 한다. 분류하지 못한 내부 결함을 품절·키 충돌·의존성 장애로 숨기지 않아야 한다. 이야기 3.4·4.1~4.6으로 검증한다.

### 핵심 개체

- **예약 대상**: 고유 식별자, 최초 수량, 남은 수량을 가진다. 예약 성공 시 남은 수량 한 개를 소비한다.
- **예약**: 고유 식별자, 대상 식별자, 인증 사용자 식별자, 생성 키, 상태, 생성 시각, 취소 시각을 가진다. 대상·사용자·키·생성 시각은 생성 후 불변이다.
- **성공한 생성 키**: 사용자별 예약의 지속적인 식별 기준이다. 실패 기록은 아니며 대상이 달라도 동일 사용자의 키 범위는 공유한다.
- **최초 생성 결과**: 예약 식별자·대상·확정 상태·생성 시각·위치 정보로 구성된다. 현재 예약 상태와 별개로 재현할 수 있다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 최초 수량 1에서 한 번 성공하면 예약 1개·남은 수량 0이며, 같은 요청을 두 번 보내도 고유 예약은 1개다. 두 결과의 생성 정보와 위치 정보는 100% 같고 최초·재현 구분만 달라진다.
- **SC-002**: 같은 사용자·키의 다른 대상 요청, 다른 사용자·같은 키, 같은 사용자·다른 키 사례가 모두 정해진 충돌 또는 독립 예약 결과와 일치하고 의도하지 않은 수량 감소는 0개다.
- **SC-003**: 수량 감소 후 저장 실패 사례에서 남은 수량·예약 수·성공 키가 모두 요청 전과 같고, 원인 제거 후 같은 키로 고유 예약 1개를 성공시킨다. 품절·입력 오류·일시적 이용 불가 이력에 의한 키 차단은 0건이다.
- **SC-004**: 세밀한 시각 입력과 취소된 기존 예약의 재요청에서도 최초 생성 정보의 불일치는 0건이며, 재요청에 의한 재활성화·추가 수량 소비는 0건이다.
- **SC-005**: 이야기 4의 경계·잘못된 요청은 모두 정해진 사유로 거부하고, 거부에 의한 예약·성공 키 생성은 0건이다. 사용자는 공통 오류의 구분 정보만으로 입력 오류·인증 실패·대상 없음·품절·키 충돌·일시적 이용 불가를 판별할 수 있다.

## 전제와 의존성

- 기준은 [로컬 개발 계획](<../../한정 수량 예약 백엔드 로컬 개발 계획.md>) 2~5절·7절 5단계, [예약 도메인](../../knowledge/domain/reservation.md), [대상 도메인](../../knowledge/domain/resource.md), [인증 도메인](../../knowledge/domain/security.md), [트랜잭션 규칙](../../knowledge/rules/domain-and-transactions.md), [API·보안 규칙](../../knowledge/rules/api-and-security.md), [기존 외부 계약](../../docs/openapi.yaml)이다. 기존 상태 코드·오류 코드·필드·헤더 계약을 바꾸지 않는다. 이 명세는 사용자 관점의 기대 결과이며 구체적인 통신 계약은 연결된 기존 계약을 따른다.
- 2단계 저장 기반·성공 키 조회, 3단계 생성 키 규칙, 4단계 인증 사용자 식별·공통 입력 및 오류 처리를 재사용한다. 계획 당시 미구현이던 생성 처리·쓰기 경계와 선택된 세 통합 검증을5단계에서 구현했다. 관련 과거 실행 기록은 [검증 증거](../../docs/test-evidence.md)를 참조하며 이번 작업에서 기능 검증을 재실행한 것으로 보지 않는다.
- 범위는 5단계 예약 생성·성공 키 재현·실패 복구다. 취소된 예약은 준비된 상태로 재현만 확인한다. 예약 단건 조회·취소 기능은 6단계, 실제 동시 요청 반복 검증은 7단계, 요청 제한 및 관련 장애 검증은 8단계, 자동 계약·속성·변이·부하는 후속이다. 경쟁 시 지킬 결과는 유지하되 이번 단계의 완료를 실제 경쟁 검증 완료로 표현하지 않는다.
- 요청 제한은 후속 연동 시에도 인증 뒤·입력 검증과 예약 처리 앞에 적용돼야 하며 재요청도 차단될 수 있다. 이번 단계에 제한 기능이 구현됐다고 가정하거나 완성 버전에서 제외하지 않는다.
- localhost CLI/API 클라이언트 범위를 유지한다. 결제·만료·목록·수량 변경·대상 삭제·외부 공개는 추가하지 않는다.
- 선택 범위의 제공 인터페이스·트랜잭션 경계·중복 오류 분류·테스트 이름 및 실행 명령은 후속 `$speckit-plan`에서 계획서 5.2절과 7절 5단계에 따라 구체화한다. 명세 품질 검토를 구현·테스트 통과로 취급하지 않는다.
