**상태**: 초안 — 명세 품질 검토 완료, 환경 구성·도구 실행 검증 전

## 확인 사항

### 2026-10-13 세션

- 질문: 1단계에서 서비스 종료·재시작 후 데이터 보존을 확인할 대상은 어디까지인가? → 답변: A. PostgreSQL 데이터 보존만 필수로 검증한다. Redis는 저장·조회 연동을 확인하며 재시작 후 키 보존은 인수 범위에서 제외한다.

## 사용자 시나리오와 검증 *(필수)*

### 사용자 스토리 1 - 기존 작업 공간에서 실행 준비 상태를 확인한다 (우선순위: P1)

개발자는 기존 프로젝트를 보존하면서 필요한 실행 도구와 로컬 의존 서비스를 준비하고, 설치된 것·부족한 것·실행 확인한 것을 구분하고 싶다. 기능 구현 전에 환경 문제를 분리할 수 있어야 한다.

**우선순위 이유**: 작업 공간을 잘못 선택하거나 기존 구성을 교체하면 이후 검증의 근거와 기존 작업을 잃을 수 있다.

**독립 검증**: 작업 공간, 환경 목록, 로컬 기동·종료와 PostgreSQL 데이터 보존을 확인한다. 예약 기능 없이도 재현 가능한 개발 환경을 제공한다.

**인수 시나리오**:

1. **조건** 기존 프로젝트와 독립 저장소가 있을 때, **행동** 준비 상태를 점검하면, **결과** 저장소 최상위와 애플리케이션 위치를 확인하고 기존 파일·이력을 보존한다. 새 저장소를 중첩 생성하지 않는다. (FR-001)
2. **조건** 일부 도구가 이미 설치되어 있을 때, **행동** 환경 목록을 작성하면, **결과** 도구별 실제 버전, CPU 아키텍처, 컨테이너 실행 메모리 설정과 부족한 항목을 기록하고 부족한 항목만 준비한다. 부하 도구는 버전 확인까지 포함한다. (FR-002)
3. **조건** 필요한 로컬 설정과 비밀값을 별도로 제공했을 때, **행동** 서비스와 애플리케이션을 시작하면, **결과** 문서화된 로컬 주소에서 실행되고 시작 실패는 실패로 기록한다. 기본 종료 후 다시 시작해도 PostgreSQL에 저장한 시험용 개발 데이터가 유지된다. (FR-003, FR-004)
4. **조건** 의존 서비스가 준비되지 않았을 때, **행동** 기동 또는 연동 검증을 실행하면, **결과** 환경 미준비를 명시하고 성공으로 처리하지 않는다. (FR-010)

---

### 사용자 스토리 2 - 기본 검증과 실제 저장소 연동을 실행한다 (우선순위: P1)

개발자는 기본 검증이 실제 발견·실행되고, 격리된 실제 저장소에서 값을 저장한 뒤 같은 값을 읽는지 확인하고 싶다. 기존의 빈 기동 검사만으로 연동 준비를 완료했다고 판단하지 않는다.

**우선순위 이유**: 이후 수량·예약 정합성을 검증하려면 기본 실행과 실제 저장소 연동이 먼저 확인되어야 한다.

**독립 검증**: 작은 값 하나를 검증하는 기본 사례와 두 저장소의 저장·조회 사례를 각각 실행한다. 실제 업무 테이블과 API 없이도 연동 기반의 준비 여부를 판정할 수 있다.

**인수 시나리오**:

1. **조건** 기본 검증 사례가 존재할 때, **행동** 기본 검증을 실행하면, **결과** 적어도 1건을 발견·실행하고 실패·건너뜀 없이 통과한다. 지정 사례만 실행하는 방법도 확인된다. (FR-005, FR-009)
2. **조건** 격리된 실제 관계형 저장소가 준비되었을 때, **행동** 시험 값을 삽입하고 조회하면, **결과** 삽입한 값과 조회값이 일치하고 개발용 데이터는 변하지 않는다. (FR-006)
3. **조건** 격리된 실제 키·값 저장소가 준비되었을 때, **행동** 시험 값을 저장하고 조회하면, **결과** 저장한 값과 조회값이 일치하고 개발용 키는 변하지 않는다. (FR-006)
4. **조건** 의도적으로 기대값을 깨뜨린 사례가 있을 때, **행동** 해당 검증을 실행하면, **결과** 실패가 실행 결과와 비성공 종료 코드에 반영된다. 결함을 원복한 뒤 같은 사례가 통과한다. (FR-009, FR-011)

---

### 사용자 스토리 3 - 심화 검증이 잘못된 동작을 탐지하는지 확인한다 (우선순위: P2)

개발자는 도구를 설치했다는 사실에 그치지 않고, 작은 잘못된 동작과 계약 위반을 실제로 탐지하고 재현할 수 있는지 확인하고 싶다.

**우선순위 이유**: 결함을 찾지 못하는 도구나 실행되지 않는 검증을 뒤늦게 발견하면 이미 작성한 기능 검증을 다시 구성해야 한다.

**독립 검증**: 작은 순수 규칙, 0~100 정수의 저장·조회 사례, 최소 요청·응답 계약을 각각 시험한다. 서로 다른 도구의 성공으로 다른 검증의 실패를 대신할 수 없다.

**인수 시나리오**:

1. **조건** 정상 규칙과 이를 검사하는 사례가 있을 때, **행동** 규칙을 자동으로 변형해 검사하면, **결과** 변형이 적어도 1개 생성되고 적어도 1개가 탐지된다. 변형 0개·미검사·도구 예외는 성공이 아니다. 남은 미탐지 결과가 있으면 이유를 기록한다. (FR-007)
2. **조건** 0~100 정수의 저장·조회 속성을 확인하는 사례가 있을 때, **행동** 정상 동작을 검사하면, **결과** 0과 100을 포함한 범위 내 값이 일치한다. 경계값 처리를 고의로 깨뜨리면 실패하고 축소된 실패 입력과 재현 식별값을 얻는다. 같은 재현 식별값으로 실패가 다시 발생하며 원복 후 통과한다. (FR-008, FR-011)
3. **조건** 필수 식별자를 선언한 최소 계약과 시험용 요청·응답이 있을 때, **행동** 정상 응답과 필수 `id`를 제거한 응답을 검사하면, **결과** 정상 응답은 통과하고 훼손한 응답은 실패한다. 요청·응답을 검증기에 전달하는 경로도 확인한다. (FR-012)
4. **조건** 이전 단계에서 확정한 계약 문서가 있을 때, **행동** 같은 검증 도구로 문서를 읽으면, **결과** 문법·참조를 처리할 수 있는지 실제 결과를 기록한다. 이것을 업무 API의 실제 응답 준수 증거로 간주하지 않는다. (FR-012)

---

### 사용자 스토리 4 - 실행 범위와 근거를 보고 다음 단계로 진행한다 (우선순위: P2)

개발자는 어떤 검증이 실행되었는지와 어떤 조합이 실제로 동작했는지를 기록만으로 확인하고, 동일한 준비 절차를 다시 수행하고 싶다.

**우선순위 이유**: 근거 없는 호환성 주장과 부분 실행을 전체 성공으로 오해하는 일을 막아야 한다.

**독립 검증**: 실행 안내와 결과 기록을 대조해 범위별 사례 수·종료 코드·실패 재현·미검증 항목을 확인한다. 다른 기능을 추가하지 않고도 기록의 완전성을 검사할 수 있다.

**인수 시나리오**:

1. **조건** 기본·연동·계약·속성·전체 심화·변형 검증이 준비되었을 때, **행동** 각 실행 범위를 선택하면, **결과** 문서와 실제 발견 대상이 일치한다. 일반 연동 실행에서는 계약·속성을 제외하고 각 포함 실행과 전체 심화 실행에서 의도한 사례가 발견된다. (FR-009)
2. **조건** 성공과 고의 실패를 실행했을 때, **행동** 결과를 기록하면, **결과** 명령·종료 코드·실행 수·환경 버전·실패 재현값·원복 결과를 연결해 확인할 수 있다. 미실행 항목은 미검증으로 남긴다. (FR-013)
3. **조건** 필요한 검증이 모두 통과하고 고의 결함이 원복되었을 때, **행동** 준비 완료를 판정하면, **결과** 실행 확인한 조합만 호환 확인으로 기록하고 관련 변경을 검토 가능한 로컬 커밋으로 남긴다. 하나라도 실패·누락되면 해당 항목과 원인을 기록하고 단계 완료로 표시하지 않는다. (FR-010, FR-014)

### 경계 사례

- 저장소가 이미 준비된 경우 새 폴더·중첩 저장소·초기 골격을 중복 생성하지 않는다.
- 컨테이너 실행 중단, 이미지 취득 실패, 포트 충돌, 비밀값 누락은 환경 실패로 드러나야 한다.
- 검증 이름·태그·엔진 설정 오류로 사례 0건이 발견되거나 대상 사례가 건너뛰어지면 성공으로 처리하지 않는다.
- 기본 실행이 연동·심화 검증을 포함한다고 추정하거나 한 종류의 성공으로 다른 종류를 완료 표시하지 않는다.
- 통합 검증은 개발용 주소로 접속하지 않는다. 임의 포트에서 격리된 데이터를 사용한다.
- 정수 0과 100의 경계는 반드시 검증한다. 고의 결함은 컴파일 오류가 아니라 값 불일치로 탐지되어야 한다.
- 자동 변형 0개, 미검사 결과, 도구 예외는 호환성 확인이 아니다.
- 고의 실패가 로그에만 나타나고 종료 코드가 성공이면 실행 계약 위반이다.
- 재현 식별값만 있고 실패 입력 축소가 없거나 그 식별값으로 실패가 재현되지 않으면 속성 도구 검증이 미완료다.
- 최소 계약 검증 성공과 기존 계약 문서 읽기 성공은 실제 업무 API 계약 준수를 입증하지 않는다.
- 기존 기동 검사에 실행 환경이 필요하면 기본 순수 검증과 분류를 구분해야 한다.
- 고의 결함 원복 누락, 비밀값의 기록·커밋 포함, 기본 종료 과정의 PostgreSQL 개발 데이터 삭제는 완료를 차단한다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 개발자는 기존 작업 공간과 독립 저장소를 확인하고 기존 애플리케이션·빌드 방식·이력을 보존할 수 있어야 한다. 인수 기준: 스토리 1-1.
- **FR-002**: 필요한 실행·빌드·컨테이너·부하 도구의 존재와 실제 버전, CPU 아키텍처와 컨테이너 실행 메모리 설정을 기록해야 한다. 확인 불가 항목은 이유를 적고 필요한 도구만 보완해야 한다. 인수 기준: 스토리 1-2.
- **FR-003**: 로컬 의존 서비스와 애플리케이션의 시작·정상 종료 절차를 제공하고 최소 기동을 확인해야 한다. PostgreSQL 개발 데이터는 기본 종료·재시작 후 유지해야 한다. Redis는 저장·조회 연동을 확인하며 재시작 후 키 보존은 인수 범위에서 제외한다. 인수 기준: 스토리 1-3.
- **FR-004**: 비밀값은 외부 설정으로 제공하고 공유 예시에는 변수명만 남겨야 한다. 실행 환경의 문자 인코딩·시각 기준·로컬 접근 범위는 기존 규칙과 일치해야 한다. 인수 기준: 스토리 1-3의 설정·기동 확인과 비밀값·공유 파일 검토.
- **FR-005**: 기본 검증은 실행 환경 기동이 필요 없는 작은 사례를 적어도 1건 실제 발견·실행해야 한다. 인수 기준: 스토리 2-1.
- **FR-006**: 격리된 실제 관계형 저장소의 삽입·조회와 실제 키·값 저장소의 저장·조회를 각각 검증해야 한다. 개발 데이터에 접속하거나 대체 저장소로 결과를 대신해서는 안 된다. 시험 migration 실패는 상태·정리 책임·원인 수정·새 격리 DB 재개 조건을 기록해야 한다. 개발 보존 표식 준비 중단은 commit 여부와 본인 표식의 같은 UUID·기대값을 확인하고 기존 개발 데이터를 보존한 채 전체 보존 시험을 재개해야 한다. 인수 기준: 스토리 2-2·2-3 및 실행 계약의 중단·실패 후 정리와 재개.
- **FR-007**: 작은 순수 규칙에서 자동 변형을 적어도 1개 생성하고 적어도 1개를 탐지해야 한다. 생성·탐지·미탐지·미검사 수와 남은 결과의 이유를 기록해야 한다. 인수 기준: 스토리 3-1.
- **FR-008**: 속성 검증은 0~100 정수의 저장·조회 일치와 양 끝값을 검사해야 한다. 경계 결함을 탐지하고 실패 입력 축소·재현 식별값을 통한 재현을 보여야 한다. 인수 기준: 스토리 3-2.
- **FR-009**: 기본, 기본+일반 연동, 지정 기본·연동 사례, 계약 포함, 속성 포함, 전체 심화, 자동 변형의 실행 범위와 발견 규칙을 구분해야 한다. 계약 포함은 속성을, 속성 포함은 계약을 제외하고 전체 심화는 기본·모든 연동·계약·속성을 포함한다. 자동 변형은 별도 실행한다. 각 범위에서 대상 사례 수가 0이 아니어야 하며 고의 실패는 비성공 종료 코드에 반영되어야 한다. 인수 기준: 스토리 2-1·2-4·4-1.
- **FR-010**: 실패·건너뜀·0건 실행·변형 0개·미검사·도구 예외를 성공으로 취급해서는 안 된다. 실패는 코드, 의존성, 컨테이너 실행 환경으로 원인을 구분하고 반복 실행·제외·기대값 변경으로 숨겨서는 안 된다. 인수 기준: 스토리 1-4·3-1·4-3.
- **FR-011**: 실패 탐지용 고의 결함은 정상 동작 → 의도한 실패 → 재현 → 원복 후 정상 결과를 남겨야 한다. 결함과 임시 변경이 남은 상태로 완료를 선언해서는 안 된다. 인수 기준: 스토리 2-4·3-2와 최종 변경 검토.
- **FR-012**: 최소 계약의 정상 요청·응답 검증 경로와 필수 `id` 누락 응답 거부를 확인해야 한다. 기존 고정 계약 문서도 도구로 읽어 문법·참조 처리 결과를 기록해야 한다. 문서 생성이나 읽기만으로 실제 업무 응답 검증을 대신해서는 안 된다. 인수 기준: 스토리 3-3·3-4.
- **FR-013**: 실제 버전·이미지 식별값·해석된 의존성 조합과 선택 이유, 실행 명령·종료 코드·사례 수·재현 식별값·축소 입력·원복 결과·미검증 범위를 기존 기록 체계에 남겨야 한다. 후보·채택·실행 확인을 구분해야 한다. 인수 기준: 스토리 4-2와 기록 전수 대조.
- **FR-014**: 전체 필수 최소 검증이 통과한 뒤에만 1단계 완료와 실행 호환성을 표시해야 한다. 한 검증 대상씩 수행하고 검증된 변경을 목적별 로컬 커밋으로 남겨야 한다. 불필요한 확인용 예제는 후속 실제 검증으로 대체할 대상으로 명시해야 한다. 인수 기준: 스토리 4-3.

### 핵심 개체

- **환경 목록**: 도구·버전·아키텍처·메모리 설정·설치 및 실행 확인 상태를 담는 준비 기록.
- **검증 사례**: 실행 범위·입력·기대 결과·실제 결과·발견 여부·실행 수를 가진 최소 확인 단위.
- **실패 재현 기록**: 고의 결함·실패 원인·재현 식별값·축소 입력·원복 결과를 연결하는 증거.
- **도구 조합 기록**: 버전·이미지·해석된 의존성과 실행 결과를 연결해 후보와 호환 확인을 구분하는 기록.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 개발자는 준비 목록의 모든 필수 항목에 설치·버전·실행 확인 또는 확인 불가 이유를 남기고, 로컬 시작 → 종료 → 재시작 1회를 수행해 관계형 저장소에 저장한 시험용 개발 데이터 보존을 확인한다.
- **SC-002**: 기본 검증과 두 종류의 실제 저장소 연동 검증에서 각각 1건 이상의 사례가 실행되며, 정상 실행의 실패·건너뜀은 모두 0건이다.
- **SC-003**: 자동 변형은 생성 1개 이상·탐지 1개 이상이며, 속성 검증은 경계 결함 탐지·실패 입력 축소·동일 재현값 재실패·원복 후 통과의 네 가지 증거를 모두 제공한다.
- **SC-004**: 계약 검증은 정상 응답 1건 이상을 허용하고 필수 식별자가 없는 응답 1건 이상을 거부한다. 기존 계약 문서 읽기 결과도 1건 기록한다.
- **SC-005**: 정의한 실행 범위마다 대상·실행 수·종료 코드가 기록되며, 고의 실패의 비성공 종료와 원복 후 성공 종료를 확인한다. 사례 0건인 필수 범위와 원복되지 않은 고의 결함은 모두 0건이다.
- **SC-006**: 개발자는 실행 안내와 증거만으로 각 필수 검증의 성공 여부·실패 재현 방법·미검증 범위를 판정할 수 있다. 필수 항목의 근거 없는 호환 확인 표시는 0건이며, 다음 단계 진행 여부를 기록으로 설명할 수 있다.

## 가정과 의존성

- 기준은 [로컬 개발 계획](<../../한정 수량 예약 백엔드 로컬 개발 계획.md>) 2~5절, 6절의 검증 범위, 7절 1단계와 [지식 문서 안내](../../knowledge/README.md), 개발 헌법이다. 이번 작업은 명세 작성이며 실행 완료를 뜻하지 않는다.
- 0단계의 문서·학습 인수는 완료되었다. 기존 [고정 계약](../../docs/openapi.yaml)과 [결정 기록](../../docs/decisions.md)을 입력으로 사용한다. 자동 계약 검증과 기능 실행은 아직 미실시다.
- 현재 독립 저장소는 프로젝트 루트, 애플리케이션은 `backend/`, 기존 빌드는 Gradle Wrapper, 기본 패키지는 `com.limitedbooking.backend`다. 사용자 지침에 따라 이를 유지한다. 계획서의 새 저장소·Maven·다른 경로는 기존 준비 상태와 대조하며 자동 교체하지 않는다. 구체적인 실행 태스크와 의존성 선택은 다음 계획에서 정한다.
- 사용자가 지정한 기술 제약은 Java 25·preview 제외, 기존 Spring Boot 골격, PostgreSQL 18.x·Redis·Flyway와 실제 컨테이너 연동, Jupiter, 순수 규칙의 PIT다. Property와 계약 검증기의 후보는 최소 실행 후 선택한다. 이 목록은 구현 방법을 새로 설계한 것이 아니라 기존 문서의 제약을 참조한 것이다.
- 현재 기본 starter·테스트 starter와 기동 검사만 존재한다. 업무 API·SQL·마이그레이션·연동·심화 검증이 갖춰졌다고 가정하지 않는다. 기존 기동 검사의 분류는 순수 기본 검증 계약에 맞게 계획 단계에서 정리한다.
- 로컬 서비스의 주소·UTF-8/UTC·비밀값 주입·데이터 보존과 테스트의 동적 접속값·격리는 [환경 규칙](../../knowledge/rules/environment-and-records.md)을 따른다. 개발자는 컨테이너 실행 환경과 필요한 의존성을 취득할 수 있어야 하며 접근 실패는 미검증으로 기록한다.
- 버전은 `docs/versions.md`, 선택은 `docs/decisions.md`, 실행 증거는 `docs/test-evidence.md`, 재현 안내는 README에 기록할 예정이다. 없는 파일·명령을 존재하거나 검증 완료한 것으로 기록하지 않는다.
- 범위는 환경과 도구의 최소 실행·실패 탐지다. 업무 스키마·예약 API·인증 구현·요청 제한 구현·경쟁 검증·업무 모델 속성 검증·부하 측정·외부 CI·배포는 포함하지 않는다. 최소 시험 데이터와 계약 fixture는 도구 확인용이며 업무 규칙을 추가하지 않는다.
- 계획서의 3~4시간은 추정이며 성공 기준의 시간 제한이 아니다. 실패가 생기면 원인을 분리하고 이 단계에서 도구 선택을 조정하되 기존 규칙과 기대값은 바꾸지 않는다.
