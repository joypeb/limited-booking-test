# 데이터 모델: 환경·최소 사례·실행 증거

## 범위

업무 대상·예약 테이블은 이번 단계에서 만들지 않는다. 아래 모델은 검증용 데이터와 문서 기록 형식이며 새로운 업무 도메인이 아니다. PostgreSQL 보존은 사용자 A 답변대로 필수이고 Redis 키 영속화는 인수 범위 밖이다.

## 환경 항목

- 식별: 도구 이름 + 실행 위치(호스트/컨테이너).
- 필드: 설치 여부, 명령, 실제 버전, CPU 아키텍처, Docker 메모리, 이미지 tag/digest, 확인일, 근거, 상태, 확인 불가 이유.
- 상태: 후보 → 설치/취득됨 → 버전 확인됨 → 해당 최소 사례 실행 확인됨. 실패/미실행은 이유와 함께 남긴다.
- 불변식: 문서 조사 상태를 실행 확인으로 바꾸지 않는다. 비밀번호·토큰·전체 환경 덤프는 기록하지 않는다.

## 도구 조합

- 식별: 검증일 + 대상 commit/작업 트리 상태 + 해석된 좌표 묶음.
- 필드: JDK, Gradle, Boot, Jupiter/Platform, Testcontainers, Flyway, driver, 이미지, PIT/plugin, Property, validator 좌표, 사례 결과 연결.
- 검증: BOM 관리 의존성과 명시적 고정 후보를 구분한다. 성공한 개별 도구를 전체 조합 성공으로 확대하지 않는다.

## 연동 시험 데이터

- PostgreSQL 테스트 전용 `toolchain_probe`: `id` UUID 기본키, `value` 정수. 테스트 전용 Flyway 위치의 migration으로 생성하고 적용 메타데이터·insert/select를 확인한다. 업무 migration 위치에 넣지 않는다.
- Compose 개발용 보존 표식: 시험 전용 schema `toolchain_smoke`의 probe 한 행에 UUID와 임의 정수를 저장한다. 정지·컨테이너 재생성 후 같은 UUID·값이 남는지 확인한다. 사용자 업무 데이터는 초기화하지 않는다. 검증 후 본인이 만든 행만 정리한다. 전체 SQL은 구현 단계에서 작성한다.
- Redis: 격리된 컨테이너에 `toolchain:smoke:<UUID>` 키와 시험 문자열. set/get 값 일치 후 해당 키만 삭제한다. 개발 제한 키를 지우지 않는다.
- 컨테이너 연결: host와 동적 mapped port는 시작 후 얻는다. 로컬 5432/6379를 IT 기본값으로 두지 않는다.

## 시험 데이터의 실패·중단 상태

- 격리 시험 DB: 준비 → migration 적용 중 → 적용 실패/상태 미확인 → 시험 자원 정리 확인 → 원인 수정 → 새 격리 DB에서 재검증. 실패 DB를 자동 repair·clean해 성공으로 바꾸지 않는다.
- 개발 보존 표식: 준비 트랜잭션 → commit 전 rollback 또는 commit 결과 미확인 → 새 연결에서 같은 UUID·기대값 대조 → commit 확인 → 전체 보존 시험 → 본인 표식 정리. 행 없음은 준비 미완료, 값 불일치/확인 불가는 재개 보류다.
- 실패 근거는 실행 UUID·대상 DB·시험 자원 식별값·적용 metadata/조회 가능 여부·commit/표식 확인·정리 담당·정리 결과·재개 조건·재개 결과를 포함한다. 비밀값은 제외한다.
- 정리 담당과 상세 조건은 [실행 계약의 중단·실패 후 정리와 재개](contracts/validation-contract.md#중단실패-후-정리와-재개)를 따른다. 개발 DB·volume·다른 시험 자원을 초기화하거나 삭제하지 않는다.

## 순수 정수 프로브

- 입력: 정수 0~100. 검증 대상은 입력을 보관·반환하는 작은 프로브이고 기대값은 원래 생성 입력이다.
- 매 입력마다 새 상태를 사용한다. 정상 0과100, 생성 입력 최소100회를 확인한다.
- 일시 결함: n>50에서 다른 값을 보관한다. 실패 입력 원본·축소 입력·seed·동일 seed 재현·원복 후 결과를 기록한다.
- 이 정수 범위는 업무 capacity 0~1000의 규칙이 아니다. 업무 속성 모델·경쟁·DB 검증을 대신하지 않는다.

## 계약 시험 데이터

- 계약: `contracts/toolchain-smoke.openapi.yaml`, 테스트 전용 GET 경로와 UUID id 필수 응답.
- 요청 기록: 실제 method/path/headers/body. 응답 기록: status/headers/body와 검증 오류.
- 정상: 200 JSON에 유효 UUID id. 음성: 200 JSON에서 id를 제거. 실제 전송한 응답으로 validator 판정을 비교한다.
- fixture는 테스트 코드에만 있으며 앱 업무 API에 노출하지 않는다. 정상·음성 요청은 같은 선언 경로를 별도 실행한다.

## 검증 결과와 재현 기록

- 실행 식별: 날짜·범위·명령·commit·작업 트리 상태.
- 필드: 종료 코드, 발견/실행/실패/skipped 수, 그룹별 사례 수, 속성 시도 수, seed/반례/축소값, 변이 생성/killed/survived/NO_COVERAGE 수, 보고서 위치, 원인, 원복 결과, 미검증, 다음 작업.
- 상태: 준비 → 정상 실행 확인 → 고의 실패 탐지 → 필요 시 재현·축소 확인 → 원복·정상 재검증 → 인수.
- 완료 조건: 필수 그룹0건·실패·skip·원복 누락은0, 필수 증거가 모두 존재한다. 단순 이전 XML·캐시 결과를 새 실행으로 기록하지 않는다.
- 기록 위치: 실제 실행은 루트 `docs/versions.md`, `docs/decisions.md`, `docs/test-evidence.md`. 이 설계 파일은 실행 로그를 대신하지 않는다.
