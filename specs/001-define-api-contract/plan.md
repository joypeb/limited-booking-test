## 요약

예약·취소·재시도의 기대 결과를 고정하고 다섯 API의 계약 초안과 세 설계 결정 기록을 작성하는 계획이다. 이번 명령은 조사·데이터 모델·계약 설계·검토 안내를 작성한다. 실제 산출물 `docs/openapi.yaml`, `docs/decisions.md`와 수동 검토 증거는 후속 작업에서 작성한다. 서비스 코드·SQL·마이그레이션·환경·테스트 도구를 구현하지 않는다.

이름 길이는 사용자 답변 A에 따라 공백 제거 후 유니코드 코드 포인트로 계산한다. 다른 규칙은 계획서 2~5절을 유지한다. [조사](research.md)와 [계약 설계](contracts/api-contract.md)를 사용해 최종 계약을 작성하고 [검토 안내](quickstart.md)로 판정한다.

## 기술 맥락

- **언어·버전**: 문서는 한국어 Markdown, 최종 계약은 YAML/OpenAPI 3.0.3. 기존 앱은 Java 25, Spring Boot 4.1.1, Gradle Wrapper 9.7.1이며 변경하지 않는다.
- **주요 의존성**: 계획서·지식 규칙·개발 헌법·공식 OpenAPI 3.0.3 사양. 계약 validator 선정·호환성 확인은 1단계에서 수행한다. 문서 검토에 앱이나 컨테이너는 필요하지 않다.
- **저장소**: 문서는 파일로 보관한다. 업무 데이터의 PostgreSQL 원본과 Redis 제한 책임은 설계 기준이며 이번 작업에서 접속하거나 구성하지 않는다.
- **검증**: 링크·필수 항목·계약 매트릭스·표의 수량식·키 유일성·실패 무변경을 수동 대조한다. 실제 HTTP·DB·Redis·자동 OpenAPI 검증은 미실행으로 기록한다.
- **대상 플랫폼**: localhost CLI/API 클라이언트. 브라우저·공개·클라우드 배포 제외.
- **프로젝트 유형**: 단일 백엔드의 문서·API 계약 확정 작업.
- **성능 목표**: 이번 문서 작업에는 처리량·지연 목표를 추가하지 않는다. 원 계획의 2~3시간은 학습 예상값이며 완료 보장이 아니다.
- **제약**: 다섯 작업, 기존 권한·DTO·오류·헤더 유지. 본문 8KiB, 생성/취소 합산 20회/60초, 실패 키 비보존, 성공 키 계속 보존. 운영 성능·가용성을 주장하지 않는다.
- **규모·범위**: 정상 5개 이상·비정상 10개 이상, 핵심 6행 흐름, 실패 키 복구·키 충돌·다른 키/사용자·입력 경계·장애/제한 사례. 기술 도구의 새 채택값은 없다.

## 헌법 검토

| 원칙·게이트 | 설계 전 | 설계 후 | 근거 |
| --- | --- | --- | --- |
| I. 서비스 경계·API 호환성 | 통과 | 통과 | 다섯 API 보존, 코드 변경 없음, 계약 설계에 상태·권한·헤더 대조 |
| II. 근거 확인·도메인 기록 | 통과 | 통과 | 지식 규칙 전체·계획서 확인, 이름 정책을 resource 지식 문서에 기록 |
| III. 검증 방식·실행 증거 | 통과 | 통과 | 문서 검사와 실제 HTTP 시험 분리, 자동 검증은 1단계 이후 |
| IV. 정책 동기화 | 통과 | 통과 | A 답변을 명세·계획서·도메인 규칙·resource 문서·계약 설계에 반영, 해당 구현·테스트는 아직 없음 |
| V. 미확정 정책 | 통과 | 통과 | 길이 단위 답변 기록, 이번 범위의 미해결 정책 없음. 헌법 채택일·CI TODO는 이 작업의 선행 조건 아님 |

예외가 필요한 헌법 위반은 없다. 도구 후보 확인은 채택·실행 증거가 아니다. 문서상 상태 전이는 후속 구현의 기대값이다.

```text
backend/                       # 기존 최소 앱, 이번 계획에서 변경 없음
```

## 실행 순서와 검토 경계

1. [조사](research.md)의 결정과 사용자 A 답변을 확인한다. 기존 정책과 새로 명확해진 길이 계산을 구분한다.
2. [계약 설계](contracts/api-contract.md)의 다섯 작업·DTO·오류·헤더를 최종 OpenAPI에 선언한다. 이름의 전처리 후 길이와 실제 본문 바이트 제한은 설명·사례에도 남긴다.
3. 정상·비정상 사례마다 초기 사용자·수량·키와 최종 상태를 기록한다. 핵심 흐름과 실패 키 복구 사례를 수량식으로 검토한다.
4. 세 선택의 이유·대안을 각각 3~5줄로 결정 기록에 적는다. 이번 조사 결과는 이 작업의 설계 근거다.
5. [검토 안내](quickstart.md)를 따라 누락·모순·링크·형식을 검사하고 명령·종료 코드·미실행 범위를 증거로 남긴다. 사용자가 자기 말로 설명했는지는 실제 확인 전 미검증이다.
6. 0단계 산출물과 설명 기준이 충족된 이후에만 원 계획 0단계 완료를 기록한다. 자동 계약 검증은 1단계의 도구 준비 뒤 실행한다.

이 순서는 실행 계획이며 task ID·완료 체크박스를 대신하지 않는다. 다음 명령은 `$speckit-tasks`다.
