## 사용자 시나리오와 검증 *(필수)*

### 사용자 스토리 1 - 재시도와 취소의 결과를 이해한다 (우선순위: P1)

개발자는 예약 요청을 다시 보냈을 때 추가 예약이 생기는지, 취소 뒤 어떤 응답을 받는지, 실패한 요청의 키로 나중에 성공할 수 있는지를 구현 전에 설명할 수 있어야 한다.

**우선순위 이유**: 같은 요청의 반복과 새 요청을 구분하지 못하면 수량·예약·응답의 기대값이 서로 모순된다.

**독립 검증**: 실행 중인 서버 없이 아래 표를 따라가며 매 단계의 남은 수량, 활성 예약 수, 성공한 키 기록, 응답을 대조한다. 다음 수치는 요구되는 사례의 기대값이며 실제 실행 결과가 아니다.

**인수 시나리오**:

1. **조건**: 최초 수량 1, 인증 사용자 A, 미사용 키 K. **행동**: 예약 → 같은 키 재요청 → 취소 → 같은 키 생성 재요청 → 조회. **결과**: 아래 표의 상태와 응답을 모두 설명할 수 있다.
2. **조건**: A가 K로 대상 R1 예약에 성공했다. **행동**: K로 다른 대상 R2를 예약한다. **결과**: 키 충돌이며 R2 수량과 기존 예약은 바뀌지 않는다. R1이 취소된 뒤에도 같은 규칙이다.
3. **조건**: 대상이 품절이고 A의 키 F로 성공한 예약이 없다. **행동**: F로 예약해 실패한 뒤 기존 예약 취소로 수량이 복구되면 F로 다시 예약한다. **결과**: 처음 실패가 F를 점유하지 않아 나중 요청이 성공한다.
4. **조건**: 수량이 충분하다. **행동**: A가 서로 다른 키로 두 번 예약하고 B가 A와 같은 문자열 키로 예약한다. **결과**: 세 예약이 각각 가능하며 요청당 수량은 1이다.

| 순서 | 행동 | 기대 결과 | 남은 수량 | 활성 예약 수 | A의 K 기록 |
| --- | --- | --- | --- | --- | --- |
| 0 | 수량 1 대상 준비 | 대상 생성 완료 | 1 | 0 | 없음 |
| 1 | A가 K로 예약 | 201, CONFIRMED, 최초 응답 표시 | 0 | 1 | 예약 1개 |
| 2 | 같은 사용자·키·대상 재요청 | 201, 최초 식별자·생성 시각·Location·JSON 필드 값 재현, 재요청 표시 | 0 | 1 | 동일 예약 |
| 3 | 소유자가 취소 | 200, CANCELLED, 취소 시각 있음 | 1 | 0 | 유지 |
| 4 | 같은 생성 요청 재요청 | 201, 최초 CONFIRMED 생성 결과 재현, 재요청 표시 | 1 | 0 | 유지 |
| 5 | 소유자가 예약 조회 | 200, 현재 CANCELLED와 취소 시각 | 1 | 0 | 유지 |
| 6 | 같은 예약 중복 취소 | 200, 기존 CANCELLED와 동일 취소 시각 | 1 | 0 | 유지 |

### 사용자 스토리 2 - 다섯 작업의 계약으로 기대 결과를 판정한다 (우선순위: P1)

개발자와 검토자는 대상 생성·조회, 예약 생성·조회·취소의 입력, 권한, 응답과 오류를 같은 문서로 판단할 수 있어야 한다.

**우선순위 이유**: 구현에 따라 기대값을 바꾸지 않고 후속 테스트의 기준을 고정한다.

**독립 검증**: 각 작업의 정상 사례 1개 이상·비정상 사례 2개 이상을 작성하고, 계획서 4절과 계약 초안을 대조한다.

**인수 시나리오**:

1. **조건**: 계약 초안을 작성한다. **행동**: 아래 다섯 작업의 사례를 검토한다. **결과**: 최소 15개 사례 각각에 권한·입력·응답·변경 여부가 명시된다.
2. **조건**: 잘못된 입력, 인증 실패, 본문 초과, 요청 제한 또는 의존성 장애가 발생한다. **행동**: 계약에서 결과를 찾는다. **결과**: 상태·오류 코드·필수 헤더를 판정할 수 있고 실패가 새 예약이나 부분 수량 변경을 남기지 않는다.
3. **조건**: 타인의 예약이다. **행동**: 일반 사용자 또는 관리자가 조회·취소한다. **결과**: 없는 예약과 동일하게 404이며 상태·수량은 바뀌지 않는다.

| 작업 | 정상 사례 | 비정상 사례 1 | 비정상 사례 2 |
| --- | --- | --- | --- |
| 대상 생성 | ADMIN, 유효한 이름·수량 0 → 201, Location, capacity=available=0 | USER → 403 FORBIDDEN, 생성 없음 | capacity 문자열·소수 → 400 INVALID_REQUEST, 생성 없음 |
| 대상 조회 | 인증 사용자, 존재하는 대상 → 200, 현재 수량 | 미인증 → 401 UNAUTHENTICATED, WWW-Authenticate | 존재하지 않는 UUID → 404 NOT_FOUND |
| 예약 생성 | 인증 사용자, 유효한 키, 수량 있는 대상 → 201, Location, CONFIRMED, 수량 1 감소 | 미사용 키, 품절 → 409 SOLD_OUT, 키 기록 없음 | 성공한 같은 사용자·키로 다른 대상 → 409 IDEMPOTENCY_CONFLICT, 수량 무변경 |
| 예약 조회 | 소유자 → 200, 현재 상태·생성 시각·취소 시각 또는 null | 타인(관리자 포함) → 404 NOT_FOUND | 잘못된 UUID → 400 INVALID_REQUEST |
| 예약 취소 | 소유자, 본문 없음 → 200 CANCELLED, 최초 취소만 수량 1 복구 | 타인(관리자 포함) → 404 NOT_FOUND, 변경 없음 | 비어 있지 않은 8KiB 이하 본문 → 400 INVALID_REQUEST, 변경 없음 |

### 사용자 스토리 3 - 설계 선택과 한계를 설명한다 (우선순위: P2)

개발자는 명시적 SQL 접근, 성공한 예약의 키 보존, 예약 쓰기 진입 제한이라는 세 선택의 이유와 대안을 읽고 설명할 수 있어야 한다.

**우선순위 이유**: 선택 근거를 남겨 이후 구현이나 도구 변경 때 업무 규칙과 기술 선택을 구분한다.

**독립 검증**: 결정 기록에서 세 항목 각각의 선택·이유·대안·영향을 확인한다.

**인수 시나리오**:

1. **조건**: 결정 기록을 작성한다. **행동**: 세 필수 결정을 검토한다. **결과**: 각 결정에 3~5줄로 이유·대안·영향을 기록한다.
2. **조건**: 검토자가 실패한 키와 취소 후 키에 대해 묻는다. **행동**: 사례와 결정 기록으로 설명한다. **결과**: 실패한 키는 나중에 성공할 수 있고 취소된 성공 키는 새 예약을 만들지 않는 이유를 설명한다.

### 경계 사례

- 이름은 앞뒤 공백 제거 후 유니코드 코드 포인트 기준 1~100자(`😀`는 1자), 최초 수량은 정수 0~1,000이다. 공백만인 이름, 길이·수량 범위 밖 입력은 거부한다.
- 생성 키의 길이 1·64는 허용하고 0·65, 공백·허용되지 않은 문자는 거부한다. 공백 제거·대소문자 변환은 하지 않는다.
- 요청 대상의 동일성은 UUID 값 기준이며 JSON 공백·필드 순서는 영향을 주지 않는다.
- 미정의 필드, 중복 JSON 키, 잘못된 JSON·UUID, 수량의 문자열·소수 입력을 거부한다. 예약 수량이나 사용자 식별자를 클라이언트가 지정하지 못한다.
- 본문 8KiB(8,192바이트)는 상한 이내, 초과는 413이다. 길이 헤더 없는 요청·chunked 요청도 실제 읽기 크기를 기준으로 제한한다. 초과는 인증보다 먼저 판정한다.
- 상한 이하 요청은 인증 → 예약 쓰기 요청 제한 → 입력 검증 → 업무 처리 순서다. 정상적인 재요청도 401·429·503으로 먼저 차단될 수 있다.
- 인증된 예약 생성·취소는 합산 20회/60초이며 최초 요청부터 고정 창이다. 재요청·잘못된 입력도 포함하고 요청마다 창을 연장하지 않는다.
- 마지막 수량의 동일 키 경쟁, 같은 키의 다른 대상 경쟁, 중복 취소, 생성·취소 경쟁에서도 수량 보존·키 유일성·최대 1회 복구를 기대한다. 실제 경쟁 검증은 후속 단계다.
- 의존성 장애·잠금 시간 초과는 503이며 부분 반영이 없어야 한다. 커밋 뒤 응답 유실은 같은 키로 최초 생성 결과를 확인한다.
- 분류하지 못한 내부 결함은 500으로 탐지하며 계약에 없는 오류 코드를 새로 만들거나 409·503으로 숨기지 않는다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 0단계는 기존 규칙과 다섯 작업의 계약을 확정하는 문서 작업이어야 한다. 서비스 기능·실행 환경·테스트 도구 구현과 새 엔드포인트 추가는 범위 밖이다. 인수 기준: 스토리 1~3과 산출물 범위 대조.
- **FR-002**: 키 재사용·실패한 키·다른 키의 추가 예약·취소 후 재시도를 자기 말로 설명하는 사례를 작성해야 한다. 성공 키는 사용자별로 대상을 가로질러 공유되고 계속 보존되며 실패 요청은 키를 점유하지 않는다. 인수 기준: 스토리 1의 네 사례.
- **FR-003**: 대상별 남은 수량은 0~최초 수량이고, 남은 수량 + CONFIRMED 예약 수 = 최초 수량이어야 한다. 사용자·키당 예약은 최대 1개, 취소 복구는 예약당 최대 1개다. 상태 전이는 CONFIRMED → CANCELLED만 허용하며 예약을 재활성화·삭제하지 않는다. 인수 기준: 흐름 표 전체와 경쟁 기대 결과.
- **FR-004**: 다섯 작업 각각에 정상 사례 최소 1개·비정상 사례 최소 2개를 작성해야 한다. 사례에는 초기 조건·사용자·입력·응답·상태·수량·키 변경 여부 또는 읽기/거부로 무변경임을 명시해야 한다. 인수 기준: 스토리 2의 표를 산출물에서 구체화.
- **FR-005**: 같은 사용자·키·대상 재요청은 최초 201·Location·JSON 필드 값을 재현하고 Idempotent-Replayed를 최초 false, 재요청 true로 반환해야 한다. 취소 후에도 생성 응답의 status는 CONFIRMED이고 GET은 현재 CANCELLED를 반환한다. 시각은 저장된 UTC 값을 사용하며 최초·재요청이 일치해야 한다. 인수 기준: 흐름 표 1~6행.
- **FR-006**: 계획서 4절의 입력·권한·성공·오류 계약을 `docs/openapi.yaml` 초안에 OpenAPI 3.0.3으로 선언해야 한다. path·requestBody·security·response·ProblemDetail과 Location·Idempotent-Replayed·Retry-After·WWW-Authenticate 헤더를 포함한다. 인수 기준: 다섯 작업 모두를 기준 문서와 대조.
- **FR-007**: 요청 객체의 additionalProperties는 false, 생성 키는 `^[A-Za-z0-9_-]{1,64}$`, resourceId와 식별자는 uuid, 시각은 date-time, status는 enum이어야 한다. 현재 상태 응답의 cancelledAt은 필수 필드로서 null을 허용하고 CONFIRMED일 때 null, CANCELLED일 때 취소 시각이다. 인수 기준: 스토리 2와 경계 사례 대조.
- **FR-008**: 응답 필드는 대상의 id·name·capacity·available, 생성 예약의 id·resourceId·status·createdAt, 현재 예약의 id·resourceId·status·createdAt·cancelledAt으로 고정해야 한다. 생성 예약 status는 CONFIRMED만 허용한다. 인수 기준: 계획서 4.1절과 필드 목록 대조.
- **FR-009**: 엄격한 입력 검증, 생성의 application/json 전용·415, 취소의 본문 없음, 본문 8KiB 상한·413과 처리 순서를 계약에 명시해야 한다. 선언만으로 중복 JSON 키·실제 바이트 제한·권한·경쟁을 실행 검증했다고 주장하지 않는다. 이름 길이는 공백 제거 후 코드 포인트로 계산한다. `😀` 100개는 허용하고 101개는 400으로 거부하는 사례를 포함한다. 인수 기준: 경계 사례와 계약 설명 대조.
- **FR-010**: 오류는 application/problem+json으로 통일하고 type·title·status·detail·instance·code를 명시해야 한다. 계획서 4.2절의 10개 오류 코드와 상태 대응을 보존하고 인증·권한·본문 제한·요청 제한 오류에도 적용한다. 401의 인증 헤더, 429의 재시도 대기 헤더를 포함하고 비밀정보를 노출하지 않는다. 인수 기준: 오류 목록·헤더·예시 전수 대조.
- **FR-011**: 권한은 대상 생성 ADMIN, 대상 조회·예약 생성 인증 사용자, 예약 조회·취소 소유자로 확정해야 한다. 사용자 식별자는 인증에서 얻고 타인의 예약은 관리자에게도 404다. 인수 기준: 스토리 2의 권한 사례.
- **FR-012**: 예약 쓰기 제한 초과는 429, 제한 의존성 장애는 503이며 해당 요청은 업무 데이터를 바꾸지 않아야 한다. 조회와 대상 생성은 제한 의존성의 장애로 차단하지 않는다. Retry-After는 남은 창의 밀리초를 초로 올림한 최소 1초다. 인수 기준: 경계 사례와 계약의 실패 응답 대조.
- **FR-013**: `docs/decisions.md`에 “SQL을 명시하기 위해 JDBC 사용”, “성공한 예약에 키 보관”, “Redis는 요청 진입 제한에 사용”의 선택 이유와 대안을 각각 3~5줄로 작성해야 한다. 인수 기준: 스토리 3. 이는 사용자 지정 산출물 요구이며 이번 명세에서 구현 알고리즘을 추가하지 않는다.
- **FR-014**: 작성한 사례를 표로 검토해 수량·활성 예약·키 기록의 모순과 미정인 성공·실패 결과가 없어야 한다. 문서 검토와 실행 검증을 구분하고 자동 계약 검증은 도구를 준비하는 1단계로 넘겨야 한다. 인수 기준: 모든 사례의 수량식·키·응답 대조 기록.

### 핵심 개체

- **예약 대상**: 식별자·이름·최초 수량·현재 남은 수량을 가진다. 최초 수량과 이름의 입력 범위를 계약으로 고정한다.
- **예약**: 식별자·대상·소유자·생성 키·생성 시각·현재 상태·취소 시각을 가진다. 생성 결과와 현재 상태를 구분한다.
- **생성 키**: 인증 사용자와 함께 성공한 생성 요청을 식별한다. 실패는 점유하지 않으며 취소로 해제하지 않는다.
- **계약 사례**: 초기 조건·행동·기대 응답·최종 상태·수량·키 기록을 연결하는 검토 단위다.
- **결정 기록**: 선택·이유·대안·영향을 남겨 설계 판단을 설명하는 기록이다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 다섯 작업 모두에 정상 1개 이상·비정상 2개 이상, 총 15개 이상의 사례가 있고 모든 사례의 결과를 추가 추측 없이 판정할 수 있다.
- **SC-002**: 예약 → 재요청 → 취소 → 재요청 → 조회 → 중복 취소의 6개 행동에서 수량·활성 예약·성공 키의 모순이 0건이다.
- **SC-003**: 키 재사용·실패 후 재시도·다른 키의 추가 예약·취소 후 재시도의 4개 규칙을 모두 사례로 설명할 수 있다. 특히 실패한 키로 나중에 성공할 수 있는 조건과 성공한 키의 지속 보존을 구분한다. 실제 본인 설명 여부는 별도로 기록한다.
- **SC-004**: 계약 검토에서 다섯 작업의 필수 입력·권한·성공·실패 결과의 누락과 기준 문서 대비 모순이 각각 0건이다.
- **SC-005**: 세 설계 결정 모두에 이유·대안·영향이 기록되고 검토자가 각 선택의 목적과 한계를 설명할 수 있다.
- **SC-006**: 모든 산출물과 검토 기록은 설계·작성·실행 검증 상태를 구분하며 미실행 검증을 완료로 표시한 항목이 0건이다.

## 전제와 의존성

- 기준은 [로컬 개발 계획](<../../한정 수량 예약 백엔드 로컬 개발 계획.md>) 2~5절과 7절 0단계, [지식 문서 안내](../../knowledge/README.md), [개발 헌법](../../.specify/memory/constitution.md)이다. 기존 규칙을 바꾸는 요청으로 해석하지 않는다.
- 이번 명령은 0단계 수행을 위한 요구사항을 정의한다. `docs/openapi.yaml`·`docs/decisions.md`는 후속 계획·작업에서 작성할 산출물이며 현재 생성됐다고 간주하지 않는다.
- 실제 도메인 개발 전 관련 지식 문서를 템플릿으로 작성·등록한다. 이번 명세 작성으로 예약·보안·요청 제한이 구현됐다고 간주하지 않는다.
- 실행 범위는 localhost CLI/API 클라이언트다. 고정 로컬 계정의 인증 계약을 사용하며 외부 공개·브라우저 서비스는 포함하지 않는다.
- 결제·만료·대기열·알림·프런트엔드·회원가입·비밀번호 재설정·목록·페이지네이션·대상 수량 변경/삭제는 포함하지 않는다.
- 자동 계약 검증 도구 준비·호환성 확인은 1단계, 실제 HTTP 계약 검증은 후속 계약 테스트 단계에 의존한다. 이번 단계의 완료는 수동 사례 대조와 문서 계약 확정으로 판정한다.
- 계획서의 2~3시간은 예상 학습 시간이며 실행 시간이나 완료 보장이 아니다. 헌법의 채택일·별도 CI 확인 TODO는 이 기능의 계약을 결정하는 데 영향을 주지 않는다.
