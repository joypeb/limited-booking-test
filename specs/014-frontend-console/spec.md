# Feature Specification: 로컬 브라우저 예약 콘솔

**Feature Branch**: `feature/frontend-sdd-tdd-orchestration`

**Created**: 2026-10-26

**Status**: Clarified(2026-10-26)

**Input**: 사용자 요청(2026-10-26): 완료된 백엔드에 어떤 기능이 개발되었는지 명세·계획·지침·구현 상태를 조사하고, 그 백엔드를 직접 조작하기 위한 프런트엔드를 저장소 루트 `frontend/`에 개발한다. 기술은 Next.js 16.4.3 App Router + TypeScript, Tailwind CSS 4.3.3(조사일 기준 두 패키지의 최신 안정 버전)이다. Spec Kit SDD와 TDD를 따르고 독립 리뷰와 GitHub PR 리뷰까지 진행한다.

## 기준과 범위

- 설계 기준: [계획서](<../../한정 수량 예약 백엔드 로컬 개발 계획.md>) 2~5절(업무 규칙·API·오류 계약), 헌법 1.1.0(원칙 VI 신설), `knowledge/rules/*.md` 전체, `knowledge/domain/resource.md`·`reservation.md`·`security.md`·`ratelimit.md`, 고정 계약 `docs/openapi.yaml`.
- 이번 기능은 **이미 구현·검증된 백엔드 API 5개를 사람이 브라우저에서 직접 호출·관찰하는 로컬 콘솔**이다. 백엔드의 API 계약·보안 설정·SQL·스키마·Redis 정책은 바꾸지 않는다.
- 백엔드에 실제로 존재하는 기능(2026-10-26 Explorer 조사, 코드·OpenAPI 대조):
  - `POST /api/resources`(ADMIN, 201+Location), `GET /api/resources/{id}`(인증 사용자)
  - `POST /api/reservations`(인증 사용자, `Idempotency-Key`, 201+Location+`Idempotent-Replayed`), `GET /api/reservations/{id}`(소유자), `POST /api/reservations/{id}/cancel`(소유자, 본문 없음)
  - 오류: `application/problem+json`, `code` 10종(`INVALID_REQUEST`, `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `SOLD_OUT`, `IDEMPOTENCY_CONFLICT`, `PAYLOAD_TOO_LARGE`, `UNSUPPORTED_MEDIA_TYPE`, `RATE_LIMITED`, `DEPENDENCY_UNAVAILABLE`), 401 `WWW-Authenticate`, 429 `Retry-After`
  - 인증: 고정 계정 `ADMIN`·`USER_A`·`USER_B` Basic 인증, 무상태(세션·쿠키 없음), CSRF 비활성(비브라우저 전제), CORS 설정 없음
  - 목록 API 없음(대상·예약 모두 ID 단건 조회만 존재)
- 범위 밖: 백엔드 변경(CORS 허용·목록 API·새 엔드포인트), 외부 공개·배포·TLS, 회원가입·비밀번호 변경, 결제·만료·대기열·알림, 대상 수량 변경·삭제, 서버 측 영속 저장, 다국어, 모바일 전용 레이아웃 최적화, 프런트엔드 CI 워크플로 추가(사용자 결정 전까지 보류), 부하 시험.

## Clarifications

### Session 2026-10-26

업무 정책 질문은 없다(백엔드 규칙은 바꾸지 않음). 설계 모호점은 계획서·실제 코드와 Explorer 조사, Advisor 반대 의견으로 해소했다(Orchestrator 결정).

- Q: 브라우저가 CORS 없는 백엔드를 어떻게 호출하는가? → A: 같은 출처의 콘솔 서버가 계약 경로 5개만 전달한다. 백엔드 CORS 허용 추가는 헌법 원칙 VI·api-and-security 규칙 위반이라 기각.
- Q: 브라우저 도입 후 CSRF 전제는? → A: 비밀번호는 탭 메모리에만 있고 매 요청 명시적 인증 헤더로 보낸다. 쿠키·브라우저 자동 인증이 없어 브라우저가 자동으로 붙이는 자격 증명(ambient credential)이 없으므로 다른 사이트의 위조 요청은 인증되지 않는다. 추가로 DNS rebinding·다른 출처 요청을 막기 위해 콘솔 서버는 `Host`를 루프백 허용 목록으로 검사하고, `Origin`이 있으면 같은 허용 목록이어야 하며, `Sec-Fetch-Site`가 있으면 `same-origin` 또는 `none`(주소창 직접 입력)이어야 한다(Advisor 지적: Origin==Host 단순 비교는 rebinding에 무력).
- Q: 401의 `WWW-Authenticate`는? → A: 그대로 두면 브라우저 기본 로그인 대화상자가 뜬다. 제거하면 계약 관찰이 불가하므로 이름을 `X-Upstream-WWW-Authenticate`로 바꿔 전달하고 화면에 원문을 표시한다(Advisor 권고 채택).
- Q: 본문은 어떻게 전달하는가? → A: 파싱·재직렬화 없이 받은 바이트 그대로 전달해 중복 키·소수·미정의 필드·8KiB 초과(413)를 백엔드가 그대로 판정하게 한다. 콘솔 서버는 메모리 보호용으로 1MiB 초과 본문만 자체 413으로 거부하며(백엔드 상한 8KiB보다 충분히 커 관찰을 왜곡하지 않음), 이를 콘솔 자체 오류로 구분한다.
- Q: 수량 입력은? → A: 입력 원문이 JSON 숫자 문법이면 그 원문을 그대로 본문에 넣는다(`1.0`·`1e2`·`1.5`도 원문 전송, 백엔드 400 관찰 가능). JSON 숫자 문법이 아니면 전송하지 않는다. 이름은 JSON 문자열로만 인코딩하고 다듬지 않는다(Java `strip()`과 JS `trim()`의 공백 정의 차이로 클라이언트 중복 검증은 불일치를 만든다).
- Q: 백엔드 연결 실패·지연은? → A: 콘솔 서버가 502 problem+json(`code`=`CONSOLE_UPSTREAM_UNREACHABLE`)으로 응답해 백엔드 503과 구분한다. 콘솔 서버의 백엔드 호출 상한 10초(백엔드 소켓 읽기 7초보다 김), 초과 시 504(`CONSOLE_UPSTREAM_TIMEOUT`). 자동 재시도 없음.
- Q: 최근 기록 저장 위치는? → A: 이 브라우저의 영속 저장소(새로고침 후 유지)에 식별자 메모만 저장한다. 비밀번호·수량·상태는 저장하지 않는다.
- Q: 콘솔 응답 보안 헤더는? → A: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, 프레임 삽입 금지(`X-Frame-Options: DENY`·`frame-ancestors 'none'`)를 둔다. 전체 스크립트 CSP는 프레임워크 인라인 스크립트의 nonce 설계가 필요해 이번 범위에서 제외하고 기록한다.
- Q: 프런트엔드 CI는? → A: 기존 CI 결정 변경이므로 제외. 후속 사용자 결정으로 남긴다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 관리자가 콘솔에서 예약 대상을 만들고 수량을 확인한다 (Priority: P1)

로컬 개발자는 관리자 계정으로 콘솔에 자격 증명을 입력하고, 이름과 최초 수량으로 예약 대상을 만든 뒤, 생성 결과(식별자·이름·총 수량·잔여 수량)와 응답 상태를 화면에서 확인한다. 식별자를 입력해 같은 대상을 다시 조회할 수 있다.

**Why this priority**: 대상이 없으면 예약을 시험할 수 없다. 자격 증명 입력·백엔드 전달·오류 표시라는 콘솔의 공통 기반도 이 흐름에서 처음 검증된다.

**Independent Test**: 실행 중인 백엔드에 대해 관리자 자격 증명으로 대상을 생성·조회하고, 일반 사용자 자격 증명으로 생성을 시도해 거부(403)가 표시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 관리자 자격 증명을 입력한 콘솔, **When** 이름 "콘서트 A"·수량 3으로 대상을 생성, **Then** 응답 상태 201과 식별자·이름·총 수량 3·잔여 수량 3이 표시되고, 그 식별자로 상세를 바로 조회할 수 있다.
2. **Given** 관리자 자격 증명, **When** 수량 0으로 생성, **Then** 201과 잔여 수량 0이 표시된다.
3. **Given** 일반 사용자 자격 증명, **When** 대상 생성을 시도, **Then** 상태 403과 `FORBIDDEN` 코드·한국어 설명이 표시되고 대상은 만들어지지 않는다.
4. **Given** 잘못된 비밀번호, **When** 어떤 요청이든 보내면, **Then** 상태 401과 `UNAUTHENTICATED`, 백엔드가 보낸 인증 요구 헤더 원문이 콘솔 화면 안에 표시되며 브라우저의 기본 로그인 대화상자가 뜨지 않는다.
5. **Given** 관리자 자격 증명, **When** 공백뿐인 이름·수량 1001·소수 수량으로 생성을 시도, **Then** 백엔드의 400 `INVALID_REQUEST`가 그대로 표시된다(콘솔이 입력을 다듬거나 바꾸어 전송하지 않는다).
6. **Given** 인증된 사용자, **When** 존재하지 않는 대상 식별자를 조회, **Then** 404 `NOT_FOUND`가 표시된다. 식별자 형식이 아니면 요청을 보내지 않고 형식 오류를 안내한다.

### User Story 2 - 사용자가 대상 1개를 예약하고 같은 요청의 재전송을 관찰한다 (Priority: P1)

로컬 개발자는 일반 사용자 계정으로 대상 식별자를 입력해 예약을 생성한다. 콘솔은 새 예약 시도마다 생성 키를 만들어 함께 보내고, 같은 키로 다시 보내는 기능을 제공해 최초 응답과 재현 응답(재현 여부 표시)을 비교하게 한다. 품절·키 충돌·요청 제한·의존성 장애를 구분해 보여 준다.

**Why this priority**: 예약 생성과 멱등 재현은 백엔드의 핵심 정합성 기능이며 콘솔로 직접 관찰하려는 주된 대상이다.

**Independent Test**: 수량 1인 대상에 USER_A로 예약 → 같은 키 재전송 → USER_B로 새 예약 시도 순서로 수행하고, 각 응답의 상태·재현 여부·코드와 대상의 잔여 수량을 확인한다.

**Acceptance Scenarios**:

1. **Given** 잔여 수량 1인 대상과 USER_A, **When** 예약 생성, **Then** 201·예약 식별자·`CONFIRMED`·생성 시각·재현 여부 "아니오"와 사용한 생성 키가 표시된다.
2. **Given** 방금 성공한 예약, **When** "같은 키로 다시 보내기", **Then** 201·같은 예약 식별자·같은 생성 시각·재현 여부 "예"가 표시되고 잔여 수량은 더 줄지 않는다(대상 재조회로 확인).
3. **Given** 잔여 수량 0인 대상, **When** USER_B가 새 키로 예약, **Then** 409 `SOLD_OUT`이 품절로 구분되어 표시된다.
4. **Given** USER_A가 키 K로 대상 X를 예약한 상태, **When** 같은 키 K로 대상 Y를 예약, **Then** 409 `IDEMPOTENCY_CONFLICT`가 품절과 다른 문구로 표시된다.
5. **Given** 사용자가 직접 입력한 키가 허용 형식(영문·숫자·`_`·`-` 1~64자)이 아님, **When** 전송, **Then** 콘솔은 그대로 보내고 백엔드의 400을 표시한다(콘솔은 키를 다듬지 않는다).
6. **Given** 쓰기 요청 제한 초과, **When** 예약을 시도, **Then** 429 `RATE_LIMITED`와 다시 시도 가능까지 남은 초(응답의 `Retry-After`)가 표시된다.
7. **Given** 백엔드가 의존성 장애로 503을 반환, **When** 예약, **Then** `DEPENDENCY_UNAVAILABLE`이 표시되고 콘솔은 자동 재시도하지 않는다.

### User Story 3 - 사용자가 자신의 예약을 조회하고 취소한다 (Priority: P1)

로컬 개발자는 예약 식별자로 자신의 예약 상태를 조회하고 취소한다. 다시 취소해도 기존 취소 시각이 그대로 반환되는 것을 관찰하고, 다른 사용자의 예약은 존재 여부를 알 수 없게 404로 표시되는 것을 확인한다.

**Why this priority**: 취소의 원자성·중복 취소 처리·소유권 은닉은 백엔드 정합성 규칙의 나머지 핵심이다.

**Independent Test**: USER_A의 예약을 USER_A로 조회·취소·재취소하고, USER_B·ADMIN으로 같은 예약을 조회·취소해 404를 확인한 뒤 대상 잔여 수량이 1만 복구됐는지 확인한다.

**Acceptance Scenarios**:

1. **Given** USER_A의 `CONFIRMED` 예약, **When** USER_A가 조회, **Then** 200·상태 `CONFIRMED`·취소 시각 없음이 표시된다.
2. **Given** 같은 예약, **When** USER_A가 취소, **Then** 200·상태 `CANCELLED`·취소 시각이 표시되고, 대상 잔여 수량은 1 증가한다.
3. **Given** 이미 취소된 예약, **When** 다시 취소, **Then** 200과 처음과 같은 취소 시각이 표시되고 잔여 수량은 더 늘지 않는다.
4. **Given** USER_A의 예약, **When** USER_B 또는 ADMIN이 조회·취소, **Then** 404 `NOT_FOUND`가 표시된다.
5. **Given** 취소된 예약의 생성 키, **When** 같은 키·같은 대상으로 예약을 다시 보내면, **Then** 최초 `CONFIRMED` 응답이 재현(재현 여부 "예")되고, 현재 상태는 예약 조회에서 `CANCELLED`로 확인된다는 안내가 표시된다.

### User Story 4 - 목록 API 없이도 이 브라우저에서 다룬 식별자를 다시 찾는다 (Priority: P2)

백엔드에는 목록 API가 없으므로, 로컬 개발자는 이 브라우저에서 생성·조회한 대상과 예약의 식별자를 최근 기록에서 골라 다시 조회한다. 기록은 백엔드 상태가 아니라 이 브라우저의 메모이며, 언제든 지울 수 있다.

**Why this priority**: UUID를 복사·붙여넣는 수고를 줄이지만, 핵심 정합성 관찰에는 필수가 아니다.

**Independent Test**: 대상과 예약을 하나씩 만든 뒤 새로고침하고 최근 기록에서 각각 선택해 조회되는지, "기록 지우기" 후 비는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 이 브라우저에서 대상과 예약을 생성, **When** 최근 기록을 열면, **Then** 각 식별자와 종류·기록 시각·당시 계정이 표시되고 선택하면 해당 상세를 새로 조회한다.
2. **Given** 최근 기록, **When** 표시되는 값, **Then** 기록에는 식별자·종류·이름 등 메모만 있고 잔여 수량·상태는 저장 값이 아니라 선택 시 새로 조회한 백엔드 응답으로 표시된다.
3. **Given** 최근 기록, **When** "기록 지우기", **Then** 기록이 모두 사라진다. 기록에는 비밀번호가 포함되지 않는다.

---

### Edge Cases

- 백엔드가 꺼져 있거나 연결할 수 없음 → 백엔드의 503과 구분되는 "백엔드에 연결할 수 없음" 오류를 표시하고 자동 재시도하지 않는다.
- 백엔드가 problem+json이 아닌 응답(예: HTML 오류 페이지)을 반환 → 상태 코드와 "알 수 없는 응답 형식"을 표시하고 본문을 해석된 사실처럼 꾸미지 않는다. 응답 본문의 내부 정보를 그대로 노출하지 않는다.
- 예상하지 못한 `code` 값 → 원래 `code`·`detail`을 그대로 보여 준다.
- 전송 중 같은 버튼을 반복 클릭 → 진행 중에는 같은 작업을 다시 보내지 않는다(같은 키 재전송은 명시적 버튼으로만).
- 응답 대기 중 계정을 바꿈 → 이전 계정의 응답을 새 계정의 결과로 표시하지 않는다.
- 페이지 새로고침 → 비밀번호는 사라지고 다시 입력해야 한다. 최근 기록(식별자 메모)은 남는다.
- 콘솔 서버에 다른 출처의 페이지가 요청을 보냄 → 거부한다.
- 콘솔 서버가 허용하지 않은 경로·메서드(예: 목록 경로, `DELETE`) 요청 → 백엔드로 전달하지 않고 거부한다.
- 예약 식별자 자리에 경로 조작 문자열(`../` 등) → UUID 형식이 아니므로 전달하지 않는다.
- 시각 표시 → 백엔드가 준 UTC 값을 원문 그대로 보여 주고, 필요하면 로컬 시각을 보조로 함께 보여 준다(원문이 기준).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 콘솔은 백엔드 API 5개(대상 생성·조회, 예약 생성·조회·취소)를 화면에서 호출할 수 있어야 하며, 계약에 없는 기능(목록·수정·삭제)을 제공하지 않아야 한다.
- **FR-002**: 콘솔은 고정 계정(ADMIN·USER_A·USER_B) 중 하나와 비밀번호를 입력받아 이후 요청의 인증에 사용해야 한다. 비밀번호는 브라우저 저장소·쿠키·URL·로그·저장소 파일에 남기지 않고, 새로고침·계정 전환·"자격 증명 지우기" 시 사라져야 한다.
- **FR-003**: 브라우저는 백엔드에 직접 연결하지 않고 같은 출처의 콘솔 서버를 거쳐야 한다. 콘솔 서버는 계약의 5개 경로·메서드만 전달하고, 경로의 식별자는 UUID 형식일 때만 전달하며, 그 밖의 요청은 백엔드로 보내지 않고 거부해야 한다.
- **FR-004**: 콘솔 서버는 요청 대상 호스트가 루프백 허용 목록이 아니거나, 다른 출처·교차 사이트에서 온 요청을 백엔드로 보내지 않고 거부해야 한다. 백엔드 주소는 루프백 주소로만 설정할 수 있어야 한다.
- **FR-005**: 콘솔 서버는 요청의 인증 정보·Content-Type·`Idempotency-Key`·본문을 바꾸지 않고 전달하며, 사용자 식별 헤더를 추가하지 않아야 한다. 응답의 상태·본문·`Location`·`Idempotent-Replayed`·`Retry-After`를 보존해야 한다.
- **FR-006**: 401 응답 시 브라우저의 기본 인증 대화상자가 나타나지 않아야 하며, 오류와 백엔드의 인증 요구 헤더 원문은 콘솔 화면 안에 표시되어야 한다.
- **FR-007**: 모든 결과 화면은 HTTP 상태, 성공 시 응답 필드 전체, 오류 시 `code`·`title`·`detail`과 코드별 한국어 설명을 표시해야 한다. 알 수 없는 `code`나 형식은 원문을 표시해야 한다.
- **FR-008**: 콘솔은 이름·수량·생성 키를 다듬거나 변환하지 않고 전송해야 한다. 업무 규칙(이름 길이·수량 범위·키 형식) 판정은 백엔드 응답에 맡기며, 사전 안내는 전송을 막지 않아야 한다. 수량은 입력 원문이 숫자 표기 문법에 맞으면 원문 그대로 보내고(소수·지수 포함), 맞지 않거나 경로 식별자가 UUID 형식이 아니면 전송하지 않고 안내한다.
- **FR-009**: 예약 생성 시 콘솔은 새 시도마다 허용 형식의 생성 키를 만들어 보여 주고, 사용자는 키를 직접 바꿀 수 있어야 한다. "같은 키로 다시 보내기"는 직전 시도의 키와 대상으로 다시 보내야 한다.
- **FR-010**: 예약 생성 결과는 재현 여부(`Idempotent-Replayed`)를 표시해야 하며, 재현 응답이 최초 `CONFIRMED`를 재현할 뿐 현재 상태는 조회로 확인해야 함을 안내해야 한다.
- **FR-011**: 409 `SOLD_OUT`과 `IDEMPOTENCY_CONFLICT`, 429(남은 초 포함), 503 `DEPENDENCY_UNAVAILABLE`, 콘솔 서버가 백엔드에 연결하지 못한 경우를 서로 다른 문구로 구분해야 하며, 어떤 실패도 자동 재시도하지 않아야 한다.
- **FR-012**: 진행 중인 요청과 같은 작업은 중복 전송되지 않아야 하고, 응답 도착 전 계정이 바뀌면 그 응답을 새 계정의 결과로 표시하지 않아야 한다.
- **FR-013**: 잔여 수량·예약 상태는 백엔드 응답만 표시해야 하며, 콘솔이 계산·추정한 값을 확정 값처럼 보여 주지 않아야 한다. 예약 생성·취소 후 대상 상세를 새로 조회하는 수단을 제공해야 한다.
- **FR-014**: 콘솔은 이 브라우저에서 생성·조회한 대상·예약의 식별자 메모(종류·식별자·이름·기록 시각·당시 계정)를 최근 기록으로 보관하고 선택 시 새로 조회해야 하며, 모두 지우는 기능을 제공해야 한다. 기록에는 비밀번호·잔여 수량·상태를 저장하지 않는다.
- **FR-015**: 시각은 백엔드의 UTC 원문을 기준으로 표시해야 한다.
- **FR-016**: 모든 입력에는 접근 가능한 이름(레이블)이 있어야 하고, 결과·오류는 보조 기술이 변경을 알 수 있게 알려야 한다. 키보드만으로 모든 작업을 수행할 수 있어야 한다.
- **FR-017**: 콘솔은 localhost에서만 열리도록 실행되어야 하며, 실행·테스트·종단 검증 방법이 README와 기록 문서에 실제 실행 결과와 함께 남아야 한다.
- **FR-018**: 프런트엔드 도입으로 바뀌는 범위·보안 전제(브라우저 사용, CSRF·CORS 판단)를 AGENTS.md·계획서·지식 문서에 같은 정책으로 반영해야 한다. 백엔드 계약 문서(OpenAPI)는 바뀌지 않아야 한다.
- **FR-019**: 콘솔 응답은 내용 유형 추측 금지·참조 정보 미전송·프레임 삽입 금지 보안 헤더를 가져야 한다.

### Key Entities

- **자격 증명(세션 메모리)**: 선택한 계정 이름과 비밀번호. 현재 탭 메모리에만 존재한다.
- **예약 대상 화면 값**: 백엔드 ResourceView(id·name·capacity·available)의 표시.
- **예약 화면 값**: CreatedReservationView(id·resourceId·status·createdAt)와 재현 여부, ReservationView(…·cancelledAt)의 표시.
- **예약 시도**: 대상 식별자 + 생성 키 + 시도한 계정. "같은 키로 다시 보내기"의 기준.
- **API 결과**: HTTP 상태, 성공 본문 또는 문제 상세(code·title·detail·status), 보존 헤더(Location·Idempotent-Replayed·Retry-After), 콘솔 연결 실패 여부.
- **최근 기록 항목**: 종류(대상/예약)·식별자·이름(대상일 때)·기록 시각·당시 계정. 비밀번호·수량·상태 없음.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 실행 중인 로컬 백엔드에 대해 "대상 생성 → 예약 → 같은 키 재전송 → 조회 → 취소 → 재취소 → 대상 재조회"의 전체 흐름을 콘솔 화면만으로 5분 안에 수행할 수 있고, 각 단계의 상태·재현 여부·잔여 수량이 백엔드 계약과 일치한다(실제 백엔드 대상 종단 검증 1회 이상 기록).
- **SC-002**: 백엔드의 오류 `code` 10종 각각과 백엔드 연결 실패가 콘솔에서 서로 다른 한국어 설명으로 표시된다(자동 테스트로 전부 확인).
- **SC-003**: 비밀번호가 브라우저 저장소·쿠키·최근 기록에 0회 저장된다(자동 테스트와 종단 검증에서 확인).
- **SC-004**: 계약 밖 경로·메서드·다른 출처·UUID가 아닌 식별자 요청은 100% 백엔드에 도달하지 않는다(자동 테스트로 확인).
- **SC-005**: 401 응답에서 브라우저 기본 인증 대화상자가 0회 나타난다(종단 검증에서 확인).
- **SC-006**: 콘솔 작업 전후 백엔드의 기존 검증(`./gradlew test`)과 계약 문서가 변경 없이 유지된다.
- **SC-007**: 콘솔의 자동 테스트는 0건·skip·실패 없이 통과하며, 각 사용자 시나리오가 최소 1개의 실패를 먼저 확인한 테스트로 대응된다.

## Assumptions

- 사용자는 백엔드를 README 절차로 직접 실행한다(`docker compose`·환경 변수·`bootRun`). 콘솔은 백엔드를 시작·종료하지 않는다.
- 콘솔 사용자는 고정 계정의 비밀번호를 알고 있는 로컬 개발자 본인이다. 계정 목록 추가·비밀번호 변경은 백엔드 범위 밖이므로 다루지 않는다.
- 단일 사용자 로컬 환경이며 동시 사용자·부하는 고려하지 않는다. 경쟁 검증은 기존 백엔드 테스트·k6가 담당한다.
- 화면 언어는 한국어 하나이며, 데스크톱 브라우저 최신 버전(Chromium 계열 기준)을 대상으로 한다.
- 최근 기록은 이 브라우저에만 남는 메모이며, 다른 브라우저·기기와 공유되지 않는다.
- 프런트엔드 CI 실행 추가는 기존 CI 결정(헌법 1.1.0 제약)을 바꾸므로 이번 범위에서 제외하고 후속 사용자 결정으로 남긴다.
