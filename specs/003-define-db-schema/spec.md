# 기능 명세: 예약 데이터 제약과 테스트 초기화

**작업 브랜치**: `feature/db-schema`

**작성일**: 2026-10-14

**상태**: 초안 — 명세 품질 검토 완료, 구현·실행 검증 전

**입력**: 사용자가 선택한 [로컬 개발 계획](<../../한정 수량 예약 백엔드 로컬 개발 계획.md>) 7절의 「2단계: DB 제약과 테스트 초기화 구현」. 잘못된 예약 데이터를 저장 단계에서 거부하고, 대상·성공 예약 조회 및 격리된 테스트 초기화와 수량 보존 검사를 제공한다.

## 사용자 시나리오와 검증 *(필수)*

### 사용자 이야기 1 - 잘못된 수량 저장 차단 (우선순위: P1)

개발자는 상위 입력 검증을 거치지 않고 데이터를 저장해도 최초 수량과 남은 수량의 범위를 벗어나는 대상이 남지 않는지 확인한다. 관리자가 만든 수량 0인 대상도 정상 데이터로 취급한다.

**우선순위 이유**: 잘못된 수량은 이후 예약·취소의 정합성 검증을 무의미하게 만든다.

**독립 검증**: 예약 없이 대상 데이터를 직접 저장해 허용 경계와 거부 경계를 각각 확인한다.

**인수 시나리오**:

1. **조건** 최초 수량이 10일 때, **행동** 남은 수량 -1 또는 11을 각각 저장하면, **결과** 두 경우 모두 저장이 거부되고 해당 행이 남지 않는다.
2. **조건** 최초 수량 범위가 0~1000일 때, **행동** 최초 수량 -1 또는 1001을 각각 저장하면, **결과** 두 경우 모두 거부된다.
3. **조건** 새 대상일 때, **행동** 최초 수량·남은 수량을 각각 0·0 또는 1000·1000으로 저장하면, **결과** 저장과 조회가 모두 성공한다.
4. **조건** 최초 수량이 10일 때, **행동** 남은 수량 0 또는 10을 저장하면, **결과** 개별 수량 범위 검사에서 허용한다. 예약을 포함한 전체 수량 보존 여부는 별도로 검사한다.

---

### 사용자 이야기 2 - 예약의 식별·참조·상태 일관성 보장 (우선순위: P1)

개발자는 같은 사용자의 성공한 생성 키가 중복 예약을 만들지 않으며, 존재하지 않는 대상을 가리키거나 현재 상태와 취소 시각이 모순되는 예약이 남지 않는지 확인한다.

**우선순위 이유**: 성공한 예약 행이 생성 키 기록이므로 저장 단계의 중복 차단과 상태 일관성이 후속 재시도의 기반이다.

**독립 검증**: 대상과 예약을 직접 준비해 사용자·키·대상·상태를 한 항목씩 바꾸고 저장 결과를 비교한다.

**인수 시나리오**:

1. **조건** 사용자 A의 키 `key-1` 예약이 있을 때, **행동** A가 같은 키로 새 예약을 저장하면, **결과** 대상이 같거나 달라도 거부하고 기존 예약은 그대로 보존한다.
2. **조건** A의 키 `key-1` 예약이 있을 때, **행동** 사용자 B가 `key-1`로 예약을 저장하거나 A가 `key-2`로 저장하면, **결과** 다른 조건이 유효한 두 경우 모두 허용한다.
3. **조건** A의 키 `key-1` 예약이 `CANCELLED`일 때, **행동** A가 같은 키로 새 예약을 저장하면, **결과** 취소 후에도 중복을 거부하고 기존 예약을 보존한다.
4. **조건** 대상 식별자가 존재하지 않을 때, **행동** 해당 대상을 참조하는 예약을 저장하면, **결과** 거부하고 예약이 남지 않는다.
5. **조건** 나머지 값이 유효할 때, **행동** `CONFIRMED`·취소 시각 없음 또는 `CANCELLED`·취소 시각 있음의 예약을 저장하면, **결과** 두 조합 모두 허용한다.
6. **조건** 나머지 값이 유효할 때, **행동** `CONFIRMED`·취소 시각 있음, `CANCELLED`·취소 시각 없음 또는 정의되지 않은 상태를 각각 저장하면, **결과** 모든 경우 거부한다.
7. **조건** 정상 대상·예약이 있을 때, **행동** 필수 속성을 빠뜨리거나 기존 식별자를 중복해 저장하면, **결과** 거부하고 기존 데이터는 유지한다.

### 사용자 이야기 3 - 저장된 대상과 성공 예약을 정확히 찾기 (우선순위: P2)

개발자는 후속 예약 처리에서 대상 식별자와 사용자·생성 키로 저장 데이터를 찾을 수 있다. 취소된 예약도 성공한 키 기록으로 찾고 실제 저장 시각을 확인한다.

**우선순위 이유**: 후속 생성·재요청 판단이 저장 사실을 정확히 읽어야 한다.

**독립 검증**: 서로 다른 대상·사용자·키와 두 상태의 예약을 준비해 조회 결과와 준비 값을 대조한다.

**인수 시나리오**:

1. **조건** 대상이 저장돼 있을 때, **행동** 대상 식별자로 조회하면, **결과** 식별자·이름·최초 수량·남은 수량이 저장 값과 일치하고 없는 식별자는 결과 없음으로 구분된다.
2. **조건** 사용자·키가 일치하는 예약이 있을 때, **행동** 해당 조합으로 조회하면, **결과** 예약 식별자·대상 식별자·사용자 식별자·키·현재 상태·생성 시각·취소 시각을 모두 얻는다. 사용자나 키가 다른 조회는 결과 없음이다.
3. **조건** 취소된 예약이 있을 때, **행동** 같은 사용자·키로 조회하면, **결과** 해당 예약의 `CANCELLED` 상태와 저장된 취소 시각을 얻는다.
4. **조건** UTC 시각이 마이크로초 정밀도로 저장돼 있을 때, **행동** 예약을 반복 조회하면, **결과** 생성·취소 시각의 저장 값이 매번 동일하다.

### 사용자 이야기 4 - 안전하게 초기화하고 수량 보존 오류를 찾기 (우선순위: P2)

개발자는 개발 데이터에 영향을 주지 않고 같은 검증을 새 저장소와 이미 준비된 저장소에서 재현한다. 수량 검사는 한 관측 시점의 데이터로 일관성을 판단하고, 정상 데이터와 의도적으로 불일치한 데이터를 구별한다.

**우선순위 이유**: 테스트 간 데이터 잔류와 잘못된 검사 자체가 거짓 통과를 만들지 않아야 한다.

**독립 검증**: 테스트 전용 저장소에서 준비·초기화·재준비를 수행하고 정상·비정상 수량 사례를 각각 검사한다.

**인수 시나리오**:

1. **조건** 비어 있는 테스트 전용 저장소일 때, **행동** 저장 구조를 준비하고 이야기 1~3의 사례를 검증하면, **결과** 기대대로 정상 저장과 잘못된 저장 거부가 구분된다.
2. **조건** 같은 저장 구조가 이미 적용된 저장소일 때, **행동** 준비 절차와 같은 사례를 다시 실행하면, **결과** 구조 중복이나 데이터 잔류로 인한 오류 없이 같은 기대 결과를 얻는다.
3. **조건** 대상과 두 상태의 예약이 남아 있을 때, **행동** 테스트 데이터를 초기화하고 다시 초기화하면, **결과** 예약을 먼저, 대상을 나중에 제거하며 두 번 모두 대상·예약이 0건이다. 저장 구조와 적용 이력은 유지된다.
4. **조건** 최초 수량 10·남은 수량 8·확정 예약 2개·취소 예약 1개일 때, **행동** 수량 보존을 검사하면, **결과** 통과하고 취소 예약은 확정 예약 수에 포함하지 않는다. 최초 수량·남은 수량이 0이고 예약이 없는 경우도 통과한다.
5. **조건** 개별 수량 범위는 유효하지만 최초 수량 10·남은 수량 9·확정 예약 2개일 때, **행동** 수량 보존을 검사하면, **결과** 불일치로 실패한다. 대상이 없는 경우도 정상으로 처리하지 않는다.
6. **조건** 개발 데이터가 따로 보관돼 있을 때, **행동** 테스트 준비·검증·초기화를 실행하면, **결과** 테스트 전용 데이터만 변경하고 개발 데이터는 변경하지 않는다.
7. **조건** 빈 전용 DB에 업무 V1 전체 DDL 뒤 고의 SQL 오류를 붙인 테스트 전용 사본을 한 트랜잭션으로 적용할 때, **행동** 마지막 SQL이 실패하면, **결과** 실패를 반환하고 resources·reservations·업무 인덱스가 남지 않으며 V1 성공 적용 이력은0건이다. Flyway 이력 테이블 자체는 존재할 수 있다. 실패 DB의 증거와 종료를 확인한 뒤 다른 실행소유 DB에 변경하지 않은 정상 V1을1건 적용하고 동일 제약 사례를 검증한다.
8. **조건** 대상·예약이 커밋돼 있고 초기화의 예약 삭제 뒤 대상 삭제에만 고의 SQL 오류가 발생할 때, **행동** 초기화를 요청하면, **결과** 오류가 전달되고 두 테이블의 모든 기존 행·값과 적용 이력이 초기화 전과 동일하다. 롤백 후 별도 연결에서 상태를 확인하고 고의 장애를 제거한 뒤 같은 DB에서 새 초기화 트랜잭션을 명시적으로 요청하면 두 테이블0건·구조/이력 유지로 끝난다. 자동 무한 재시도는 하지 않는다.

### 경계 사례

- 최초 수량 0·1000, 범위 밖 -1·1001 및 남은 수량 0·최초 수량·-1·최초 수량+1.
- 같은 사용자·같은 키·다른 대상, 다른 사용자·같은 키, 같은 사용자·다른 키, 취소 후 같은 키 재사용.
- 비공백 이름 100자 허용·101자 거부, 비공백 키 64자 허용·65자 거부 및 필수 속성 누락·중복 식별자. 초과 부분이 모두 일반 공백인 경우는 상한으로 잘린 저장 값을 기대하는 별도 사례다.
- 상태와 취소 시각의 두 정상 조합·두 비정상 조합 및 알 수 없는 상태.
- 참조 대상 부재, 조회 대상 부재, 예약 없는 대상과 취소 예약만 있는 대상.
- 초기화를 연속 두 번 실행한 경우, 새 저장소와 기존 적용 저장소의 차이.
- 업무 V1의 마지막 SQL 실패, 예약 삭제 뒤 대상 삭제 실패, 장애 제거 후 다음 준비·초기화 시도의 상태.
- 개별 수량 제약은 만족하지만 전체 수량 보존식은 어기는 데이터. 저장 제약만으로 이를 막는다고 간주하지 않는다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 저장 단계에서 최초 수량은 정수 0~1000, 남은 수량은 정수 0~최초 수량만 허용해야 한다. 정상·비정상 경계는 이야기 1로 검증한다.
- **FR-002**: 대상·예약 식별자는 각각 유일해야 한다. 대상의 식별자·이름·최초 수량·남은 수량·생성 시각은 모두 필수여야 한다. 예약의 식별자·대상 식별자·사용자 식별자·생성 키·상태·생성 시각은 모두 필수이며, 취소 시각의 필수 여부는 FR-004의 상태 규칙을 따라야 한다. 저장된 이름·생성 키·상태의 길이 상한은 각각 100·64·16자다. 길이는 바이트가 아닌 문자 수이며 이름의 😀는 1자로 센다. 직접 저장 검증에서는 비공백 문자로 구성된 이름·생성 키의 상한을 허용하고 상한 초과를 거부해야 한다. 초과 부분이 모두 일반 공백인 문자열은 상한으로 잘려 저장될 수 있으므로 별도의 정상 저장 사례로 구분한다. 요청 입력의 길이·문자 규칙·이름 전처리는 후속 입력 검증 단계에서 보장한다. 이야기 2.7과 경계 사례로 검증한다.
- **FR-003**: 사용자·생성 키 조합당 예약은 최대 1개여야 한다. 대상과 현재 상태는 이 유일성의 범위를 바꾸지 않아야 하며 다른 사용자나 다른 키의 정상 예약은 허용해야 한다. 이야기 2.1~2.3으로 검증한다.
- **FR-004**: 예약은 존재하는 대상만 참조해야 한다. 예약 상태는 `CONFIRMED`·`CANCELLED`만 허용하며 각각 취소 시각 없음·있음과 일치해야 한다. 이야기 2.4~2.6으로 검증한다.
- **FR-005**: 대상 식별자 조회는 저장된 식별자·이름·최초 수량·남은 수량을 반환하거나 결과 없음을 구분해야 한다. 이야기 3.1로 검증한다.
- **FR-006**: 사용자·키 조회는 예약의 전체 저장 속성을 반환하거나 결과 없음을 구분해야 한다. 취소된 예약도 조회하며 UTC 시각과 저장된 마이크로초 정밀도를 유지해야 한다. 이야기 3.2~3.4로 검증한다.
- **FR-007**: 테스트용 저장 구조 준비는 빈 저장소와 이미 적용된 저장소 모두에서 같은 제약·조회 결과를 제공해야 한다. 재적용은 기존 저장 구조를 임의로 삭제·재생성하지 않아야 한다. 빈 DB의 업무 V1 도중 고의 SQL 실패는 적용 전체를 롤백해 업무 테이블·인덱스 잔류와 V1 성공 적용 이력이 없어야 한다. 실패 증거·자원 종료를 확인한 뒤 새 실행소유 DB에서 정상 V1로 준비를 재개하며 실패 DB에 clean/repair 또는 수정된 V1을 적용해 통과시키지 않아야 한다. 이야기 4.1~4.2·4.7로 검증한다.
- **FR-008**: 테스트 준비·초기화는 격리된 테스트 전용 저장소만 변경해야 하며 개발·부하·실제 개인정보 데이터에 연결하지 않아야 한다. 초기화는 예약 다음 대상으로 수행하고 반복 실행해도 빈 상태를 유지하며 적용 이력은 보존해야 한다. 예약 삭제 이후 대상 삭제가 실패하면 두 테이블의 행·값·적용 이력을 모두 초기화 전 상태로 롤백하고 오류를 전달해야 한다. 장애 제거 후 같은 DB의 새 트랜잭션으로 명시적으로 재요청하며 실패 트랜잭션에서 조회하거나 자동 재시도하지 않아야 한다. 이야기 4.3·4.6·4.8로 검증한다.
- **FR-009**: 테스트 준비 데이터는 다른 검증 작업에서 읽을 수 있도록 확정된 상태여야 한다. 대상과 두 상태의 예약을 준비할 수 있어야 하며 의도적 제약 위반 사례는 정상 준비와 구분해야 한다. 이야기 2~4의 준비 조건으로 검증한다.
- **FR-010**: 수량 보존 검사는 한 관측 시점에서 최초 수량·남은 수량·확정 예약 수를 함께 확인해 `0 ≤ 남은 수량 ≤ 최초 수량`과 `남은 수량 + 확정 예약 수 = 최초 수량`을 판정해야 한다. 취소 예약은 제외하고 대상 부재·불일치는 실패해야 한다. 이야기 4.4~4.5로 검증한다.
- **FR-011**: 검증 기록은 실제 저장 거부·정상 저장·조회·초기화·보존식 탐지 결과를 구분하고, 실행 명령·종료 코드·검증 수·환경·미검증 범위를 남겨야 한다. 검증 0건·실패·건너뜀은 통과로 취급하지 않아야 한다. 이야기 1~4의 실행 증거로 확인한다.

### 핵심 개체

- **예약 대상**: 고유 식별자, 이름, 최초 수량, 남은 수량, 생성 시각을 가진다. 예약이 참조하는 수량의 기준이다.
- **저장된 예약**: 고유 식별자, 대상·사용자 식별자, 생성 키, 현재 상태, 생성·취소 시각을 가진다. 취소 후에도 성공한 생성 키의 기록으로 남는다.
- **수량 관측 결과**: 같은 관측 시점의 대상 최초 수량·남은 수량·확정 예약 수로 구성하며 보존 여부의 검증 근거다.
- **테스트 준비 데이터**: 전용 저장소에서만 사용하는 대상·예약 데이터다. 정상 준비와 의도적 제약 위반·수량 불일치 사례를 구분한다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 이야기 1~2와 경계 사례에 명시된 수량·유일성·참조·상태·필수 값·식별자 및 비공백 문자 길이 제약 위반 사례가 100% 거부되고 거부된 행의 잔류가 0건이다. 정상 사례는 모두 저장되며 공백 초과분 절단 사례는 명시한 저장 값과 일치한다.
- **SC-002**: 이야기 3의 조회에서 모든 반환 속성이 저장 값과 100% 일치하며 없는 대상·사용자·키의 오탐 조회가 0건이다.
- **SC-003**: 새 저장소·이미 준비된 저장소의 두 조건에서 같은 인수 사례가 모두 같은 결과를 내고 연속 두 번 초기화한 뒤 대상·예약이 각각 0건이다. 테스트 외 데이터 변경은0건이다. 고의 마이그레이션 실패의 업무 구조 잔류·V1 성공 이력은0건, 초기화 중간 실패의 기존 행·값 변경은0건이며 명시한 복구 시도는 정상 준비 또는 두 테이블0건으로 완료돼야 한다.
- **SC-004**: 이야기 4의 정상 수량 사례는 모두 통과하고 의도적 수량 불일치와 대상 부재는 모두 실패해 검사 자체의 탐지력을 확인한다.
- **SC-005**: 개발자는 모든 인수 사례를 정상·거부·조회·초기화·보존식 검증 결과와 연결해 확인할 수 있으며, 실행 기록에서 미실행 사례가 통과로 표시되는 경우는 0건이다.

## 전제와 의존성

- 업무 기준은 계획서 2~5절과 기존 [resource](../../knowledge/domain/resource.md)·[reservation](../../knowledge/domain/reservation.md) 문서다. 이번 명세는 기존 규칙을 변경하지 않는다.
- 이 단계의 사용자는 저장 규칙을 직접 이해·검증하는 개발자다. 관리자·예약 사용자의 HTTP 동작은 후속 단계에서 구현하며 이번 명세가 공개 API를 추가하지 않는다.
- 1단계의 테스트 도구와 격리된 컨테이너 지원 코드는 존재한다. 명세 작성 시 업무 저장 구조·조회·초기화·검사는 미구현이었다. 현재 구현·실행 증거는 docs/test-evidence.md를 따른다. 기존 도구 최소 실행 자체는 이번 인수 사례의 통과 증거가 아니다.
- 저장 제약의 범위는 계획서 5.1절이다. 이름 공백 제거·최소 길이, 키 문자 규칙·최소 길이 등의 입력 규칙은 3단계 이후에서 검증하며 이번 단계에 새 저장 제약을 추가하지 않는다.
- 현재 상태와 취소 시각의 일치 검증은 상태 전이 전체의 보장이 아니다. 재활성화 방지, 수량 변경의 원자성, 생성·취소 경쟁, 응답 재현, 인증·요청 제한·HTTP 오류 변환은 후속 범위다.
- 테이블을 가로지르는 수량 보존은 개별 저장 제약만으로 보장하지 않는다. 이번 단계는 검사 도구와 탐지력을 제공하고 실제 예약·취소 처리의 보장은 후속 트랜잭션·경쟁 검증에서 다룬다.
- 계획서의 기술 선택·파일명·조회 인터페이스·검색 인덱스·단일 조회 방식·실패 확인 순서와 정확한 실행 명령은 후속 `$speckit-plan`에서 실제 저장소에 맞춰 구체화한다. 기존 도구·패키지를 교체하거나 성능 목표를 새로 정하지 않는다.

연결 단절·프로세스 중단처럼 롤백 이후 상태를 조회할 수 없는 장애의 복구 시험은11단계의 의존성 장애 검증 범위다. 이번 단계의 실패 시나리오는 연결이 정상인 실제 DB의 고의 SQL 오류로 트랜잭션 롤백을 관측한다. 조회 불가능한 상태는 불명으로 기록하고 통과로 간주하지 않으며 소유 자원 정리 후 새로운 테스트 환경에서 재개한다.
