# Feature Specification: CI·재현 가능한 실행 안내·최종 검증 기록

**Feature Branch**: `feature/013-ci-readme-final`

**Created**: 2026-10-26

**Status**: Clarified(2026-10-26)

**Input**: 사용자 요청: 계획서 7절 12단계(CI·README·설명·종료)를 Spec Kit SDD와 TDD로 개발한다. 0~11단계는 완료되었으며 반복하지 않는다. 2026-10-26 사용자 결정: verify는 PR·push에서 실제 실행, deep-tests는 수동 실행 1회, 사람 전용 항목(AI 없는 시연·작은 변경)은 준비 자료만 만들고 미완료로 표시한다.

## 기준과 범위

- 설계 기준: [계획서](<../../한정 수량 예약 백엔드 로컬 개발 계획.md>) 2~5절, 3절(로컬 구성), 6.1~6.3절(테스트 분담·Gradle 실행 계약), 7절 12단계, 8.3절, 13절. 적용 지식: `knowledge/rules/*.md` 전체, `knowledge/domain/reservation.md`·`resource.md`·`security.md`·`ratelimit.md`, 헌법 1.0.1.
- 이번 단계는 **이미 구현·검증된 동작을 외부 실행 환경(CI)과 문서로 재현 가능하게 만들고, 최종 기준점에서 전체 검증 증거를 다시 확보**한다. 업무 규칙·API 계약·SQL·스키마는 바꾸지 않는다. 재현 과정에서 실제 결함이 드러나면 규칙을 완화하지 않고 재현·원인·영향을 기록한 뒤 TDD로 최소 수정한다.
- 0~11단계의 검증은 재작성하지 않고 근거로 연결한다. 최종 기준점에서의 재실행은 “같은 명령을 최종 코드로 다시 실행한 증거”이며 새 시험 설계가 아니다.
- 범위 밖: Qodana, 외부 공개 서비스·클라우드 배포, CV 기재, 새 기능, 성능 튜닝, 정기(cron) 심화 실행, OCR 리뷰의 GitHub Actions 실행, release 브랜치·태그·main 병합(사용자 승인 사항).

## Clarifications

### Session 2026-10-26

업무 정책 질문은 없다. 사용자 질문 2건(CI 실행 범위, 사람 전용 항목 처리)은 사용자 답변으로, 나머지 설계 모호점은 계획서·실제 코드와 Explorer 갭 분석·Advisor 의견으로 해소했다(Orchestrator).

- Q: verify는 외부에서 실제로 실행하는가? → A: 사용자 결정. PR(develop/main 대상)·push(develop/main)에서 실행한다. deep-tests는 수동 트리거만 두고 이번에 1회 실행한다. OCR 리뷰는 Actions로 실행하지 않는다.
- Q: AI 없는 시연·작은 변경은? → A: 사용자 결정. 준비 자료(대본·연습 안내)만 만들고 계획서 항목은 체크하지 않은 “사용자 수행 대기”로 남긴다.
- Q: deep-tests의 명령은? → A: `./gradlew propertyTest mutationSmoke`. verify.yml이 Unit·IT·Contract를 이미 실행하므로 중복을 피한다(Advisor 권장). 수동 단독 실행 시 Unit/IT 회귀는 탐지하지 않는다는 한계를 워크플로 설명과 기록에 남긴다. `propertyTest`는 6.2절이 seed 재현 명령으로 명시한 기존 태스크다.
- Q: seed·실제 시도 수는 어떻게 남기는가? → A: 테스트 코드를 바꾸지 않는다. 기존 테스트가 표준 출력에 `seed=`·`attempts=`(실제 실행 수, `finally`에서 출력)·`generated-attempts=`를 남기고 JUnit XML `<system-out>`에 보존된다. 워크플로가 XML에서 해당 줄을 추출해 요약 파일·실행 요약으로 저장한다(Advisor의 “실제 시도 수 미출력” 지적은 `ReservationPropertyIT`의 `finally` 출력으로 사실이 아님을 확인).
- Q: 외부 실행 환경의 이미지 호환성은? → A: Explorer는 고정 digest가 arm64 전용이라 추정했으나, `docker buildx imagetools inspect`로 두 digest가 amd64를 포함한 OCI index임을 확인했다. 이미지·digest를 바꾸지 않는다.
- Q: CI가 테스트 실패를 실제 실패로 반영하는지 외부에서 증명하는가? → A: 하지 않는다. 실패 커밋을 원격에 올리는 것은 사용자 승인 범위(변경사항 push·Draft PR) 밖이다. 정적 검사(문법·금지 설정·단계 구성)와 기존 Gradle 게이트의 고의 실패 근거로 보장하고, “외부 실패 전파 미검증”을 명시한다(Advisor 동의).
- Q: 워크플로 정적 검사 수단은? → A: 버전을 고정한 actionlint와 저장소 내 검사 스크립트(금지 설정·필수 단계 확인). 결함 사본으로 검사의 탐지력을 확인한다.
- Q: 새 환경 재현 방법은? → A: 별도 디렉터리에 저장소를 새로 복제하고 별도 Compose 프로젝트 이름(새 named volume)으로 README 절차를 그대로 실행한다. 환경 변수는 `.env.example`을 복사해 새 값으로 채우며 호스트 셸의 기존 값 상속을 배제한다. 포트 비어 있음을 먼저 확인한다. 검증 후 **이 임시 프로젝트의** 볼륨만 정리할 수 있고 기존 로컬 볼륨은 건드리지 않는다.
- Q: 최종 기준 커밋과 README 재현의 순서는? → A: README 초안의 새 환경 재현을 먼저 끝내 코드·스크립트 결함을 드러낸 뒤 코드 기준점을 고정한다(Advisor 지적: 순서가 반대면 무거운 증거를 다시 실행해야 함). 기준점 이후에는 README·docs·specs·knowledge·계획서만 바꾼다. README의 실행 명령이 기준점 이후 바뀌면 바뀐 절차를 다시 재현한다.
- Q: k6 최종 실행 횟수는? → A: 시나리오당 1회. 3회 판정은 11단계에서 완료했고, 12단계는 최종 코드의 회귀 확인용임을 기록에 명시한다(Advisor 동의, 규칙 문구와의 차이를 기록).
- Q: 추적표·결함 기록·시연 자료의 위치는? → A: 추적표·미검증 목록은 `docs/traceability.md`, 시연 대본·작은 변경 안내는 `docs/demo.md` 신규 파일로 두고 `knowledge/rules/environment-and-records.md` 문서 책임 표에 등록한다. AI 결함 기록은 8.3절 템플릿의 “발견한 문제” 기록 위치인 `docs/test-evidence.md`에 12단계 절로 둔다.
- Q: deep-tests 수동 실행 1회는 언제 가능한가? → A: GitHub의 수동 트리거는 워크플로 파일이 기본 브랜치(main)에 있을 때만 동작한다. 이번 작업 브랜치·Draft PR 단계에서는 외부 수동 실행이 불가하므로, 같은 명령과 요약 추출 스크립트를 로컬에서 실행해 산출물 구성을 검증하고 외부 run은 “main 반영(사용자 승인) 후 실행 대기”로 기록한다. 워크플로에 자동 트리거를 임시로 추가하지 않는다.
- Q: 시간 상한 시험이 외부 실행 환경에서 느려 실패하면? → A: 재실행·상한 완화로 숨기지 않는다. 실제 경과·원인을 기록하고, 제품 결함인지 환경 차이인지 분류한 뒤 Advisor 분석과 사용자 판단을 받는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 변경을 올리면 외부 환경에서 기본 검증이 자동 실행되는 개발자 (Priority: P1)

개발자는 PR을 열거나 통합 브랜치에 push하면, 로컬과 같은 Gradle 명령(`verifyContract`)이 깨끗한 외부 실행 환경에서 실제 PostgreSQL·Redis 컨테이너를 사용해 실행되고, 실패는 실패로 드러나며, 결과 보고서를 내려받아 확인할 수 있기를 원한다.

**Why this priority**: 로컬 실행만으로는 환경 의존 결함(경로·아키텍처·캐시·Docker 차이)을 놓칠 수 있고, 리뷰어가 같은 근거를 볼 수 없다. 12단계의 핵심 산출물이다.

**Independent Test**: 정적 검사(워크플로 문법·금지 설정 부재·필수 단계 존재)를 통과하고, Draft PR에서 실제 실행이 성공 종료되며 보고서 artifact가 남는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 워크플로 파일이 없는 상태, **When** 정적 검사를 실행, **Then** 검사가 실패한다(검사 자체의 탐지력 확인).
2. **Given** 작성된 verify 워크플로, **When** 정적 검사를 실행, **Then** 문법 오류 0건, `continue-on-error` 0건, JDK 25·Gradle 캐시·Docker 사용 가능 실행 환경·`./gradlew verifyContract` 실행·종료 결과와 무관한 보고서 저장 단계가 모두 존재한다.
3. **Given** 의도적으로 잘못 작성한 워크플로 사본, **When** 같은 정적 검사를 실행, **Then** 실패한다(커밋하지 않음).
4. **Given** Draft PR 생성, **When** verify가 실행, **Then** 실제 run의 결론·소요 시간·Unit/IT/Contract 실행 수·실패/skip 0과 artifact 이름이 기록된다. 실행되지 않았거나 실패하면 그대로 기록하고 성공으로 표시하지 않는다.

### User Story 2 - 무거운 Property·Mutation 검증을 필요할 때 외부에서 수동 실행하는 개발자 (Priority: P2)

개발자는 Property와 PIT를 수동으로 실행하고, seed·실제 시도 수·Property 결과 XML·PIT 보고서를 artifact로 받아 재현할 수 있기를 원한다.

**Why this priority**: 무거운 검증을 매 변경마다 돌리지 않되, 필요할 때 같은 조건으로 외부에서 재현할 수 있어야 한다. 기본 검증(US1)보다 빈도가 낮다.

**Independent Test**: 정적 검사 통과 후 같은 명령·요약 추출의 로컬 실행으로 seed·시도 수·PIT 생성/탐지 수와 산출물 구성을 확인한다. 외부 수동 실행 1회는 기본 브랜치 반영 후 가능하다.

**Acceptance Scenarios**:

1. **Given** deep-tests 워크플로, **When** 정적 검사, **Then** 수동 트리거만 존재하고(자동 트리거 0), seed 입력을 받으며, Property 결과 XML·seed/시도 수 요약·PIT 보고서를 종료 결과와 무관하게 저장한다.
2. **Given** seed를 지정하지 않은 수동 실행, **When** 실행 완료, **Then** 기본 seed와 실제 시도 수가 요약에 표시되고 PIT 게이트(탐지율≥0.80·대상 밖0·무효0)가 적용된 결과가 남는다.
3. **Given** 실행 결과, **When** 기록, **Then** run 식별자·결론·seed·시도 수·PIT 수를 증거 문서에 남긴다. 기본 브랜치 반영 전이라 외부 수동 실행이 불가하면, 같은 명령·요약 추출의 로컬 실행 결과를 기록하고 외부 run은 미실행(대기)으로 표시한다.

### User Story 3 - 저장소만 받은 사람이 문서대로 처음부터 실행·검증·종료하는 개발자 (Priority: P1)

새 환경의 개발자는 README의 Quick Start만 보고 필요한 환경 확인, 환경 변수 설정, Compose 시작과 준비 대기, 마이그레이션 적용 확인, 애플리케이션 실행(Gradle 실행과 빌드 산출물 실행), API 전체 흐름, 각 검증 명령, 종료까지 수행할 수 있기를 원한다. 문서에 없는 기억이나 숨은 준비 단계가 필요하면 안 된다.

**Why this priority**: 계획서 13절 “로컬 시작·API 한 바퀴를 문서대로 재현”의 직접 근거이며, 면접·리뷰에서 재현성을 보여주는 기반이다.

**Independent Test**: 새 위치에 저장소를 복제하고 기존 로컬 데이터와 분리된 Compose 프로젝트로 README 절차를 순서대로 실행해 모든 단계의 기대 결과를 확인한다.

**Acceptance Scenarios**:

1. **Given** 갱신 전 README, **When** Quick Start 요구 항목 점검표로 확인, **Then** 누락 항목(독립 Quick Start·API 전체 흐름·준비 대기/healthcheck/URL 차이·빌드 산출물 실행)이 실패로 드러난다.
2. **Given** 갱신된 README와 새로 복제한 저장소, **When** 문서 순서대로 실행, **Then** Compose 서비스가 healthy가 된 뒤 앱이 기동하고 health가 UP이며, 대상 생성 → 예약 생성 → 같은 키 재요청 → 조회 → 취소 → 중복 취소 → 취소 후 생성 재요청 → 대상 조회의 응답과 최종 수량이 문서의 기대값과 일치한다.
3. **Given** 빌드 산출물, **When** 문서의 산출물 실행 절차를 따름, **Then** Gradle 실행과 같은 health·API 결과를 얻는다.
4. **Given** 실행 종료, **When** 문서의 종료 절차를 따름, **Then** 앱·서비스가 종료되고 named volume은 보존되며 볼륨 삭제는 기본 절차에 없다.
5. **Given** README의 모든 명령, **When** 저장소의 실제 스크립트·태스크·설정과 대조, **Then** 존재하지 않는 명령이 0건이고, 테스트 수 등 수치는 최신 실행 증거와 일치한다.

### User Story 4 - 최종 기준점에서 전체 검증 증거를 확보하는 개발자 (Priority: P1)

개발자는 12단계의 마지막 코드 기준점(이후 문서 기록만 바뀌는 커밋)에서 심화 테스트 전체·PIT·원래 제한값의 보안/Redis 시험·k6 네 시나리오를 실행하고, 해당 커밋과 결과를 기록하며, 고의로 넣은 오류가 남아 있지 않음을 확인하기를 원한다.

**Why this priority**: 이전 단계 증거는 각 시점의 코드에 대한 것이다. 최종 상태에 대한 단일 기준점 증거가 13절 완료 조건이다.

**Independent Test**: 기준 커밋 SHA를 고정하고, 해당 커밋의 깨끗한 작업 트리에서 명령을 실행해 종료 코드·실행 수·판정·DB 검사 결과를 저장한다.

**Acceptance Scenarios**:

1. **Given** 기준 커밋의 깨끗한 작업 트리, **When** 심화 테스트 전체와 PIT를 실행, **Then** 종료 0, Unit/IT/Contract/Property 실행 수>0·실패/오류/skip 0, PIT 생성=탐지·게이트 통과가 기록된다.
2. **Given** 원래 제한값(20회/60초), **When** 보안·Redis 제한·장애 시험을 지정 실행, **Then** 통과와 해당 시험이 원래 제한값으로 실행됐다는 근거가 기록된다.
3. **Given** 기준 커밋의 load 환경, **When** low·high·replay·rate-limit를 각각 실행, **Then** k6 threshold 종료 코드 0과 종료 후 DB 불변식 검사 통과가 결과 디렉터리와 함께 기록되고, 결과 meta에 기준 커밋과 작업 트리 clean 여부가 남는다.
4. **Given** 저장소, **When** 고의 결함 잔존 검사(작업 트리 diff·고의 표식 검색·전체 테스트 통과), **Then** 잔존 0건이 기록된다.
5. **Given** 기준 커밋 이후 커밋, **When** 변경 경로를 비교, **Then** 애플리케이션·테스트·load·Compose·워크플로 변경이 없음을 확인한다. 변경이 있으면 영향받는 검증을 다시 실행한다.

### User Story 5 - 규칙과 증거를 추적하고 설명을 준비하는 개발자 (Priority: P2)

개발자는 “규칙 → 대상 클래스 → 테스트 이름 → 실행 명령 → 증거” 추적표와 검증하지 않은 범위 목록, 개발 중 실제로 발견한 AI 구현 결함 기록, 5분 시연 대본과 작은 변경 연습 안내를 갖고 싶다. 시연과 작은 변경 자체는 사람이 AI 없이 수행해야 하므로 준비 자료만 만든다.

**Why this priority**: 설명 능력과 이해 확인을 위한 자료다. 기능·검증 증거(US1~US4)가 먼저 있어야 정확히 연결할 수 있다.

**Independent Test**: 추적표의 각 행이 실제 존재하는 클래스·테스트 메서드·명령·증거 위치를 가리키는지 기계적으로 대조하고, 결함 기록의 각 사례가 증거 문서·커밋에서 실제 결함(학습용 고의 변경 아님)으로 확인되는지 검사한다.

**Acceptance Scenarios**:

1. **Given** 추적표, **When** 각 행의 클래스·테스트 메서드·명령을 저장소와 대조, **Then** 존재하지 않는 참조 0건이며 계획서 2절의 핵심 규칙(입력 경계, 1개 예약·사용자 UUID, 상태 전이, 수량 불변식, 멱등성, 취소 복구, 실패 롤백, 권한, 요청 제한, 장애)이 모두 한 행 이상 연결된다.
2. **Given** 미검증 범위 목록, **When** 확인, **Then** 각 항목에 이유가 있다.
3. **Given** AI 결함 기록, **When** 각 사례를 증거와 대조, **Then** 재현 → 원인 → 탐지 테스트 → 수정 → 한계가 모두 있고, 실제 결함과 고의 변이 결과가 구분되어 있다. 근거가 확인되지 않는 사례는 싣지 않는다.
4. **Given** 시연 대본, **When** 확인, **Then** 마지막 수량 경쟁·같은 키 재시도·타인 예약 취소·Redis 중단의 네 주제가 실제 존재하는 명령·테스트로 5분 안에 보일 수 있게 구성되고, 계획서의 시연·작은 변경 항목은 “사용자 수행 대기”로 체크되지 않은 채 남는다.

### Edge Cases

- 외부 실행 환경의 CPU 아키텍처가 로컬(arm64)과 다를 때 고정 이미지 digest가 해당 플랫폼을 포함하지 않으면 실패한다 → 사전에 멀티 아키텍처 여부를 확인하고 기록한다(2026-10-26 확인: 두 digest 모두 amd64 포함 index).
- 외부 실행 환경의 느린 디스크·CPU로 시간 상한 시험이 실패할 수 있다 → 재실행으로 숨기지 않고 실제 경과·원인을 기록한 뒤 판단한다. 상한을 임의로 늘리지 않는다.
- 외부 실행의 일시적 컨테이너 연결 실패(11단계에 관찰된 Redis 접속 실패 사례) → 실패로 기록하고 원인을 분류한다. 자동 재시도로 숨기지 않는다.
- 새로 복제한 환경의 Compose가 기존 로컬 볼륨·포트와 충돌 → 별도 Compose 프로젝트 이름과 포트 사용 가능 여부를 먼저 확인하고, 기존 로컬 데이터를 삭제하지 않는다.
- k6 실행 중 기준 커밋과 작업 트리가 달라짐 → 결과 meta의 commit·dirty로 탐지하고 무효 실행으로 분류한다.
- 문서 기록 커밋이 기준 커밋 뒤에 쌓임 → 기록 대상 경로 외 변경이 없는지 비교한다.
- 리뷰 수정이 코드를 바꿈 → 기준 커밋을 갱신하고 영향받는 검증을 다시 실행한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 저장소는 PR과 통합 브랜치 push에서 실행되는 기본 검증 워크플로를 가져야 하며, JDK 25·Gradle 캐시·컨테이너 실행 가능 환경에서 6.2절의 `./gradlew verifyContract`를 실행해야 한다.
- **FR-002**: 모든 워크플로는 실패를 숨기는 설정(`continue-on-error`, 실패 무시 셸 구문, 테스트 제외 옵션)을 사용하지 않아야 하며, 테스트 결과·보고서를 종료 결과와 무관하게 artifact로 저장해야 한다.
- **FR-003**: 심화 검증 워크플로는 수동 트리거만 가져야 하며, Property(seed 입력 선택)와 PIT를 실행하고 Property 결과 XML·seed·실제 시도 수 요약·PIT 보고서를 저장해야 한다. Gradle 경로와 계획서의 Maven 경로 표기 차이를 기록해야 한다.
- **FR-004**: 워크플로는 최소 권한, 고정된 실행 환경 버전(`latest` 계열 미사용), 고정된 외부 action 버전, 실행 시간 상한, 동일 브랜치 중복 실행 정리를 가져야 한다.
- **FR-005**: 워크플로 정적 검사 절차가 있어야 하며, 그 절차가 결함 있는 워크플로를 실패시키는지 확인해야 한다.
- **FR-006**: 외부 CI의 실제 run 결과(식별자·결론·실행 수·artifact)는 실제로 확인한 경우에만 성공으로 기록하고, 파일 작성만으로 CI 성공을 주장하지 않아야 한다.
- **FR-007**: README는 독립된 Quick Start에 필요한 환경·환경 변수·Compose 시작과 준비 대기·마이그레이션 적용과 확인·앱 실행(Gradle 실행과 빌드 산출물 실행)·API 전체 흐름과 기대 결과·각 검증 명령과 범위·종료 절차를 담아야 한다.
- **FR-008**: README는 컨테이너 시작 대기(Compose wait)·healthcheck(서비스 준비)·애플리케이션 health의 차이와 각 접속 URL(호스트 127.0.0.1 포트, 테스트의 동적 포트)을 설명해야 한다.
- **FR-009**: README와 docs의 명령·수치는 실제 존재하는 스크립트·태스크·최신 실행 증거와 일치해야 한다. 만들지 않은 명령을 싣지 않는다.
- **FR-010**: Quick Start는 새로 복제한 저장소·분리된 Compose 프로젝트에서 처음부터 실행되어야 하며, 그 실행 기록(명령·결과·기대값 대조)이 남아야 한다. 기존 로컬 데이터와 볼륨을 삭제하지 않는다.
- **FR-011**: 최종 코드 기준 커밋에서 `deepTest`, `mutationSmoke`, 원래 제한값의 보안·Redis 시험, k6 low·high·replay·rate-limit를 실행하고 커밋 SHA·명령·종료 코드·실행 수·판정·DB 검사 결과를 기록해야 한다.
- **FR-012**: 고의로 넣은 오류가 남아 있지 않음을 작업 트리 비교·고의 표식 검색·전체 테스트 통과로 확인해야 한다.
- **FR-013**: “규칙 → 대상 클래스 → 테스트 이름 → 실행 명령 → 증거” 추적표와 이유가 붙은 미검증 범위 목록이 있어야 하며, 참조는 실제 존재해야 한다.
- **FR-014**: 개발 중 실제로 발견한 AI 구현 결함을 재현 → 원인 → 탐지 테스트 → 수정 → 한계로 기록해야 한다. 근거가 없는 사례를 만들지 않으며 고의 변이 검증과 구분한다.
- **FR-015**: 네 주제(마지막 수량 경쟁·같은 키 재시도·타인 예약 취소·Redis 중단)의 5분 시연 대본과 작은 변경(예: 생성 키 최대 길이) 연습 안내를 제공해야 하며, 사람이 수행해야 하는 시연·작은 변경·AI 없는 설명 항목은 체크하지 않은 “사용자 수행 대기”로 남겨야 한다.
- **FR-016**: decisions·test-evidence·performance·versions·계획서(12단계·13절 체크박스, 6.2절 수치)·knowledge 문서를 실제 상태에 맞게 최종 갱신해야 하며, 체크박스는 실제 실행·검증된 항목만 표시해야 한다.
- **FR-017**: 업무 규칙·API 계약·SQL·스키마·의존성 버전을 바꾸지 않아야 한다. 실제 결함 수정이 필요하면 RED 확인 후 최소 수정하고 관련 문서·계약·테스트를 함께 갱신한다.

### Key Entities

- **워크플로**: 트리거·실행 환경·권한·단계·artifact를 가진 외부 CI 정의. 기본 검증과 심화 검증 두 개.
- **CI 실행 기록**: run 식별자·트리거·커밋·결론·소요 시간·실행 수·artifact.
- **최종 기준 커밋**: 이후 문서 기록만 바뀌는 코드 기준점. 모든 최종 증거가 참조한다.
- **추적 행**: 규칙(계획서 절) → 대상 클래스 → 테스트 이름 → 실행 명령 → 증거 위치.
- **결함 기록**: 단계·재현·원인·탐지 테스트·수정 커밋·한계·구분(실제/고의).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Draft PR의 기본 검증 run이 실제로 실행되어 결론이 기록되며, 성공일 경우 Unit·IT·Contract 실행 수가 각각 1 이상이고 실패·skip 0이다. 보고서 artifact 1개 이상이 남는다.
- **SC-002**: 심화 검증의 같은 명령·요약 추출을 로컬에서 실행해 seed·실제 시도 수(100 이상)·PIT 생성/탐지 수와 산출물 구성을 확인한다. 외부 수동 run은 기본 브랜치 반영 후 실행하며, 그 전에는 미실행(대기)으로 기록한다.
- **SC-003**: 워크플로 정적 검사 오류 0건, 금지 설정 0건이며, 결함 사본에서 검사가 실패한다.
- **SC-004**: 새로 복제한 환경에서 Quick Start 전 단계가 문서 수정 없이 통과하거나, 실패한 단계가 원인과 함께 기록되고 문서 수정 후 재실행으로 통과한다. API 흐름의 응답 상태·최종 수량이 문서 기대값과 100% 일치한다.
- **SC-005**: 최종 기준 커밋에서 심화 테스트 전체 종료 0(실패·오류·skip 0), PIT 생성=탐지·게이트 통과, k6 네 시나리오 threshold 종료 0과 DB 불변식 위반 0건이 기록된다.
- **SC-006**: 추적표에서 존재하지 않는 참조 0건, 계획서 2절 핵심 규칙 미연결 0건.
- **SC-007**: README·docs의 명령 중 저장소에 없는 명령 0건, 최신 증거와 다른 테스트 수치 0건.
- **SC-008**: 고의 결함 잔존 0건, 업무 계약·SQL·스키마 변경 0건(실제 결함 수정이 있었다면 해당 기록과 연결).

## Assumptions

- GitHub 저장소는 공개이며 Actions가 활성화되어 있다(2026-10-26 확인). 사용자는 Draft PR 생성·push와 그에 따른 verify 실행, deep-tests 수동 실행 1회를 승인했다.
- 외부 실행 환경은 GitHub 호스팅 Linux runner(x86_64)이며 Docker를 제공한다. 고정 이미지 digest는 amd64·arm64를 포함한 index임을 확인했다.
- 테스트는 고정 테스트 계정을 사용하며 `.env`나 비밀 값이 필요 없다(앱 local/load 프로필만 환경 변수 필요). CI에 저장소 secret을 추가하지 않는다.
- 로컬 포트 5432·6379·8080은 현재 비어 있고 기존 Compose 컨테이너는 정지 상태다. 새 환경 재현은 별도 Compose 프로젝트 이름으로 수행한다.
- “최종 commit”은 애플리케이션·테스트·load·Compose·워크플로가 더 바뀌지 않는 커밋으로 정의하고, 이후 커밋은 증거·문서 기록만 담는다.
- 사람이 수행할 시연·작은 변경·AI 없는 설명은 이번 자동화 범위 밖이며 사용자 수행 대기로 남는다(2026-10-26 사용자 결정).
- release 브랜치·태그·main 병합은 사용자 승인 후 별도로 수행한다.
