# 기능 명세: 예약 입력과 취소 판단의 기본 규칙 검증

**작업 브랜치**: `feature/validate-domain-rules` (문서 원본: docs/validate-domain-rules)

**작성일**: 2026-10-15

**상태**: 순수 규칙 구현·Unit 검증 완료, 사용자 완료 지시로 T029 처리·작업33/33 완료. 독립 재설명 시험 및 실제 요청 경로 연동 미완료

**입력**: 사용자가 선택한 [로컬 개발 계획](<../../한정 수량 예약 백엔드 로컬 개발 계획.md>) 7절의 「3단계: Spring 없이 규칙 검증」. 최초 수량·이름·생성 키의 경계와 현재 상태에 따른 취소 판단을 독립적으로 검증하고 개발자가 기대 결과의 이유를 설명할 수 있게 한다.

## 사용자 시나리오와 검증 *(필수)*

### 사용자 이야기 1 - 대상의 유효한 이름과 최초 수량 구분 (우선순위: P1)

개발자는 관리자가 입력할 이름과 최초 수량을 직접 대조해 허용·거부 경계를 확인한다. 이름의 앞뒤 공백을 정리한 결과와 문자 수를 확인하고, 수량 0인 대상도 유효하다는 점을 이해한다.

**우선순위 이유**: 이후 대상 생성과 예약 가능 수량 검증에 일관된 입력 기준이 필요하다.

**독립 검증**: 이름·정수 수량의 실제 값을 각각 전달해 허용 여부와 정리된 이름을 확인한다. 대상 저장이나 예약 생성은 필요하지 않다.

**인수 시나리오**:

1. **조건** 최초 수량이 정수일 때, **행동** -1·0·1·1000·1001을 각각 검사하면, **결과** 0·1·1000만 허용하고 -1·1001은 거부한다.
2. **조건** 이름이 없거나 빈 문자열일 때, **행동** 이름을 검사하면, **결과** 모두 거부한다. 일반 공백·탭·줄바꿈만 있는 이름도 정리 후 빈 문자열이므로 거부한다.
3. **조건** 이름이 `  예약 대상  ` 또는 앞뒤에 탭·줄바꿈을 붙인 `예약 대상`일 때, **행동** 이름을 정리하면, **결과** `예약 대상`을 얻고 내부 공백은 유지한다. 다시 정리해도 같은 값이다.
4. **조건** 앞뒤 제거 대상 공백을 정리한 이름일 때, **행동** 일반 문자 1개·100개·101개를 각각 검사하면, **결과** 1개·100개는 허용하고 101개는 거부한다.
5. **조건** 이름 길이를 유니코드 코드 포인트로 셀 때, **행동** `😀` 100개·101개와 `가` 99개 뒤 `😀` 1개인 이름을 검사하면, **결과** 100개와 혼합 이름은 허용하고 101개는 거부한다. 앞뒤 일반 공백을 붙인 `😀` 100개도 허용하며 반환 이름에는 그 공백이 없다.
6. **조건** 이름에 U+00A0·U+2007·U+202F가 있을 때, **행동** 각 문자를 이름 앞뒤에 두거나 그 문자 하나만 이름으로 검사하면, **결과** 유지하며 길이에 포함한다. 각 문자 100개는 허용하고 101개는 거부한다.

---

### 사용자 이야기 2 - 생성 키의 정확한 값과 경계 보존 (우선순위: P1)

개발자는 예약 사용자의 생성 키가 허용 문자와 길이를 만족하는지 확인하고 대소문자나 공백을 바꾸어 요청 구분 기준이 달라지지 않는지 확인한다.

**우선순위 이유**: 키를 임의로 변환하면 후속 재요청 판단을 신뢰할 수 없다.

**독립 검증**: 사용자·예약 저장 없이 키만 전달해 허용·거부와 허용 원문 보존을 확인한다.

**인수 시나리오**:

1. **조건** 키가 없거나 빈 문자열일 때, **행동** 검사하면, **결과** 모두 거부한다.
2. **조건** ASCII 영문 대문자·소문자·숫자·하이픈·밑줄만 있는 키일 때, **행동** 1자·64자·65자를 검사하면, **결과** 1자·64자는 원문 그대로 허용하고 65자는 거부한다. 하이픈 또는 밑줄 하나도 허용한다.
3. **조건** 키가 `Ab-1`·`ab-1`일 때, **행동** 검사하고 비교하면, **결과** 둘 다 허용하며 서로 다른 값으로 유지한다. 같은 원문의 키는 같은 값으로 판단한다.
4. **조건** 키에 앞뒤 또는 내부 일반 공백·탭·줄바꿈이 있거나 공백만 있을 때, **행동** 검사하면, **결과** 공백을 제거해 수용하지 않고 모두 거부한다. 유효한 키 끝 줄바꿈 하나도 거부한다.
5. **조건** 키에 한글·`😀`·마침표·슬래시·콜론·U+00A0 또는 전각 영문·숫자가 있을 때, **행동** 검사하면, **결과** 길이가 범위 안이어도 모두 거부한다.

---

### 사용자 이야기 3 - 현재 상태에 맞는 취소 판단 (우선순위: P2)

개발자는 현재 예약 상태에 따라 취소를 진행할지 이미 취소된 예약으로 취급할지 확인한다. 이미 취소된 예약을 새 취소 대상으로 판단하지 않아야 한다.

**우선순위 이유**: 취소 처리에서 수량을 한 번만 복구하기 위한 기본 분기를 구분해야 한다.

**독립 검증**: 현재 상태 두 가지를 각각 전달해 취소 판단을 비교한다. 실제 예약 변경·수량 복구는 수행하지 않는다.

**인수 시나리오**:

1. **조건** 현재 상태가 `CONFIRMED`일 때, **행동** 취소 여부를 판단하면, **결과** `CANCEL_NOW`(지금 취소 진행)를 반환한다.
2. **조건** 현재 상태가 `CANCELLED`일 때, **행동** 취소 여부를 판단하면, **결과** `ALREADY_CANCELLED`(이미 취소됨)를 반환한다.
3. **조건** 같은 현재 상태를 반복 전달할 때, **행동** 취소 여부를 판단하면, **결과** 매번 같은 판단을 얻고 판단 자체는 현재 상태·수량·취소 시각을 변경하지 않는다.

### 경계 사례

- 수량 -1·0·1·1000·1001: 0의 유효성과 상한 포함 여부를 각각 구분한다.
- 이름 누락·빈 문자열·제거 대상 공백만 있는 입력과 정리 후 1·100·101 코드 포인트.
- 원문 길이가 100을 넘더라도 앞뒤 공백 제거 후 100이면 허용한다. 정리 후 101이면 자르지 않고 거부한다.
- `😀` 100개·101개와 일반 문자·`😀`가 섞인 경계. 화면상의 글자 묶음이나 저장 바이트 수 대신 코드 포인트 수를 사용한다.
- 앞뒤 일반 공백·탭·줄바꿈과 내부 공백, 제거하지 않는 U+00A0·U+2007·U+202F를 구분한다.
- 생성 키 누락·빈 문자열·1·64·65자, 대소문자 차이, 허용된 하이픈·밑줄과 금지 구분 문자.
- 유효한 생성 키 앞뒤 공백·끝 줄바꿈: 이름 정리 규칙을 키에 적용하지 않는다.
- 두 예약 상태와 반복 취소 판단: 판단만으로 상태 전이나 수량 복구를 수행하지 않는다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 최초 수량은 정수 0~1000을 양 끝 포함해 허용하고 범위 밖은 거부해야 한다. 수량 0을 유효하지 않은 입력으로 취급하지 않아야 한다. 이야기 1.1로 검증한다.
- **FR-002**: 이름이 없으면 거부하고 앞뒤 제거 대상 공백을 먼저 정리한 뒤 유니코드 코드 포인트 기준 1~100개만 허용해야 한다. 초과 이름을 잘라서 허용하지 않아야 한다. 이야기 1.2·1.4·1.5로 검증한다.
- **FR-003**: 이름 정리는 기존 확정 공백 정책을 유지해야 한다. 앞뒤 일반 공백·탭·줄바꿈을 제거하고 내부 공백은 보존하며 U+00A0·U+2007·U+202F는 제거하지 않고 길이에 포함해야 한다. 허용된 이름은 정리한 값을 반환하고 재정리해도 값이 같아야 한다. 이야기 1.3·1.5·1.6으로 검증한다.
- **FR-004**: 생성 키는 ASCII 영문 대소문자·숫자·하이픈·밑줄로만 구성된 1~64자만 허용해야 한다. 누락·빈 값·초과 길이·다른 문자 하나라도 포함된 키는 거부해야 한다. 이야기 2.1·2.2·2.4·2.5로 검증한다.
- **FR-005**: 허용된 생성 키의 원문과 대소문자를 보존하고 같은 원문은 같은 값, `Ab-1`과 `ab-1`은 다른 값으로 판단해야 한다. 공백 제거·문자 변환으로 잘못된 키를 수용하지 않아야 한다. 이야기 2.2~2.4로 검증한다.
- **FR-006**: 취소 판단은 `CONFIRMED`를 `CANCEL_NOW`, `CANCELLED`를 `ALREADY_CANCELLED`로 대응시켜야 한다. 판단은 상태·수량·시각을 변경하지 않으며 같은 입력에는 같은 결과를 반환해야 한다. 이야기 3으로 검증한다.
- **FR-007**: 개발자는 이야기 1~3의 실제 입력과 기대 결과를 직접 대조해 검증할 수 있어야 한다. 규칙 검증에 애플리케이션 기동이나 외부 저장소 연결을 요구하지 않아야 한다. 성공·거부·반환 값·값 비교·취소 판단을 각각 확인해 단순 실행 성공과 구분해야 한다.
- **FR-008**: 검증 기록은 규칙별 의도한 동작 실패와 수정 후 성공을 구분하고 실행 명령·종료 코드·실행 수·실패 수·건너뜀 수·환경·미검증 범위를 남겨야 한다. 검증 0건·실패·건너뜀을 통과로 기록하지 않아야 한다. 개발자는 경계값 최소 1개의 허용·거부 이유와 각 검증이 잘못된 어떤 동작을 찾는지 설명할 수 있어야 한다.

### 핵심 개체

- **대상 입력**: 이름과 최초 수량이다. 이름은 정리한 값과 코드 포인트 길이가 의미를 가지며 최초 수량은 0을 포함한 정수 범위를 가진다.
- **예약 생성 키**: 허용 문자·길이를 만족하는 원문 값이다. 재사용 여부나 사용자별 범위는 후속 예약 처리에서 판단한다.
- **현재 예약 상태**: 확정(`CONFIRMED`) 또는 취소(`CANCELLED`)다. 이번 단계는 현재 상태에 대한 판단만 제공한다.
- **취소 판단**: 취소 진행(`CANCEL_NOW`) 또는 이미 취소됨(`ALREADY_CANCELLED`)이며 현재 상태와 구분한다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 이야기 1의 수량 5개 값과 이름 정상·거부·공백·코드 포인트 경계 사례가 모두 기대 결과와 일치한다. 허용된 이름의 반환 값 불일치는 0건이다.
- **SC-002**: 이야기 2의 키 길이·문자·공백 사례가 모두 기대대로 허용 또는 거부되고 허용 키의 원문 변형은 0건이다. 동일 원문의 동등 판단과 대소문자가 다른 두 키의 구별이 모두 성립한다.
- **SC-003**: 현재 상태 두 가지가 각각 명시한 취소 판단과 100% 일치하며 반복 판단에 의한 상태·수량·취소 시각 변경은 0건이다.
- **SC-004**: 개발자는 외부 서비스 접속 없이 이야기 1~3 전체를 재현하고 모든 인수 사례를 실제 검증 결과에 대응시킬 수 있다. 미실행 사례를 통과로 표시하는 경우는 0건이다.
- **SC-005**: 개발자는 경계값 최소 1개에 대해 입력·기대 결과·규칙상 이유를 설명하고 전체 검증 항목의 확인 대상과 실패 조건을 설명할 수 있다. 설명의 확인 여부를 실행 통과 여부와 구분해 기록한다.

## 전제와 의존성

- 기준은 계획서 2~5절과 7절 3단계, [resource 지식](../../knowledge/domain/resource.md), [reservation 지식](../../knowledge/domain/reservation.md)이다. 이름의 정확한 공백 범위는 계획서 2절의 기존 확정 정책을 따른다. 이번 명세는 입력·저장·외부 계약을 변경하지 않는다.
- 이번 단계의 사용자는 규칙을 직접 이해·검증하는 개발자다. 관리자와 예약 사용자는 이후 요청 처리에서 이 규칙의 적용을 받는다. 새 업무 도메인을 추가하지 않는다.
- 기존 저장 기반과 두 예약 상태는 이미 존재한다. 입력 규칙과 취소 판단은 명세 작성 시 미구현이었으며 현재 구현·Unit 검증됨이다. 기존 도구 최소 검증과 저장 제약 검증은 이번 규칙 검증의 통과 증거가 아니다.
- 이번 인수 범위는 순수 규칙과 그 검증이다. 인증·입력 형식 변환·오류 응답 변환·저장·멱등 응답 재현·취소 상태 갱신·수량 복구·경쟁 보장은 후속 범위이며 판단 검증만으로 보장됐다고 보고하지 않는다. 정수가 아닌 수량의 입력 거부는 후속 입력 형식 검증에서 다룬다.
- 계획서의 실제 요청 경로 사용 조건을 유지한다. 4단계 대상 생성에 이름·수량 규칙, 5단계 예약 생성에 생성 키 규칙, 6단계 취소의 이미 취소됨 분기에 취소 판단을 연결하고 검증해야 한다. 이번 순수 규칙 인수와 별도로 연동이 확인될 때까지 요청 경로 사용 조건은 미완료로 남긴다. 점수용으로만 존재하는 규칙으로 최종 완료 처리하지 않는다.
