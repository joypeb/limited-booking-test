# Specification Quality Checklist: 고정 OpenAPI와 실제 업무 API 계약 검증

**Purpose**: 계획 전 명세의 완전성·명확성·검증 가능성을 검토한다.

**Created**: 2026-10-23

**Feature**: [spec.md](../spec.md)

**Review Ownership**: specify 문서 품질 검토다. 체크는 구현·실행 통과를 의미하지 않는다.

## Content Quality

- [x] 새로운 언어·프레임워크·코드 구조를 설계하지 않았다. 기존 지정 인터페이스·실행 제약은 별도 절에 구분했다.
- [x] 사용자 가치와 업무 필요에 초점을 맞췄다.
- [x] 사용자 시나리오는 개발자와 API 사용자가 이해할 기대 결과로 작성했다.
- [x] 필수 섹션을 모두 작성했다.

## Requirement Completeness

- [x] 미해결 확인 표시는 없다.
- [x] 요구사항이 시험 가능하고 모호하지 않다.
- [x] 성공 기준이 수치·결과로 측정 가능하다.
- [x] 성공 기준은 특정 구현 도구가 아닌 계약 적합성·거부 탐지·상태 보존으로 판정한다.
- [x] 모든 사용자 이야기에 인수 시나리오를 정의했다.
- [x] 무효 요청·UTC·헤더·default·본문 상한·상태별 null 등의 경계를 명시했다.
- [x] 9단계 범위와 10단계 등 제외 범위를 구분했다.
- [x] 기존 프로브·검증 태스크·업무 API·실제 의존성의 재사용과 한계를 명시했다.

## Feature Readiness

- [x] FR-001~012에 US1~4와 인수·경계 사례를 연결했다.
- [x] 정상·오류·재전송·탐지력의 주요 흐름을 포괄한다.
- [x] SC-001~005에 작업별 조합·오판정·고의 변경·상태 보존·실행 증거를 포함했다.
- [x] 새 구현 설계를 넣지 않았다. 메서드 시그니처와 명령은 사용자/계획서 지정 제약으로 구분했다.

## Notes

- 1차 작성 후 2차 근거 대조: 16/16 품질 항목 충족. 실제 기능 시험은 실행하지 않았다.
- US1/FR-001~002/005~006: 5작업·고정 독립 명세·실제 HTTP 전체 전달·UUID·UTC·enum·필수/미정의 필드·헤더를 확인했다.
- US2/FR-003~004/007: 요청 위반 전체 무시·응답 검사 생략을 금지했다. 정상 요청은 양쪽 적합, 의도적 무효 요청은 예상 위반 및 유효 오류 응답을 각각 판정한다. 인증/본문 상한 선행 거부도 구분했다.
- 적용표는 정상 전부와 400/401/403/404/409/413/415/429/503을 포함한다. 두409 code·DB/Redis503·필터 오류·전역 GET413을 명시했다. 4.1 GET 주요 실패 요약과 전역413 규칙의 차이는 Assumptions에 근거를 적어 해소했다.
- US3/FR-008: 취소 후 최초 CONFIRMED 재현·현재 CANCELLED 조회·중복 취소 동일 시각·추가 수량 변경0을 확인했다.
- US4/FR-009~012: 필수 id 제거·status 훼손뿐 아니라 타입/UTC/헤더/code/예상 밖 status를 포함했다. 실제 DTO의 컴파일 가능한 변경과 실제HTTP 실패·원복 통과는 응답 사본 훼손과 구분했다.
- 기존 ToolchainContractValidator는 GET프로브 전용, ToolchainContractIT의 business 검사는 파싱뿐이다. 기존 Gradle의 리소스 복사·contract 태그·의존성 게이트를 재사용 가능하되 업무 검증 완료로 표현하지 않았다.
- 최신 사용자 지시로 이번 Qodana는 미실행 사용자 후속이며 완료·PR·병합 게이트에서 제외했다. 과거8단계 유예를 자동 승계하지 않았다. 미확정·차단 조건 또는 통과로 기록하지 않았다.
- resolve-template.sh spec-template --json으로 활성 템플릿을 확인했다. extensions.yml이 없어 before/after specify 훅은 없다. 기존 feature/010-openapi-contract 브랜치를 유지했다. create-new-feature.sh의 --allow-existing-branch는 기존 디렉터리 재사용 옵션임을 조사했고, 이번 core specify는 지정 디렉터리를 직접 만들 수 있어 해당 스크립트를 실행하지 않았다. 번호010의 기존 specs 충돌도 없다.
- 문서 링크·필수 섹션·식별자·미해결 표식·변경 범위를 검사했다. plan/tasks·구현·OpenAPI 확정본 수정·테스트 실행·커밋·외부 작업은 수행하지 않았다. 후속은 메인의 명세 검토 후 plan이다.
